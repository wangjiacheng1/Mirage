# 04 · 落地路线图

| 项 | 值 |
|---|---|
| 文档版本 | **v2.0**(KMP + 不发布 修订) |
| 假设投入 | 1 名 Android 开发(你)+ 外部设计师;每周有效工时 20~30h |
| 总周期 | 约 **19~25 周** 到可对外分发版本 |
| v2.0 变更 | M1 并入 KMP 脚手架(+1~2 周);M6 由"合规与上架"改为"打包与分发(轻量)"(-1~2 周) |

> 时间是"有效工作周"而非日历周。如果是业余时间推进,请把每个里程碑的周数乘 1.5~2。

## M0 · Prompt 原型验证(1 周)

> **这一步是整个项目最高性价比的投入,绝对不要跳过。**
> 在 Android 里调 Prompt 的迭代速度比在命令行里慢 10 倍。如果你在这一步发现"角色扮演其实很难稳",你会省下几个月的错误投入。

### 具体任务

| # | 任务 | 产出 |
|---|---|---|
| 0.1 | 注册 2 个服务商账号(建议 DeepSeek + OpenRouter),各充 ¥20~50 | 2 个可用 Key |
| 0.2 | 用 curl 或 20 行 Python 跑通一次 `chat/completions` 非流式请求 | 跑通的脚本 |
| 0.3 | 跑通流式请求,观察 SSE 的原始数据格式(**亲眼看一遍 chunk 结构,后面写 Android 时会清晰很多**) | 流式脚本 |
| 0.4 | 写一个角色扮演 System Prompt(参照 `docs/05` 模板),选一个你自己想玩的角色 | v0.1 Prompt |
| 0.5 | 手动进行 3 段 20 轮以上的对话,记录所有"崩了"的瞬间(出戏、复读、替用户说话、忘设定) | 问题清单 |
| 0.6 | 针对问题清单迭代 Prompt 到 v0.5,确认哪些问题"靠 Prompt 能解"、哪些"必须靠工程解" | v0.5 Prompt + 结论 |
| 0.7 | 跑通一次 **Function Calling**,让模型输出 `update_state` | 工具调用脚本 |
| 0.8 | 测试不支持 tools 的模型下的 JSON 代码块降级方案 | 降级方案验证 |
| 0.9 | 建立 **评测集 v1**:15 个"刁难场景"(见 `docs/08`),记录当前 Prompt 的基线表现 | 评测集 + 基线 |
| 0.10 | 实测 3~4 个模型(贵/便宜/国内/国外)的角色扮演表现差异,确定推荐模型列表 | 模型推荐表 |

### 验收标准

- [ ] 能用一条命令跑完一个 20 轮对话脚本并把结果存成文件
- [ ] 20 轮对话中人设崩坏次数 ≤ 1
- [ ] Function Calling 与 JSON 降级两条路都验证通过
- [ ] 评测集 15 个场景有明确的基线记录(通过/不通过)
- [ ] 产出一份"哪些问题必须靠客户端工程解决"的清单 —— 这直接定义了 M3/M4 的需求

### 常见坑

- 不要一上来就写 2000 字的 System Prompt。从 200 字开始加,每次只加一条规则,观察效果。
- `temperature` 先固定 0.9,等 Prompt 稳了再调。
- 示例对话(few-shot)的效果往往比写十条规则更好,优先试它。

### 验收标准

- [ ] `:shared` 的 commonTest 能在 JVM 上独立跑通,不需要模拟器
- [ ] 能完成一次 10 轮的流式对话,中途可中断,重启 App 历史完好
- [ ] 断网、Key 填错、模型名填错,三种情况都给出正确的具体提示(不是"未知错误")
- [ ] 流式过程中退出页面,Ktor 请求确实被取消(抓包或日志验证)
- [ ] 调试面板能看到完整请求体
- [ ] `ContextBuilder` 单测覆盖率 > 80%
- [ ] **Room KMP 验证关卡已有明确结论**(继续用 / 切 SQLDelight)
- [ ] `presentation` 包内 grep 不到任何 `android.` 导入

### 风险提示

**最容易卡住的四件事:**
① Ktor `requestTimeoutMillis` 没设成无限,导致长回复中途被掐断(**最高频的坑**);
② 协程取消时连接未真正关闭,造成泄漏与持续计费;
③ 流式文本每 token 触发重组导致严重掉帧;
④ KMP 工具链配置问题(Gradle 插件版本不匹配、IDE 索引异常)—— 遇到先查版本矩阵,不要硬调。

前三项在 `docs/02` §5.2 / §5.10 有解法,提前看。

## 关键依赖与并行安排

```
M0 Prompt  ──┐
             ├─→ M1 骨架 ─→ M2 MVP ─→ M3 记忆 ─→ M4 游戏化 ─→ M5 打磨 ─→ M6 分发
设计师介入 ──┘                         ↑
  (M2 期间委托,M4 期间交付)  ──────────┘ 设计稿在 M5 落地
```

**建议**:在 M2 开始时就把 `docs/03` 交给设计师。设计周期通常 4~6 周,正好在你做完 M3/M4 时交付,M5 直接落地,不会卡住。

---

## 每周工作节奏建议

| 时段 | 内容 |
|---|---|
| 周一 | 看上周反馈/问题清单,定本周 3 个目标(不要超过 3 个) |
| 周二~周五 | 开发。每天结束时提交可运行的代码 |
| 周六 | **用自己的 App 玩 1 小时真实故事**,记录所有不顺手的地方 |
| 每个里程碑末 | 跑一遍 `docs/08` 的评测集 + 更新 `docs/09` 风险登记册 |

> "每周亲自玩一小时"这条纪律,比任何需求文档都更能告诉你下一步该做什么。
