## 1. 架构总原则

| # | 原则 | 理由 |
|---|---|---|
| 1 | **无服务端**。所有能力端上实现,网络请求只发往"用户配置的模型服务商" | 产品定位;已确认只做 BYOK |
| 2 | **叙事交给 LLM,数值交给代码** | LLM 不可靠地维护状态,这是本项目第一铁律 |
| 3 | **上下文组装是一等公民**,必须可测试、可观测、可回放 | 产品质量 90% 由它决定 |
| 4 | **Provider 无关**。业务层只认统一领域模型,不认任何厂商字段 | BYOK 要同时支持十几家 |
| 5 | **平台无关优先**。能放 `commonMain` 的绝不放平台源集 | 已决定采用 KMP,为将来 iOS 留门 |
| 6 | **数据结构先于功能**。对话树、状态快照在 MVP 就定型 | 后补迁移代价极高 |
| 7 | **一切皆可导出**。无云端 → 本地数据必须能完整带走 | 用户信任的基础 |
| 8 | 离线可用:除"生成回复"外,所有功能不依赖网络 | |

## 2. KMP 策略(本次新增的核心决策)

### 2.1 共享什么、不共享什么

```
✅ 共享(commonMain)          ❌ 不共享(各平台自己写)
──────────────────────────   ──────────────────────────
领域实体与 UseCase            UI(Android: Compose)
ContextBuilder 上下文组装      系统能力:TTS / ASR / 分享
StateMachine 状态机           文件选择器(SAF / UIDocumentPicker)
PromptEngine 模板引擎         通知
LLM Provider 适配与 SSE 解析   平台特有的安全存储实现(actual)
Repository + Room + DataStore  图片压缩的平台实现
角色卡解析(含 PNG chunk)
备份导入导出
Token 计数(接口 common,实现 expect/actual)
```

**原则**:业务逻辑 100% 共享,UI 与系统能力分平台。本项目 70%+ 的代码量在共享层,这正是 KMP 收益最大的形态。

### 2.2 UI 层策略:先 Android,预留 Compose Multiplatform

| 阶段 | UI 方案 |
|---|---|
| 现在(M1~M6) | Android 独占 Jetpack Compose,**不引入 Compose Multiplatform** |
| 将来若做 iOS | 两条路:① CMP 共享 UI ② iOS 原生 SwiftUI。届时再定 |

**为降低将来切换成本,现在就要做到:**

1. **ViewModel 放在 `commonMain`**,用 `androidx.lifecycle-viewmodel`(已支持 KMP)。
2. ViewModel 只暴露 `StateFlow<UiState>` 和 `onEvent(UiEvent)`,**不碰任何 Android 类型**(没有 `Context`、`Uri`、`Bitmap`)。
3. 平台能力一律通过 `commonMain` 中的接口调用,Android 侧提供实现。
4. UiState 中不放资源 id,放语义枚举,由 UI 层映射文案。

> 这样即使最终不做 iOS,也会得到一个额外好处:**ViewModel 可以在 JVM 上做纯单元测试**,不需要模拟器。

### 2.3 KMP 带来的代价(诚实评估)

| 代价 | 说明 | 应对 |
|---|---|---|
| M1 周期 +1~2 周 | 构建配置、源集、expect/actual 脚手架 | 已计入 `docs/04` |
| 部分库无 KMP 版 | tokenizer、加密库 | expect/actual 包装(§4.4、§4.9) |
| 构建更慢、IDE 偶发抽风 | KMP 工具链成熟度不如纯 Android | 接受;Gradle 配置缓存 + 本地构建缓存 |
| 调试链路更长 | 共享层崩溃栈在 iOS 侧可读性差(暂不涉及) | 现阶段无影响 |
| 库升级风险 | Room KMP 等较新 | §9 风险表已记录,并给出 SQLDelight 备选 |

**结论**:对本项目,共享层占比高、UI 不共享、现阶段只编译 Android 目标 —— KMP 的代价基本只是"一次性的配置成本",值得现在就付。

## 3. 技术选型

### 3.1 主栈

| 领域 | 选型 | KMP | 理由 / 备注 |
|---|---|---|---|
| 语言 | **Kotlin 2.1+** | ✅ | |
| 构建 | Gradle KTS + Version Catalog | — | `libs.versions.toml` 统一版本 |
| 目标 | `androidTarget()`,**预留** `iosX64/iosArm64/iosSimulatorArm64` | — | 现阶段只构建 Android,iOS 目标先不开(开了要维护编译通过) |

| 代码质量 | ktlint + detekt + Compose 编译器 metrics | — | |

### 3.2 明确不选的东西

| 不选 | 原因 |
|---|---|
| Hilt | 不支持 KMP。**本次由 Koin 替代** |
| OkHttp 直接使用 | 仅作为 Ktor 的 Android 引擎存在,业务代码不直接依赖 |
| Retrofit | 不支持 KMP;SSE 支持弱;动态 Base URL 场景下收益小于约束 |
| ktor-client-sse 插件 | 对"流中途需要实时吞噬 ```state 代码块"的定制需求支持不足,且各厂商流格式有出入,手写更可控(§5.2) |
| 厂商官方 SDK(openai-kotlin 等) | 锁死单一厂商,与 BYOK 冲突;协议本身很简单 |
| Compose Multiplatform(现阶段) | iOS 未定;现在引入会增加构建复杂度而无收益 |
| 端侧 LLM(MediaPipe / llama.cpp) | 手机可跑的模型质量不足以支撑长篇角色扮演,且 +300MB 包体 |
| 向量数据库 | 端上数据量小(千级),SQLite BLOB + 暴力余弦足够 |
| Firebase 全家桶 | 与"数据不出端"卖点冲突 |
| RxJava | 无必要 |

## 4. 模块划分(KMP 源集)

### 4.1 目标结构

```
Mirage/
├── shared/
│   ├── domain/              ← 纯 Kotlin,无任何平台依赖
│   │   └── commonMain/      实体、UseCase、ContextBuilder、StateMachine、PromptEngine
│   ├── llm/
│   │   ├── commonMain/      LlmProvider 抽象、SSE 引擎、OpenAI/Anthropic/Gemini 适配器
│   │   ├── androidMain/     Ktor OkHttp 引擎
│   │   └── iosMain/         (预留)Ktor Darwin 引擎
│   ├── data/
│   │   ├── commonMain/      Repository、Room 实体/DAO、DataStore、备份导入导出
│   │   ├── androidMain/     actual: SecureKeyStore / FilePaths / TokenCounter
│   │   └── iosMain/         (预留)
│   └── presentation/
│       └── commonMain/      ViewModel + UiState + UiEvent(不含任何 Android 类型)
├── androidApp/
│   ├── ui/                  Compose 页面、设计系统、Markdown 渲染
│   └── platform/            SAF、分享、TTS、通知等平台能力的实现
└── iosApp/                  (预留,暂不创建)
```

### 4.2 MVP 阶段的简化

**不要一开始就拆 4 个 shared 模块。** M1 阶段建议:

```
:shared        (单模块,内部按包分层:domain / llm / data / presentation)
:androidApp
```

等到 M3 结束、代码量上来后再拆。**提前拆模块会显著拖慢早期迭代速度**,而包级分层已足够保证边界清晰(配合 detekt 的包依赖规则)。

### 4.3 关键边界纪律

| 规则 | 检查方式 |
|---|---|
| `domain` 包不依赖 Ktor / Room / Koin | detekt 自定义规则或 ArchUnit 风格测试 |
| `presentation` 不出现 `android.*` 导入 | CI 中 grep 检查 |
| `ContextBuilder` / `StateMachine` 必须是纯函数(无 IO) | 代码评审 + 单测即可在 JVM 毫秒级跑完 |
| 平台能力只通过 commonMain 接口暴露 | 接口定义在 domain,实现在 androidApp |

## 5. 关键技术点设计

### 5.1 LLM Provider 适配层

```kotlin
// commonMain
interface LlmProvider {
    val capabilities: ProviderCapabilities
    fun chatStream(request: ChatRequest): Flow<StreamEvent>
    suspend fun listModels(): Result<List<ModelInfo>>
    suspend fun testConnection(): Result<Unit>
    suspend fun embed(texts: List<String>): Result<List<FloatArray>>  // P2
}

data class ProviderCapabilities(
    val supportsStreaming: Boolean,
    val supportsTools: Boolean,       // 决定状态机走 tool_call 还是 JSON 块降级
    val supportsSystemRole: Boolean,  // 少数模型不支持 system,需合并进 user
    val supportsPenalties: Boolean,   // 不支持时传了会 400
    val maxContextTokens: Int,
    val supportsVision: Boolean,
    // —— 以下由 docs/14 实测反推新增(E1) ——
    val supportsStreamUsage: Boolean,     // 是否支持 stream_options.include_usage
    val reasoningControl: ReasoningControl, // 如何关闭思维链(各家方言不同)
    val reportsCostUsd: Boolean,          // 是否直接返回 usage.cost(OpenRouter 有)
    val supportsProviderPinning: Boolean, // 是否可固定上游 provider(聚合商专有,评测必需)
)

/** 关闭思维链的方言。实测两家写法完全不同(docs/14 §5.4) */
sealed interface ReasoningControl {
    object None : ReasoningControl                     // 模型无思维链
    object DeepSeekThinking : ReasoningControl         // thinking: {"type":"disabled"}
    object OpenRouterReasoning : ReasoningControl      // reasoning: {"enabled": false}
}

/** 必须是枚举而非裸字符串:判定逻辑完全依赖它(docs/14 §5.3) */
enum class FinishReason {
    STOP,            // 正常完成
    LENGTH,          // 🔴 触达长度上限(实测 6 次中有 4 次!)
    TOOL_CALLS,      // 模型要调工具 —— 此时 content 为空是【预期行为】,不是错误
    CONTENT_FILTER,  // 被内容过滤 —— 不要自动重试
    ABORTED,         // 用户取消 / 断流
    UNKNOWN,         // 保留原始值到 nativeFinishReason 供诊断
}

sealed interface StreamEvent {
    data class Delta(val text: String) : StreamEvent
    data class ReasoningDelta(val text: String) : StreamEvent
    data class ToolCallDelta(val id: String, val nameChunk: String?, val argsChunk: String?) : StreamEvent
    data class Usage(
        val prompt: Int,
        val completion: Int,
        val reasoning: Int?,    // ⚠️ 仅供展示,不得用于预算计算(实测不自洽,R-T17)
        val cached: Int?,       // DeepSeek: prompt_cache_hit_tokens
        val costUsd: Double?,   // OpenRouter 直接给;其余为 null
    ) : StreamEvent
    data class Done(
        val finishReason: FinishReason,
        val nativeFinishReason: String?,  // 原始值,诊断用
        val providerName: String?,        // OpenRouter 的 provider,用于复现(R-T16)
    ) : StreamEvent
    data class Failed(val error: LlmError) : StreamEvent
}
```

#### ⭐ 5.1.1 响应归一化层(P0 必做,由 `docs/14` 实测升级)

> **原文档把归一化列为"建议",实测后升级为 P0。** 仅测 2 家就发现 4 处不兼容。

| 内部字段 | DeepSeek 来源 | OpenRouter 来源 |
|---|---|---|
| `content` | `message.content` / `delta.content`(思考阶段为 **`null`**) | 同路径(思考阶段为 **`""`**) |
| `reasoning` | **`reasoning_content`** | **`reasoning`** + `reasoning_details[].text` |
| `cachedTokens` | `prompt_cache_hit_tokens` | `prompt_tokens_details.cached_tokens` |
| `costUsd` | ❌ 无(需自维护价格表) | ✅ `usage.cost` |
| `providerName` | ❌ 无 | ✅ `provider` |

> **2026-10-16 第二轮探针补充(E1,`docs/14 §10.7`)。** 完整的 per-provider 映射表以 `docs/14 §10.7` 为准,下表是对本节的增量补充:

| 内部字段 | DeepSeek 来源 | OpenRouter 来源 |
|---|---|---|
| `cacheWriteTokens` | `prompt_cache_miss_tokens` | `prompt_tokens_details.cache_write_tokens` |
| `nativeFinishReason` | ❌ 无 | ✅ `choices[].native_finish_reason`(上游原始值) |
| `requestId`(诊断用) | ✅ `error.message` 内嵌 `request_id` | ✅ 顶层 `id`(`gen-…`) |
| `upstreamFingerprint` | `system_fingerprint` | `provider` |
| `contextWindow`(来自 `/models`) | `context_window`(实测 1 048 576) | `context_length` / `top_provider.context_length` |
| `maxOutputTokens`(来自 `/models`) | `max_output_tokens`(实测 393 216) | `top_provider.max_completion_tokens` |
| `supportedParams`(能力探测) | `effort.supported_levels` / `api_capabilities` | `supported_parameters[]`(含 `"tools"`) |
| `pricing`(发送前估价) | ❌ 无 | `pricing.prompt` / `pricing.completion` |

**🔴 思考开关必须建模为三态而非布尔(E1,第二轮实测推翻了原假设):**

| 语义 | DeepSeek | OpenRouter |
|---|---|---|
| 开 | `"thinking":{"type":"enabled"}` | `"reasoning":{"enabled":true}` |
| 关 | `"thinking":{"type":"disabled"}` | `"reasoning":{"enabled":false}` |
| **强度档位** | `effort`:`low`/`high`/`max`,**默认 `high`** | `reasoning.effort`(待测,E3) |

→ `ReasoningControl` 不能是 `Boolean`,至少是 `sealed class { Off; On(effort: Effort?) }`。

**🔴 错误体必须宽松解析(E1):** 同名字段 `error.code` 在 DeepSeek 是**字符串**(`"invalid_request_error"`),
在 OpenRouter 是**数字**(`401`)。强类型 `@Serializable data class` 会直接抛反序列化异常,
**把一个本可友好提示的 401 变成 `Unknown`**。做法:`error` 整体收成 `JsonElement`,逐字段 try 取值;
用户文案一律按 **HTTP 状态码**映射(OR 的 401 原文是 `"User not found."`,抛给用户毫无意义)。

**两条实现纪律(踩过的坑):**

1. **`content` 的 `null` 与 `""` 必须在适配器里统一**(建议都归一成 `null`)。
   若用 `content != null` 判断"开始回答",OpenRouter 上会在模型刚开始思考时就误判,**UI 显示"正在回复"然后空卡几十秒**。
   判据只能是 **`content` 非空字符串**。
2. `reasoning` **绝不可混入叙事正文,也绝不可写进对话历史回传给模型**。只做可折叠的独立展示。
3. **脱敏必须覆盖错误响应体。** DeepSeek 的 401 文案会**回显 Key 尾号**(`Your api key: ****0000`),
   日志/诊断包里的 `redact()` 不能只处理请求头。

#### ⭐ 5.1.1b SSE 解析契约(E1,第二轮实测定稿)

| # | 规则 | 证据 |
|---|---|---|
| S1 | **`data: [DONE]` 两家都有**,`V-9` 已关闭。原先"不得假设其存在"的警告**作废** | DS 148 条 data + `[DONE]`;OR 86 条 + `[DONE]` |
| S2 | 🔴 **以 `[DONE]` 收尾,不得以 `finish_reason` 收尾。** OR 发**两条** `finish_reason:"stop"` 的 chunk,`usage`/`cost` 只在**第二条** | OR `finish_reason` 计数 `{null:83, stop:2}`,带 `usage` 的只有最后一条 |
| S3 | 🔴 **必须跳过 `:` 开头的注释/心跳行。** OR 发 `: OPENROUTER PROCESSING`(实测 4 行,约每 420ms 一条),DeepSeek **一条都没有** | 真实服务商差异,非边界情况 |
| S4 | `data:` 与载荷之间**有一个空格**,每条 data 后跟一个空行 → 先 `trim` 再比较 `[DONE]` | 原始流形态 |
| S5 | 🔴 **`FIRST_TOKEN` 超时阈值 ≥ 30s,且必须是绝对时长而非"空闲时长"。** 实测 OR 首 token 12 570ms,**前 11 091ms 零字节**(连心跳都没有) | `03_stream_raw.txt` 毫秒戳 |

| S7 | 每条消息**持久化 `provider` 与 `native_finish_reason`** | `R-T16` provider 漂移,见 §5.1.2b |
| **S8** 🔴 | **S2 在 tools 场景同样成立,而且更危险。** 第三轮实测 OR 发**两条** `finish_reason:"tool_calls"`(DS 只发一条)→ 在第一个非空 `finish_reason` 处 `break` 会同时丢掉 `usage` **和可能的后半截 `arguments`** | `docs/14 §12.2` C16 |
| **S9** | **注释行差异在 tools 场景复现**:OR 7 行 `: OPENROUTER PROCESSING`,DS 0 行 → S3 不是边界情况 | `docs/14 §12.2` |

#### ⭐ 5.1.1c 流式 `tool_calls` 归集契约(E1,第三轮实测定稿)

> **实测结论:`stream:true` + `tools` 两家都可用,且叙事正文与工具调用在同一个 SSE 流里共存**
> (OR:74 片正文 + 12 片工具;DS:53 片正文 + 43 片工具)。
> **但 `arguments` 一定是被切碎的,分片数在 12~43 之间波动。** 见 `docs/14 §12.2`。

| # | 规则 | 为什么(实测依据) |
|---|---|---|
| T1 | **按 `tool_call.index` 归集。** 维护 `Map<Int, PartialToolCall>`,不要用数组下标或出现顺序 | 多工具并发时 `index` 是唯一归属依据;本轮实测 `index=[0]` |
| T2 | 🔴 **`function.name` 只在第一个分片出现**,后续分片只有 `arguments` → 首次见到就记住,不要每片都读(会读到 null 覆盖掉) | 两家的「工具名出现次数」都是 **1** |
| T3 | 🔴 **`arguments` 必须把所有分片的字符串原样拼接后再解析。绝不能假设任何固定片数,也不能对中间态尝试解析** | OR 12 片 / DS 43 片,同一 schema 差 3.6 倍 |
| T4 | 🔴 **只有收到 `[DONE]` 之后才允许 `JSON.parse`**,解析失败走降级(见 §5.6 路径 B),不要重试 | 中间态必然是非法 JSON |
| T5 | **判成败看 `finish_reason == tool_calls`,不看 `content` 是否为空** | 既有硬约束,tools 场景再次确认 |
| T6 | **允许模型自己加字段。** DS 实测自发输出了 schema 外的 `flags:{"石门已推开":true}` → 反序列化必须 `ignoreUnknownKeys = true`,且**未知字段要落日志不要静默丢** | `docs/14 §12.2` |
| T7 | ⭐ **产品解锁:正文边流式打字、状态在 `[DONE]` 瞬间原子更新。** 不需要等整轮结束再放叙事 | 两种 delta 在同一流里共存 |

**伪代码(归一化层的最小正确实现):**

```kotlin
class ToolCallAccumulator {
    private val parts = mutableMapOf<Int, Part>()           // T1
    private data class Part(var name: String? = null, val args: StringBuilder = StringBuilder())

    fun onDelta(index: Int, name: String?, argsChunk: String?) {
        val p = parts.getOrPut(index) { Part() }
        if (p.name == null && name != null) p.name = name   // T2:只认第一次
        if (argsChunk != null) p.args.append(argsChunk)      // T3:原样拼接
    }

    /** 只允许在收到 [DONE] 之后调用(T4) */
    fun finish(): List<Result<ToolCall>> = parts.entries.sortedBy { it.key }.map { (_, p) ->
        runCatching { ToolCall(p.name!!, json.parseToJsonElement(p.args.toString())) }
    }
}
```

#### ⭐ 5.1.2 reasoning 预算治理(P0,`R-T15`)

> **实测:`max_tokens: 1024` 下 6 次请求 4 次 `finish_reason=length`,其中一次 `content` 为 `null`——
> 1447 个 token 全花在思考上,用户一个字没看到,但全额计费。**

| 规则 | 做法 |
|---|---|
| R1 | **角色扮演场景默认关闭 reasoning**(按 `ReasoningControl` 方言下发)。叙事不需要 CoT |
| R2 | **`max_tokens` 默认不下发**,用平台默认上限 |
| R3 | 用户若手动设置,**下限强制 2048**,UI 文案必须写明"此额度包含模型思考消耗" |
| R4 | `FinishReason.LENGTH` **必须显式提示**,不得静默。并按"是否收到过 content"区分两种文案:<br>· 收到过 → "回复被长度限制截断" + **「继续生成」**<br>· 没收到过 → "模型思考占满了长度上限" + **「调高上限 / 关闭思考」** |
| R5 | 实现 **Continue**:把已生成 content 作为 assistant 前缀再请一次(SillyTavern 有此按钮,E2) |
| **R6** 🔴 | **必须显式下发关思考参数,"不传"是最贵的选项 —— 且这对*所有*服务商成立,不只是 OpenRouter。**

角色扮演有大量「嗯」「好的」这类短回合,这条的实际代价比看起来大。

#### ⭐ 5.1.2b provider 漂移治理(P0,`R-T16`,E1 第二轮升级)

> **实测:同一次 60 秒探针运行内,同一个 model id `z-ai/glm-5.1`,5 个请求命中 4 个不同上游**
> (StreamLake / GMICloud / Venice / StreamLake / StreamLake)。**这不是偶发,是每次请求都在抽签。**

| 规则 | 做法 |
|---|---|
| P1 | **聚合商(OpenRouter 类)的单次响应不能作为能力结论。** 任何"该模型支持 X 吗"的判断必须锁 provider 且重复 ≥3 次 |
| P2 | 🔴 **这改变了 `V-12`(`stream`+`tools`)的测法** —— 不同 provider 对 `tools` 支持度不同,碰巧测中支持的会得出错误的乐观结论。V-12 必须在 DeepSeek(单一上游)上测,并在 OR 上锁 provider 复测 |
| P3 | ✅ **已实测生效(第三轮,3/3 命中)**:`"provider": {"order": ["Phala"], "allow_fallbacks": false}`。`V-17` 关闭 → 评测可复现,`V-12`/Step 4 解除阻塞 |
| P4 | **运行时能力兜底不可省。** 即使 `/models` 的 `supported_parameters` 声明支持 `tools`(那是聚合商的**聚合**声明),实际命中的 provider 仍可能不支持 → 必须有"工具调用失败 → 降级到纯文本协议"的路径 |
| P5 | **把漂移变成功能:每条消息展示/记录 `provider` + `native_finish_reason`。** 用户抱怨"今天它变傻了"时这是唯一能自证的证据。竞品(ChatterUI / SillyTavern)都没做 |
| **P6** 🔴 | **`allow_fallbacks:false` 不做 App 默认值 —— 它的代价是尾延迟。** 实测锁定组 3 次里有 1 次 **59.7s**(另两次 3.6/3.8s,不锁时 2.6~4.6s):目标上游忙时请求只能排队而不能换人。**默认允许 fallback,但记录实际 provider**;锁定只暴露在「评测 / 复现问题」的高级开关里。见 ADR-009 |
| **P7** | **上游池比想象的大。** 两轮合计见到 ≥6 个不同上游(StreamLake / GMICloud / Venice / Phala / Nebius / Friendli),**两轮之间零重叠** → 任何「我见过它用 X」的经验都不可依赖,`R-T16` 严重性上调 |

### 5.2 SSE 流式引擎(Ktor 实现)

```kotlin
// commonMain
fun HttpClient.sseLines(block: HttpRequestBuilder.() -> Unit): Flow<String> = flow {
    prepareRequest(block).execute { response ->
        val channel = response.bodyAsChannel()
        while (!channel.isClosedForRead) {
            val line = channel.readUTF8Line() ?: break
            if (line.isNotBlank() && !line.startsWith(":")) emit(line)
        }
    }
}
```

**为什么手写而不用 `ktor-client-sse` 插件:**

1. 需要在流中途 **实时检测并吞噬** ```` ```state ```` 代码块(§5.6),要求对字节流有完全控制。
2. 部分服务商返回的不是严格 SSE(无 `event:` 字段、心跳格式各异、HTTP 200 却返回错误 JSON)。
3. 需要精细的分阶段超时(连接 / 首 token / 流间隔)。

**实现要点:**

| # | 要点 | 说明 |
|---|---|---|
| 1 | **超时配置** | `requestTimeoutMillis = Long.MAX_VALUE`(或 `HttpTimeout` 不设 request 超时),仅设 `connectTimeout = 15s`。流式期间两个 chunk 间隔可能很长 —— **这是最常见的坑** |
| 2 | **首 token 超时单独计时** | 用 `withTimeoutOrNull` 包住"第一个 Delta 到达"的等待(60s),与整体超时区分 |
| 3 | **取消即关连接** | Ktor 的 `execute {}` 在协程取消时会关闭连接;需写测试验证,否则用户会被持续计费 |
| 4 | **UI 背压** | token 到达极快时不要每个都触发重组。`Channel` 聚合 + 每 ~50ms 刷新一次,或 `conflate()` |
| 5 | **增量落盘** | 每 N 个 chunk 或每 500ms 把部分内容写库,保证进程被杀不丢已生成内容 |
| 6 | **重试策略** | 仅 `Network` / `Timeout(CONNECT)` / `429` 自动重试(指数退避,≤2 次),且 **仅在尚未产生任何 token 时**;已产生内容一律交给用户决定 |
| 7 | **跨 chunk 边界** | 标记可能被切分,缓冲最后 12 个字符用于跨 chunk 匹配 |

### 5.3 上下文组装(ContextBuilder)—— 系统的心脏

#### 组装管线

```
Input: SessionId + 用户新消息
 ↓
[1] 加载:全局预设 / 角色卡 / 人格卡 / 权威状态 / 记忆条目 / 世界书 / 对话树当前路径
 ↓
[2] 世界书命中:扫描最近 N 轮 + 本轮输入 → 关键词匹配(+ P2 语义匹配)
 ↓
[3] 渲染各 Block(PromptEngine 占位符替换)
 ↓
[4] 计算 token,执行预算分配
 ↓
[5] 裁剪:固定块保留;历史块从最旧丢弃,丢弃内容进"待压缩队列"
 ↓
[6] 周期性注入:每 N 轮追加一次"人设复述"块
 ↓
[7] 输出 ChatRequest + ContextTrace(调试快照)
```

#### Block 模型

每个块有:`id`、`role`、`content`、`priority`(裁剪优先级)、`pinned`、`position`(拼装顺序)。
预设即"块的有序列表 + 各块模板",这让 G-2/G-5 的"用户可编辑 Prompt"自然成立。

#### Token 预算(以 32K 上下文为例)

| 块 | 预算 | 可裁剪 |
|---|---|---|
| 全局行文规范 | 800 | 否 |
| 角色卡(persona + 风格 + 示例对话) | 3000 | 示例对话可按条裁剪 |
| 用户人格卡 | 300 | 否 |
| **权威状态快照** | 600 | 否(游戏模式下绝不能丢) |
| 记忆摘要条目 | 1500 | 低重要度条目可裁 |
| 世界书命中条目 | 1500 | 按匹配分数裁 |
| **近期对话历史** | 剩余全部(~20K) | **是,主要裁剪区** |
| 预留输出 max_tokens | 2000~4000 | — |
| 安全余量 | 5% | — |

> **顺带的省钱收益**:固定块放前面、变化块放后面,可命中部分服务商的 **Prompt Caching** 折扣(Claude / DeepSeek 等)。

**实现要求:`ContextBuilder` 必须是纯函数**(输入全部显式传入,无 IO),可在 JVM 上写几十个单测覆盖边界:超长角色卡、空历史、状态缺失、世界书爆炸等。

#### ContextTrace(可观测性,对应 J-2)

每次组装产出一份 trace:各块内容、token 数、是否被裁剪、世界书命中原因、最终 messages 数组。调试面板直接渲染它,并支持"复制为 curl"。**这个功能会在开发期省掉至少一半调试时间,务必 M1 就做。**

### 5.5 记忆系统

```
消息被预算挤出窗口
   ↓ 进入待压缩队列
达到阈值(如累计 2000 token)
   ↓ 后台独立 LLM 调用(可配置使用更便宜的通道)
   ↓ Prompt:"压缩成不超过 150 字的第三人称事实摘要,保留人名/地点/承诺/情感变化"
   ↓ 生成 MemoryEntry(内容, 覆盖的消息区间, 重要度, 可编辑)
   ↓ 入库,下轮注入
```

- 压缩 **异步、不阻塞用户**;失败降级为"直接丢弃最旧历史"+ 轻提示。
- 压缩花用户的钱 → 设置里可关闭,并显示预估成本。
- **记忆条目必须可编辑**(D-4)。AI 摘要出错会污染后续所有回合。
- 语义检索(P2):embedding 存 `FloatArray` → `ByteArray` BLOB;端上暴力余弦,千级条目 < 10ms。

### 5.6 游戏状态机与双通道协议

#### 路径 A:原生 Tool Calling

请求带 `tools: [update_state]`,schema 由角色卡的状态定义 **动态生成**。

#### 路径 B:降级协议(模型不支持 tools)

System Prompt 末尾要求:

````text
在你的回复最后,如果本回合有状态变化,追加一个代码块:
```state
{"hp_delta": -12, "items_gained": ["钥匙"]}
```
没有变化则不要输出该块。
````

客户端流式渲染时 **实时检测并隐藏** 该代码块(不展示给用户),流结束后解析。
容错:JSON 不合法 → 尝试修复(补括号 / 去尾逗号 / 提取最外层 `{}`)→ 仍失败则忽略并记调试日志,**绝不中断叙事**。

#### 状态机

```kotlin
// commonMain,纯函数,易测
fun reduce(current: GameState, delta: StateDelta, rules: StateRules): ReduceResult
```

- **校验与钳制**:`hp` 超 `[min,max]` 则 clamp;物品不在白名单则丢弃;flag 必须在声明集合内。
- **违规记录**:记入 trace,调试面板可见 —— 这是优化 Prompt 的直接依据。
- **幂等**:"重新生成"时必须回滚该消息产生的 delta → **每条消息都存它产生的 delta**。
- **事件溯源**:`GameState = fold(initialState, 当前路径上所有 delta)`。天然支持分支与回档,见 ADR-003。

### 5.7 对话树

见 `docs/06` 表结构。核心:

- `Message(id, sessionId, parentId, role, content, createdAt, meta)`,**无 position 字段**。

- 渲染时把当前路径物化成 `List<Message>` 给 Paging。

### 5.8 Prompt 模板引擎

轻量占位符替换即可,**不引入 Mustache/Freemarker 这类重型库**(且它们多半没有 KMP 版):

```
{{char}} {{user}} {{persona}} {{scenario}} {{state}} {{memories}} {{lore}} {{date}} {{time}}
{{random: a, b, c}}                随机选一个,增加变化
{{#if state.hp < 30}}...{{/if}}    条件块(P2,先不做)
```

模板存于 `composeResources` / `shared` 资源的 `presets/*.json`,用户修改后存 DB 覆盖。每个预设带 `schemaVersion` 与 `promptVersion`,升级时迁移而非覆盖用户修改。

### 5.9 API Key 安全存储(expect/actual)

```kotlin
// commonMain
interface SecureKeyStore {
    suspend fun put(id: String, plaintext: String)
    suspend fun get(id: String): String?
    suspend fun remove(id: String)
}
// androidMain: Android Keystore 主密钥(StrongBox 优先)+ Tink AEAD → 密文存 Room
// iosMain(预留): Keychain Services
```

**铁律(详见 `docs/07` §1):**

1. Key **绝不写日志**;日志层统一脱敏过滤器(正则 `sk-[A-Za-z0-9_\-]{8,}` → `sk-***`)。
2. 崩溃日志(若用户主动上报)必须经同一脱敏层,并剥离所有请求体。
3. 备份导出 **默认不含 Key**;用户显式勾选时用其密码额外加密。
4. `android:allowBackup="false"`,主密钥材料放 `no_backup/`。
5. 调试面板展示请求体时,Authorization 显示为 `Bearer sk-****abcd`。

### 5.10 流式 UI 渲染性能

| 问题 | 方案 |
|---|---|
| 每个 token 触发全列表重组 | 流式中的最后一条消息用 **独立 `State<String>`**,与列表数据源解耦;流结束才写回列表 |
| Markdown 每帧全量重解析 | 增量解析:只重解析"最后一个未闭合块";或节流到 ~50ms |
| 长列表卡顿 | Paging 3 + 稳定 key + `contentType` |
| 自动滚动与手动滚动打架 | 用户上滑后暂停自动吸底,显示"回到底部"按钮 |
| 打字机动画 | 不要逐字延时动画(与真实流速打架),直接渲染已到达文本 + 光标闪烁 |

### 5.11 离线与数据可携带性

- 所有读路径完全本地,飞行模式下除生成外全可用。
- 备份格式:**zip**,含 `manifest.json` + 结构化 JSON + `media/`。
  **用结构化 JSON 而非直接拷贝 sqlite 文件**,跨版本恢复更可控(详见 `docs/06` §5)。
- 导出流式写入(okio),避免大会话 OOM。

### 5.12 无服务端下的可观测性

没有后端 = 没有日志平台。替代方案:

1. **环形缓冲日志**:内存保留最近 500 条,崩溃时落盘;设置页可"导出诊断包"(已脱敏)。
2. **请求记录表**:最近 100 次请求的 URL(脱敏)、模型、耗时、token、错误码。
3. 崩溃捕获:`Thread.setDefaultUncaughtExceptionHandler` 本地落盘 + 下次启动询问是否上报(**默认不上报**)。
4. 可选匿名统计必须 **opt-in**,且明确列出采集字段。

| 风险 | 对策 |

## 8. 架构决策记录(ADR)

> 规则:决策变更不要改写旧条目,追加新条目并标注"取代 ADR-00X"。

### ADR-001 · 不做服务端,只做 BYOK
- **状态**:✅ 已确认(2026-10-15,用户决策)
- **决策**:不建任何自有后端;**不提供官方 API Key 方案**,用户必须自带。
- **理由**:规避生成式 AI 备案与内容责任;零推理成本;"数据不出端"是对目标用户的核心卖点。
- **代价**:无云同步、无远程配置、无服务端数据分析、首次使用门槛高。
- **缓解**:强备份导出(H-1/H-2)、WebDAV(P2)、强力首次引导(A-10)。

### ADR-002 · 用 Ktor Client,不用 Retrofit/裸 OkHttp
- **状态**:✅ 生效(v2.0 修订,取代原 "裸 OkHttp" 决策)
- **理由**:KMP 要求跨平台 HTTP 客户端;Ktor 支持 Android(OkHttp 引擎)与 iOS(Darwin 引擎)。
- **代价**:Ktor 的流式与超时语义需单独验证,与 OkHttp 经验不完全互通。

### ADR-003 · 状态采用事件溯源(delta 累加)而非可变快照
- **理由**:天然支持对话树分支、回档、重新生成的回滚。
- **代价**:读取当前状态需 fold;长会话需定期落检查点快照加速。

### ADR-004 · 消息存储为树(parentId)而非线性列表
- **理由**:多候选 swipe、分支、回档都依赖它;后补迁移代价极高。
- **代价**:查询与渲染略复杂,需物化当前路径。

### ADR-005 · 不集成端侧模型
- **理由**:质量不足 + 包体与内存代价过大。
- **复议条件**:当 3B 级模型在角色扮演评测集上达到可用水准时重新评估。

### ADR-006 · 采用 Kotlin Multiplatform,UI 暂不共享
- **状态**:✅ 已确认(2026-10-15,用户决策:"iOS 还没想好,可以先用 KMP")
- **决策**:业务逻辑(domain / llm / data / presentation)放 `commonMain`;UI 与系统能力分平台;**现阶段只构建 Android 目标**,iOS 目标先不开启。
- **理由**:将来做 iOS 时可省数月;即使不做 iOS,也获得"ViewModel 可 JVM 单测"的收益。
- **代价**:M1 周期 +1~2 周;DI 由 Hilt 换 Koin;tokenizer/加密需 expect/actual。
- **纪律**:`presentation` 中出现任何 `android.*` 导入即视为违规(CI 检查)。

### ADR-007 · 数据库选 Room KMP,SQLDelight 为备选
- **状态**:✅ 生效,**M1 末设验证关卡**
- **决策**:优先 Room 2.7+ 的 KMP 支持(你有 Android 经验,学习成本最低)。
- **验证关卡**:M1 结束前必须验证 ① 迁移 ② FTS 全文搜索 ③ 树形递归查询性能。任一不过关则切换 SQLDelight。
- **代价**:Room KMP 相对较新,文档与社区案例少于纯 Android 场景。

### ADR-008 · DI 由 Hilt 改为 Koin
- **状态**:✅ 生效(ADR-006 的直接后果)
- **理由**:Hilt 不支持 KMP。
- **代价**:失去编译期校验(Koin 是运行时解析)→ 补偿措施:CI 中跑 `checkModules()` 验证依赖图完整性。

### ADR-009 · `allow_fallbacks:false` 只用于评测,不做 App 默认值
- **状态**:✅ 生效(2026-10-16,第三轮实测)
- **背景**:`R-T16` provider 漂移让任何单次测试结论都不可信(本条风险编号 `R-T24`),第三轮验证了 OpenRouter 的
  `provider:{order:[X], allow_fallbacks:false}` **能可靠锁定上游(3/3)**。
  很自然的下一步想法是「那 App 里也锁上,保证体验一致」。
- **决策**:**不锁。** App 默认允许 fallback,但**必须记录并可展示实际命中的 provider**。
  锁定能力只做成「评测 / 复现问题」场景下的高级开关,默认关闭。
- **理由(实测代价,E1)**:锁定组 3 次请求里有 1 次耗时 **59.7s**,另两次 3.6s / 3.8s;
  同一 prompt 不锁时为 2.6~4.6s。`allow_fallbacks:false` 时目标上游繁忙,请求只能排队。
  **对聊天类 App,59 秒的尾延迟比「偶尔换个上游」严重得多** —— 后者用户大多感知不到,
  前者会让用户直接判定应用卡死并重试(= 双倍计费,见 §5.1.1b S6)。
- **代价**:放弃了「体验绝对一致」。用 P5(记录 provider)来补偿可观测性。
- **取代**:无(新增)。与 ADR-002 无冲突。

### ADR-010 · 状态生成走「方案 C:后台独立结算」,解析侧兼容「方案 A:正文内标签」
- **状态**:✅ 生效(2026-10-18),⏳ 等 `V-12` 实测复核(`tools/m0_dualchannel.py`)
- **背景**:状态数值怎么产生,有三条路:
  **A** 让模型在正文里吐 `<initvar>`/```state``` 标签;**B** 原生 Tool Calling;
  **C** 正文与结算**分成两次完全独立的请求**,叙事只写字,结算只吐 JSON。
- **决策**:**生成走 C。解析认 A(只解析,不生成)。B 降级为可选/评测用。**
- **理由**:
  1. **E1 双来源互证**:`dsh-tavern` 与真 SillyTavern 的导出材料都显示,它们的变量更新
     **由后台独立结算产出,前台正文零数值**(`docs/15 §3.1` 的 `mvu-background-owner` 禁令是直接证据)。
     这不是我们的发明,是行业标杆的实际做法。
  2. **A 必须兼容但不能用来生成**:生态里的卡(包括用户给的 `DiLaoJSON.json`)把
     `<initvar>{...}</initvar>` 直接写在 `first_mes` 里。**导入时必须解析得了**,
     否则一张真实的卡就跑不起来。但**我们自己绝不生成它** —— 否则等于给模型做了一次
     "你该在正文里写状态块"的 few-shot 示范,正文纯净度立刻崩。
  3. **B 不可依赖**:很多国内/中转通道阉割 `tools`(`docs/14`,E1)。
     虽然第二轮实测确认 `stream`+`tools` 可同流共存,但这是**在 OpenRouter 上**的结论,
     不能推广到用户随便填的一个 Base URL。
  4. **铁律 2 的直接落地**:叙事交给 LLM,数值交给代码。C 是唯一能把两者物理隔开的方案。
- **代价**:**每轮两次调用。** 用 `docs/05 §4.0` 的参数策略把代价压住 ——
  叙事调用**不设 `max_tokens`**(E1 硬约束 1:它是思考+正文共用预算,设小了会只出思考不出正文),
  结算调用 `max_tokens=512` + 关思考 + `temperature=0.2` + 可指定廉价模型。
  结算调用的 prompt 不含完整对话历史(只有规则+快照+本轮输入+本轮正文),
  所以**会话越长,结算的相对成本越低**。实测数字由 `m0_dualchannel.py` 的 D4 给出。
- **风险**:C 在 `docs/05 §4.4` 曾被我自己标成 **E3(无竞品证据,我们自己设计的实现细节)** ——
  行业做法是 C 这一点是 E1,但**结算请求长什么样**没有竞品证据。
  这是 `V-12` 要关的最后一道闸门。
- **取代**:无(新增)。

### ADR-011 · 状态面板走原生 Compose 渲染,**不执行角色卡里的 JavaScript**
- **状态**:✅ 生效(2026-10-18),理由已按 `V-24` 实测修正
- **背景**:SillyTavern 的状态面板是**角色卡自带的一段 HTML + JavaScript**。
  也就是说在那个生态里,**面板 UI 属于内容,不属于 App** —— 导入一张卡就等于导入了一个前端程序。
- **决策**:**v1 只做原生渲染(`docs/15 §7.6` 选项①),为「③ 混合」留接口,明确不做「② 每条消息一个 WebView」。**
- **理由(4 条中 3 条成立,第 2 条已部分自我证伪,见下)**:
  1. ✅ **安全硬红线。** 角色卡是从互联网下载的**不可信内容**,其中的 `<script>` 可以发网络请求,
     而我们 App 里存着**用户的 API Key**(铁律 4)。这个风险不能拿来换兼容性。
  2. ◐ **WebView 与 LazyColumn 的回收机制冲突**(每条消息一个实例)—— 前半句成立。
     🔴 但我原本还写了"ChatterUI 状态管理弱很可能也是因为绕不过这一点",
     **这句已被 `V-24` 实测证伪:ChatterUI 根本没做世界书、也没做状态/MVU,是功能缺失而非性能权衡。**
     已在 `docs/15 §7.6` 原处标注、不删除。
  3. ✅ **差异化恰在此处。** 原生才能做悬浮吸顶、数值飘字(+12/−8)、横滑切换多角色、
     与系统主题联动、点数值看历史曲线。**HTML 面板是 PC 时代的产物;移动端的正确答案是原生。**
     这一条被 DZMM 侧面支持:它的聊天窗口悬浮状态面板、每轮自动更新,正是原生实现的形态(E1,用户实测)。
  4. ✅ **兼容性守在数据层,不在表现层。** 我们与 SillyTavern 共享的是 `stat_data` + JSON Pointer
     (三份材料互证),不是 HTML。变量读得对,画成什么样是我们的自由。
- **代价**:导入他人角色卡时,卡自带的精美面板**不会被渲染**,改用我们的通用面板。
- **缓解**:① 检测到 `<mvu-status/>` 或 HTML 块时,在导入页明确提示
  "该卡自带状态面板,将以 Mirage 原生样式呈现";② 提供 `A-19` 面板模板编辑器
  (从 `stat_data` 选字段 → 选控件:进度条/数字/标签/圆点);
  ③ **解析层必须剥离并记录卡内的 `<script>`**(`R-T29`),剥离结果对用户可见。
- **补充(`V-24` 的副产品)**:移动端原生渲染状态面板,**目前全行业没有先例**
  —— SillyTavern 是 PC+WebView,ChatterUI 没做,DZMM 闭源。
  所以这不是"跟随竞品",而是**我们第一个做**。既是机会,也意味着没人替我们踩过坑。
- **取代**:无(新增)。

## 🆕 调试面板规格(E1,直接抄自 `完整上下文` 页签,`docs/15 §7.10.4`)

原先 §4「trace」只写了"调试面板直接渲染它"。现在有了 E1 的具体规格,**按这个做**:

| 元素 | 规格 | 备注 |
|---|---|---|
| 定位四件套 | `第 N 轮 · 步骤 M` + 模型名 + 时间戳 + `刷新` | 竞品原文如 `第 20 轮 · 步骤 1  deepseek-flash  2026/10/10 13:31:38` |
| 搜索 | `搜索提示词、消息或工具…` | 长 Prompt 必须能搜 |
| 导出 | **`复制 JSON` 与 `下载 JSON` 两个独立按钮** | 手机上复制更常用,不要只给下载 |
| ⭐ **分段折叠 + 每段字符数** | 按 `调用参数` / `messages[i] · role` / `tools · 工具定义` 分段,**每段右侧标字符数** | **这是精髓**。BYOK 用户最常问「我的 token 都花哪了」,这个设计直接回答 |
| 展开内容 | 原样 JSON,等宽字体,浅底色块 | 与 `docs/03` 的等宽 13sp 一致 |
| 调用参数可见 | `maxTokens` / `reasoningEffort` 等**作为可见参数展示** | 印证 E1-①:`max_tokens` 是「思考+正文」共享预算,必须对用户可见可调 |

> 📌 竞品把这个页签**放在主界面顶部**(`对话`/`轨迹`/`完整上下文`),不是藏在设置里。
> → **结论:Prompt 透明化不是极客玩具,是这个品类的既有做法。**

## 🆕 工具链版本锁（2026-10-19 第 11 轮 · Sync 事故后定）

### 事故

首次 Gradle Sync 失败：

```
Could not resolve all dependencies for configuration ':androidApp:debugRuntimeClasspathCopy'.
Cannot select root node 'debugRuntimeClasspathCopy' as a variant.
```

**根因不是构建脚本写错，而是骨架里漏了 Gradle Wrapper。**
仓库没有 wrapper → Android Studio 从本地缓存里自己挑了 `gradle-9.0-milestone-1`（预览版）
→ Gradle 9 新增「一个 configuration 不能同时当解析根和变体」的强校验
→ AGP 8.7.3 给 IDE 提供同步模型时正好违反它 → 报上面这个看起来完全不相干的错。

> 📌 教训（已写进 `AGENTS.md`）：**构建工具版本不许交给 IDE 决定。**
> 手写 Gradle 骨架必须显式 pin wrapper，不能指望 IDE 补齐。

### 版本矩阵（改任何一格都要重算整行）

| 组件 | 锁定版本 | 约束 | 约束来源 |
|---|---|---|---|
| Gradle | **8.9** | 下面三条的唯一交集 | `gradle/wrapper/gradle-wrapper.properties` |
| AGP | 8.7.3 | 要求 Gradle ≥ 8.9，不支持 9.x | AGP 官方兼容矩阵 |
| Kotlin | 2.1.0 | 支持 Gradle 7.6.3 ~ 8.10，不支持 9.x | Kotlin 官方兼容矩阵 |
| KSP | 2.1.0-1.0.29 | 前缀必须 == kotlin 版本，错一位即插件不兼容 | KSP 发布规则 |
| JDK | 17（AS 自带 JBR 21 亦可） | Gradle 8.9 支持 17 ~ 21 | Gradle 兼容矩阵 |

> 交集 = `[8.9, 8.10]`，取下界 **8.9**（AGP 8.7.3 的官方搭配版本，踩坑概率最低）。
> 分发包用 `-all`（带源码/文档，IDE 里能点进 Gradle DSL 看注释）。

### 升级流程（唯一许可方式）

1. 查官方兼容矩阵，重算四者交集；
2. **同一次提交**里一起改 wrapper + `agp` + `kotlin` + `ksp`；
3. 双验证：`./gradlew :shared:jvmTest` 和 `./gradlew :androidApp:assembleDebug`。

对 Android Studio 的「有新版 Gradle/AGP，是否升级？」弹窗**一律点否**。

### 顺带关掉的两项（降低首次调通的变量数）

| 项 | 处置 | 理由 |
|---|---|---|
| `org.gradle.configuration-cache` | **M1 先关** | 不兼容时报错会变成一长串序列化异常，把真正的问题盖住。M1 稳定后单独开一次验证 |
| `kotlin.mpp.enableCInteropCommonization` | **删除** | 只对 native（iOS）target 有意义，当前只有 `jvm()` + `androidTarget()`，留着只多一条警告。开 iOS 时再加回（`Q11`） |
