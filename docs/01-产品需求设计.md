## 第一部分 · 产品定义

### 1.1 产品定位

Mirage 是一个 **纯客户端的 AI 互动叙事引擎**。它不是"AI 聊天工具",而是 **一个随身的文字冒险游戏主持人(GM)**。

三类核心玩法:

| 玩法 | 描述 | 典型场景 |
|---|---|---|
| **角色扮演(Roleplay)** | 用户与一个有稳定人设的 NPC 持续对话,NPC 不出戏、有记忆、有情感变化 | 和"侦探搭档"聊案情、和历史人物对谈 |
| **情景模拟(Simulation)** | 用户进入设定好的场景练习某种处境,AI 扮演环境中的所有角色 | 面试模拟、谈判演练、语言陪练、医患沟通训练 |
| **游戏代入(Interactive Fiction)** | 有明确数值与规则的文字冒险:HP、物品、好感度、时间推进、结局分支 | 地牢探险、校园恋爱模拟、生存推理 |

这三类共用同一套引擎,差异仅在 **角色卡 / 世界观 / 规则配置** 上。这是核心架构洞察:**不要为三种玩法写三套代码**。

### 1.2 机会判断

1. 主流 AI 角色扮演产品是"重服务端 + 自付费 + 强审核"模式,不可避免地做内容阉割与人设弱化。
2. 高级用户(从 SillyTavern 等桌面生态来)诉求明确:**我要自己的 Key、自己的 Prompt、自己的数据**,但桌面方案在手机上体验极差。
3. **BYOK 纯客户端** 正好填这个空位:零推理成本、数据不出端、功能上限由用户的 Key 决定而不是由我们的审核策略决定。
4. **(v1.3 收窄)** 原判断为"现有 BYOK 手机 App 只做聊天"。竞品研究(`docs/11`)证伪了这个过宽的说法:**ChatterUI 已经做出了可用的原生移动端 BYOK 客户端**。
   准确的空位是:**原生移动端 + 完整叙事引擎 + 数值算得准的状态机,三者同时具备者,目前为零**。
   - 酒馆系:引擎最强,移动端不可用,且状态靠 hack(让模型自己算数,会漂移)
   - ChatterUI:移动端可用,但无游戏化状态机
   - DZMM 等托管平台:有状态面板(MVU 形态)与优秀视觉,但审查 + 数据不在用户手里 + 引擎封闭
   - **→ 我们的差异化必须锋利地压在"状态与数值的正确性"上,而不是泛泛的"手机上的酒馆"**

### 1.3 目标用户

| 画像 | 特征 | 核心诉求 | 优先级 |
|---|---|---|---|
| **A. 硬核玩家** | 已在用 SillyTavern / 已有 API Key / 会调 Prompt | 手机端的完整替代品、角色卡兼容、Prompt 完全可控 | **P0(首发目标)** |
| **B. 轻度叙事爱好者** | 玩过 AI Dungeon / 读过互动小说,但没 Key | 开箱即用的故事、低配置成本 | P1(需提供 Key 获取引导) |
| **C. 工具型用户** | 用 AI 做面试/口语/销售演练 | 可复用的"情景模板"、可回看评分 | P2(第二阶段) |

**首发只服务 A。** A 群体口碑能带来早期增长,且他们容忍"要自己填 Key"这个门槛。不要在 MVP 阶段为 B 妥协架构。

#### 🆕 关于 A 群体的一个重要修正(`docs/14 §5.1`,E1)

开发者本人在实测时发现:**所在地区被 OpenRouter 明确声明不支持,也不便测试 Claude / GPT。**
这是一条真实的、此前没写进画像的约束,并且**早期用户极可能与之同构**。

| 推论 | 对需求的影响 |
|---|---|
| 首发用户的主力模型是 **DeepSeek / GLM / Qwen 这一档**,而不是 Claude / GPT | ⭐ **我们的 Prompt 与协议设计必须以这一档的能力为基线。**尤其是 `R-T14`:这档模型的 Function Calling 可靠性明显弱于 Claude,**这提高了 `E-10`(JSON 代码块)成为主方案的概率** |
| 用户会大量使用**中转/代理服务**,base_url 五花八门 | `A-1` 的 Base URL 必须**完全自由填写**,不做任何白名单或格式强校验 |
| 中转服务常阉割 `stream` 与 `tools` | `A-15`(Key 握手自检)的价值上升:要能**探测出**用户这个通道到底支持什么,而不是假设 |

### 1.4 非目标(明确不做)

- 不做自建服务端、不做账号登录、不做云同步(第一年内)
- 不转售 token、不做余额充值
- 不做模型训练 / 微调 / 端侧模型推理(端侧小模型质量不足以支撑长篇角色扮演)
- 不做多人联机叙事
- 不做图片生成(第一阶段;后续可考虑接 BYOK 的绘图 API)
- 不做"内置免费 Key"(会立刻变成成本黑洞与合规责任主体)

### 1.5 两条不可妥协的工程铁律

> 这两条不是技术细节,而是**产品级约束**。它们决定了用户能否获得"稳定的人设"与"后悔权"这两项核心价值。
> 任何需求、任何排期压力,都不得以牺牲这两条为代价。实现细节见 `docs/02` ADR-003 / ADR-004 与 `docs/06`。

**铁律一 · 叙事交给 LLM,数值交给代码。**

LLM 只负责产出两样东西:**故事文本** + **结构化的状态增量(delta)**。它**永不持有**权威数值。
所有 HP / 物品 / 好感度 / flag / 时间的真值由**客户端状态机**持有,每轮全量注入上下文;
模型给出的 delta 必须先经状态机**校验**(越界、非法、违反规则)再落库,校验失败则静默钳制并记日志,不打断叙事。

- **理由**:模型会算错数,也会被用户话术说服("你刚才说我有 3 把钥匙")。把数值交给模型 = 游戏规则可被聊天绕过。
- **对应需求**:`E-1~E-5`(状态系统)、`§2.1` 推论 4、`§2.3` 权威状态层、`§4.3` 双通道示例。
- **违反的后果**:数值漂移、存档不可信、游戏化玩法直接失效。

**铁律二 · 消息存成树,状态存成事件流 —— 两者必须 MVP 一次做对。**

| | 正确做法 | 错误做法 | 为什么不能后补 |
|---|---|---|---|
| 消息 | 每条消息带 `parentId`,构成**树** | 线性 `List<Message>` | 重 roll / 分支 / 回档全依赖它;后期迁移需改写全部历史数据与渲染层 |
| 游戏状态 | **事件溯源**:只追加 delta 事件,当前状态由 fold 求得 | 维护一份可变的"当前状态"快照并原地修改 | 回档时无法还原历史状态;分支之间状态会互相污染 |

- **理由**:"后悔权"(回档、换个说法重开)是叙事类产品的核心体验,而它在数据结构层面只有这一种正确解法。
- **对应需求**:`F-1`(P0,对话树)、`F-4`(回档)、`C-4`(重新生成/多候选)。
- **违反的后果**:这是全项目**唯一无法靠重构低成本挽回**的设计。其余模块(记忆、UI、Prompt)都可以推翻重写,这两处不行。
- **MVP 取舍说明**:游戏化状态系统(E)整体不在 MVP,但**状态事件表与 delta 协议的结构必须在 MVP 阶段就定稿并写入库**,哪怕暂时只有空实现。

### 1.6 对标定位(v1.3 新增)

> **初期战略:不追求原创形态,先对齐行业标杆并补足其短板。** 人力有限,差异化与产品特性后续再开拓。

| 对标对象 | 学什么 | 落到哪些需求 |
|---|---|---|
| **SillyTavern** | **行业标准与引擎深度**:角色卡格式、预设体系、世界书、正则后处理、Author's Note 深度注入、以及它对大模型叙事的约束手法 | `B-3/B-4`(格式互通)、`B-5`+`D-5`(世界书)、`G-1~G-6`(预设与正则)、`D-7`(深度注入)、`docs/05` 全文 |
| **ChatterUI** | **移动端的能力实现**:原生 Android 上如何把 BYOK 对话、流式渲染、角色卡管理做得顺手 | `C-1~C-12`、`docs/02` 性能设计、`docs/08` 性能基线 |
| **DZMM** | **状态面板形态(MVU)**:聊天窗口内的悬浮角色状态,每轮对话自动更新;以及优秀的界面与立绘呈现 | `E-5`/`E-5a` 状态 HUD、`I-1` 视觉、`docs/03` UI |

**三条明确的边界:**

1. **角色卡市场不做**(无服务端做不了 UGC;改为把"导入"做到行业最好,寄生现有生态)。
2. **立绘不做重资产**(不自产美术,改为把角色卡自带的图用到极致,见 `I-1`)。
3. **本地模型不做**(见 `§1.4`)。

**关于 MVU 的一处关键纠偏(我们相对它的技术优势):**

酒馆社区与 DZMM 一类的状态面板方案,本质上仍是 **让 LLM 自己做算术**(模型直接输出"HP=88"之类的赋值)。这违反 `§1.5 铁律一`,长会话必然漂移,也无法追溯。
我们的做法是:**LLM 只表达变更意图(delta),算术与校验由客户端状态机完成**(`E-2`/`E-3`)。
由此获得一个 MVU 做不到的能力 —— **状态变更可追溯**(点开 HP 能看到"第 12 轮 −12,原因:触发陷阱"),这是事件溯源(`ADR-003`)的免费副产品,且是用户一眼可感知的质量差异。

## 第二部分 · AI 概念说明(团队共识基线)

> 本节是需求的一部分,因为下面所有功能需求都建立在这些概念上。新手请先读 `docs/10-AI术语速查表.md`。

### 2.1 大模型 API 的本质:无状态的文本补全

```
请求 = [系统指令] + [完整对话历史]  →  响应 = [下一段文本]
```

**关键推论(决定了整个产品架构):**

1. **模型没有记忆。** 每一轮我们都必须把"它该记得的东西"重新发一遍。所谓"AI 记住了我",全部是客户端的上下文组装工程。
2. **上下文有长度上限(Context Window)。** 以 token 计。超过就必须丢弃或压缩历史 → 这就是"失忆"的来源,也是 **记忆系统** 存在的理由。
3. **成本与延迟正比于 token 数。** 用户的钱是自己付的,但我们有义务不浪费 → **Token 预算管理是 P0**。
4. **模型会算错数、会被话术欺骗。** 不能让它维护数值状态 → **状态机必须在客户端**。

### 2.2 决定"人设稳不稳"的四件事

| 要素 | 作用 | 产品侧体现 |
|---|---|---|
| **System Prompt** | 定义身份、行文规范、禁止行为 | 角色卡 `persona` + 全局"行文规范"预设 |
| **Few-shot 示例对话** | 给模型看"你该怎么说话",对风格的影响远大于形容词描述 | 角色卡 `example_dialogues`(**强制必填**) |
| **采样参数** | temperature 高 → 有创意但易崩;低 → 稳定但枯燥 | 设置页暴露 + "稳定/平衡/狂放"三档预设 |
| **上下文新鲜度** | 距离当前最近的内容权重最高,长对话中早期设定会被冲淡 | 需要周期性"人设复述注入" |

### 2.3 记忆的四个层次(本项目的记忆模型)

```
短期记忆:最近 K 轮原文对话 ──────── 滑动窗口,直接入上下文
中期记忆:历史对话的 LLM 摘要 ────── 被挤出窗口时自动压缩为"记忆条目"
长期记忆:世界书 / 设定条目 ──────── 关键词或语义触发,按需注入
权威状态:HP/物品/好感度/flag ────── 由客户端状态机持有,每轮全量注入
```

**"权威状态"与"叙事文本"分离**是本项目最重要的设计原则。
这是 `§1.5` **铁律一** 在记忆模型上的体现。

### 2.4 工具调用(Function Calling)= 让 AI 操作游戏

模型可被要求以结构化 JSON 输出"我想做什么",而不只是说话:

```
AI 的一次回复 = 叙事文本(给用户看) + update_state 调用(给程序看)
```

程序 **校验并执行** 这个状态变更(可以拒绝不合法的变更),再把新状态在下一轮注入。数值永远自洽,AI 只负责讲故事。

### 2.5 流式输出(Streaming / SSE)

模型逐 token 返回。角色扮演必须流式,否则用户要盯着空屏等 10~30 秒。需要:SSE 解析、打字机渲染、随时中断、断流重试。

### 2.6 内容审核的来源

无服务端 ≠ 无审核。审核发生在 **上游模型供应商**:

- 用户 Key 指向的服务商有自己的 policy,触发时返回错误或空内容。
- 我们的责任是 **优雅提示**("当前服务商拒绝了这段内容,可尝试换模型或调整描述"),而不是报一个裸 HTTP 400。
- 我们自身可提供端上的 **内容分级与未成年人保护**(已降级为 P2,见 `docs/07` §4)。

## 第三部分 · 功能需求

优先级:**P0** = MVP 必须有;**P1** = 首个正式版本必须有;**P2** = 迭代增强;**P3** = 远期。

### 3.1 模块总览

```
Mirage
├── A. 模型连接(BYOK)          ← 产品的前置闸门
├── B. 角色卡与世界观
├── C. 对话引擎(核心)

```

### A. 模型连接(BYOK)

| ID | 需求 | 优先级 | 说明 / 验收要点 |
|---|---|---|---|
| A-1 | 添加"模型通道":名称 / Base URL / API Key / Model ID | **P0** | 多通道并存、随时切换 |
| A-2 | OpenAI 兼容协议支持 | **P0** | 覆盖 DeepSeek、Kimi、GLM、OpenRouter、硅基流动、Ollama、LM Studio |

## 第四部分 · 核心用户旅程

### 4.1 首次启动(最关键的流失点)

```
启动
 → 价值说明(3 屏:它能干什么 / 为什么要你的 Key / 数据只在你手机上)
 → 二选一:
    ├─ 「我已有 Key」→ 选服务商模板 → 贴 Key → 测试连接 ✅ → 角色列表
    └─ 「我没有 Key」→ 分步图文引导(推荐 1~2 个注册简单、有免费额度的服务商)
                      → 可"先逛逛":浏览内置角色 + 看一段预录示例对话(不消耗 Key)
 → 选一个内置角色 → 设置你的人格名 → 开始第一段故事
```

**设计原则:在用户填 Key 之前,就让他看到产品的价值。**

### 4.2 一次完整对话回合(系统视角)

```
用户输入
 ↓
① 组装上下文:全局预设 + 角色卡 + 人格卡 + 权威状态 + 记忆摘要 + 命中的世界书 + 近 K 轮 + 本轮输入
 ↓
② Token 预算检查 → 超限则裁剪 / 触发压缩
 ↓
③ 发起流式请求(带 tools 定义)
 ↓
④ 边收边渲染叙事文本;并行收集 tool_call
 ↓
⑤ 流结束 → 解析状态增量 → 状态机校验 → 落库 → 更新 HUD(带动画)
 ↓
⑥ 存消息(含 parent_id、token 用量、所用模型快照)
 ↓
⑦ 判定结局条件 / 是否触发记忆压缩
```

### 4.3 游戏化回合示例(说明双通道)

> **用户**:我推开那扇门。
>
> **AI 叙事**:门轴发出刺耳的尖叫。腐臭的空气扑面而来,黑暗里有什么东西动了一下——一支弩箭擦过你的肩膀,血顺着手臂滴落。角落的石台上,放着一把锈迹斑斑的钥匙。
>
> **AI 工具调用(用户不可见)**:
> ```json
> {"hp_delta": -12, "items_gained": ["锈蚀的钥匙"], "flags_set": ["entered_crypt"], "location": "墓室入口"}
> ```
>
> **客户端**:HP 88 → 76(飘字动画);物品栏 +1;HUD 地点更新;下一轮注入 `HP: 76/100`。

## 第五部分 · MVP 边界

**MVP(M1~M2)只包含以下 P0:**

> A-1,2,3,7,9,10 · B-1,2,3,4,6,9 · C-1~6,9,10,11 · D-1,2 · **E-5a** · F-1,6 · G-1,7 · H-1,2 · **I-1** · J-1,2,6

即:**能用自己的 Key,导入(并导出)角色卡,进行稳定、可编辑、可重开的流式角色扮演,看得见一个会自动更新的状态面板,数据可备份。**

> **v1.3 对 MVP 的两项扩容(有意为之):**
> - **`E-5a` 最小只读 HUD 进 MVP** —— 这是唯一"一眼可见"的差异化。没有它,MVP 就是一个功能更少的 ChatterUI,无法验证产品价值。它的实现成本不高(协议与事件表本就要在 MVP 建好),高的是**不做它的机会成本**。
> - **`I-1` 零成本视觉方案进 MVP** —— 纯 UI 工作,无美术依赖,但决定第一印象。

游戏化状态系统(E)**不在 MVP**。但受 `§1.5` 铁律二约束,以下三项**必须在 MVP 阶段定稿**,否则后续重构代价巨大:

1. **F-1 对话树**(`parentId`)—— 真实实现,不是预留。
2. **状态事件表 + delta 协议结构**(`docs/06`)—— 建表并打通写入路径,业务逻辑可为空实现。
3. **`docs/05` 的双通道输出协议**(叙事文本 / 结构化 delta 分离)—— 协议定稿,解析器可只做校验不做消费。

## 第六部分 · 衡量成功的指标

| 指标 | 目标 | 测量方式 |
|---|---|---|
| Key 配置完成率 | > 60% | 本地埋点(用户同意匿名统计时)/ 社区反馈 |
| 首次会话达到 10 轮以上比例 | > 50% | 同上 |
| 平均单会话轮数 | > 30 | 本地可自查 |

> **用户拍板原文**:「卖点 1+2 没问题,为什么把 3 成本透明忽略了呢,
> 我认为这一点虽然不是我们的第一卖点,但是我们也要做。」
>
> ✅ **已采纳,并更正我的表述失误。** 我上一轮写「③ 不做主卖点」,
> 本意是**不作为对外第一宣传口径**,但措辞让它看起来像「不做」——
> 这是我表达不清,不是取舍。**三支柱全部要做,区别只在「谁上广告语」。**

| 支柱 | 定位 | 对外口径 | 需求落点 | 优先级 |
|---|---|---|---|---|
| **① 引擎完整度 × 移动端原生** | **主卖点(获客)** | ✅ **上广告语** —— 一句话能讲清,用户一眼能看懂 | `B-1a`/`B-1b`/`B-10`、世界书/预设/正则/楼层树全集 | **P0** |
| **② 确定性结算** | **技术护城河(留存)** | 🟡 **不上广告语,上功能页** —— 「数值不会乱」讲不清,但用两周能感觉到 | `ADR-012` G1~G8、`B-13`/`B-14`、`E-3a`/`E-3b` | **P0** |
| **③ 成本透明** | **信任与留存(BYOK 刚需)** | 🟡 **不上广告语,但进首次引导** —— 「你的 Key、你的钱、你看得见」是**打消 BYOK 疑虑**的关键一句 | `A-11`(升 P0)、`J-7`~`J-11` | **P0 / P1 混合** |

### 为什么 ③ 不上广告语,但必须做

| 理由 | 依据 |
|---|---|
| **它是 BYOK 模式的内在义务,不是加分项** | 我们要用户自己掏 API 钱(`R-P1` 已标为最大流失风险)。**不告诉他花了多少,等于让他闭着眼付费** |
| **竞品的真实状态给了我们空间** | DZMM 自带 API **完全不透明**(用户实测);DSH Tavern 有事后计量(`556K tok · 缓存…`,E1)但**没有发送前估价** |
| **但它容易被抄** | 一个计量条 + 一次估算,竞品一个版本就能补上 → **所以它撑不起"第一卖点",只能做信任底座** |
| **它和 ② 共享基础设施** | `J-9` 分段归因与 `J-2` 调试面板是同一块代码;`J-10` 双模型通道直接复用 `ADR-010` 的双通道架构 → **边际成本很低** |

> ⭐ **一条额外收益**:`J-10`(叙事/结算分别选模型)把**成本透明**和**确定性结算**连了起来 ——
> D3 实测「结算换 `deepseek-chat`:断言 91% > 85%,成本 1/3」意味着
> **省钱和算得准在这里不矛盾,是同一个选择**。这是三支柱里最漂亮的一处咬合。
