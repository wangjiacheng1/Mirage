## 1. 实测:完整上下文装配顺序(28 条消息)

这是第 8 轮(`trace.turn: 8`)时真实发出的 `messages` 骨架:

```
 #  role       content blocks      source.form              内容
--- --------- ------------------- ------------------------ ----------------------------------
 0  system    text                @deepseek-ai/dsh-…       【故事设定 · 人物卡】+【变量目录】
 1  user      text                synthetic-trajectory     "我们正在共同创作一部…沉浸式虚构小说"
 2  assistant reasoning+text      synthetic-trajectory     "明白。后续我会把人物卡…只输出小说正文"
 3  user      text                synthetic-trajectory     "开始。请从人物卡给定的开场继续。"
 4  assistant reasoning+text      character-card           开场白正文 + <initvar>{…}</initvar>
--- 以下每轮循环(轮 = 1 组) -------------------------------------------------------
 5  user      text                (kind:user)              玩家原话:"我选简单"
 6  user      text                worldbook-snapshot       【本轮世界书上下文】(条件命中,可缺省)
 7  assistant reasoning+text      deepseek-flash           正文(零数值)
 8  user      text                (kind:user)              玩家原话
 9  user      text                worldbook-snapshot       【本轮世界书上下文】
10  user      text                variable-changes         【上一轮变量变化】只列 delta
11  assistant reasoning+text      deepseek-flash           正文
…   (轮 16/19 那两组没有 worldbook-snapshot → 证明是条件注入)
--- 最后一条 --------------------------------------------------------------------
27  user      text                foreground-frame         ⭐ 写作规范 + 现场姿态 + 附加要求 + MVU 禁令
```

### 1.1 🔴 最反直觉的一条:**系统指令放在队尾,不是 system 位**

`messages[27]`(**最后一条,role=user**)才是真正的"系统指令",它由 4 个 section 拼成:

| section name | `sectionKind` | `stage` | 内容 |
|---|---|---|---|
| `tavern:foreground:writingRules:1` | `base` | `context-plan` | 4 条行文规范(只输出正文 / 演出指引语义 / 不得照抄指引 / 每轮要有剧情意义) |
| `tavern:foreground:currentStateProjection:2` | `posture` | `context-plan` | ⭐【现场 · 主要人物状态】自然语言姿态快照 |
| `tavern:foreground:writingRules:3` | `card-instruction` | `context-plan` | 【附加要求】角色卡自带的本场玩法要求 |
| (无名) | — | **`mvu-background-owner`** | ⭐ MVU 禁令(见 §3.1) |

而 `messages[0]` 的 system 位**只放角色卡 + 变量目录**。

**为什么这么干(我的解读):**
1. **近因效应** —— 长上下文里,`system` 位的约束会被后面几万 token 的正文稀释;放队尾则紧贴生成位置,最难被忽略。
2. **前缀缓存** —— system 位放"整局不变"的角色卡,正好是最长的稳定前缀(`docs/14 §2.2` 的 `prompt_cache_hit_tokens`)。把每轮都在变的行文规范/现场姿态塞进 system 会**让整段缓存失效**。
3. 这**同时满足**我们在 `docs/05 §1` 已经推导出的两个目标 —— 我们的推导方向是对的,但**位置拍错了**:我们把"人设复述"放在 `messages[n-1]` 的 system,它把**全部可变指令**放在 `messages[n]` 的 user。

→ 🔴 **`docs/05 §1` 的装配表必须按本条重写。**

### 2.1 F8 展开:我们漏掉了一整类状态

实测原文(`sectionKind: "posture"`):

```text
【现场 · 主要人物状态(每轮结算更新,务必与之一致)】
奥斯维德立于石阶下方半步处,黑手套双手重新交叠在身前,乌黑头发与深红近黑的
礼服马甲一丝不乱,视线落在那扇门上;玩家站在门前,腰间旧皮水壶塞子缠布,尚未推门。
```

这**不是数值**,是一段**自然语言的物理/姿态快照**。它解决的是一个我们没有识别出来的真实问题:

> 长对话里,LLM 会忘记"角色现在站在哪、手里拿着什么、衣服是否已经脱了/脏了",
> 下一轮就会写出"他站起身"——可他本来就站着。

**数值状态机管不了这个**(你不会给"手套是否交叠"建一个 int 字段),但它恰恰是**沉浸感最容易崩的地方**。

→ 🔴 **这是一个产品级补充,进 `docs/01` 作为新功能点,并进 `docs/13`。**
→ 实现上它和数值状态**同源**:都由后台结算 Agent 在每轮产出(数值出 delta,姿态出一段 ≤100 字的文本),一起存进事件流。

## 3. MVU 协议实证

### 3.1 🔴 核心证据:前台被明文禁止输出变量

`messages[27]` 最后一个 section(`stage: "mvu-background-owner"`)原文:

```text
变量更新由正文提交后的后台 Agent 独立结算。只输出剧情正文,
不要输出 <UpdateVariable>、JSON Patch 或变量更新说明。
```

同一条约束在人物卡(`messages[0]`)里也出现了一次:

```text
6. 数值由 MVU 后台结算,正文不输出状态块,也不写数值表格。
```

**这句禁令同时给了我们三个信息:**

1. ✅ **E1:`dsh-tavern` 的 MVU 走「正文提交 → 后台 Agent 独立结算」** —— 即我们原先的"方案 B"的升级版,**独立的第二次调用**。
2. ❌ ~~**E2:`<UpdateVariable>` 标签确实是酒馆生态的既有协议** —— 否则不必专门禁它。这是 SillyTavern MVU 的写法。~~
   🔴 **此条已于 §7.0 被证伪。** 真 SillyTavern 用工具 `mvu_submit_update`。
   **教训:从"禁用语"反推"对方在用什么"不可靠** —— 禁用语列的是所有可能的错误写法。此类反推以后一律标 E3。
3. ✅ **E1:同时点名禁了 `JSON Patch`** → 说明"正文里混 JSON Patch"也是一种见得到的野路子。

### 3.2 ✅ 用户的怀疑是对的,并且比怀疑更确定

> 用户原话:"SillyTavern 的状态栏更新方案我怀疑并没有在上下文中,因为它是在正文输出后又去异步更新的,这是我的怀疑"

**确认:怀疑成立,且不是"没抓到",而是"结构上就不在这里"。**
这份 JSON 是**前台(foreground)**帧(`frameId` 以 `foreground:` 开头),后台结算是**另一条链路、另一次请求**,导出按钮拿不到。

但我们**不必**像用户建议的那样"先不采用这个方案" —— 恰恰相反,**正因为一线厂商选了它,我们应该采用它**。缺的只是"后台那一次请求的 prompt 长什么样",而那个我们可以自己设计(见 §4.3),不需要抄。

### 3.3 三个变量协议的实测对照

| | 方案 A · 正文内标签 | 方案 B · 原生 Tool Calling | 方案 C · 后台独立结算 |
|---|---|---|---|
| 形态 | `<UpdateVariable>{…}</UpdateVariable>` 跟在正文后 | 同一次请求,`tool_calls` 与正文同流 | 正文完成后,**第二次请求**只产出 delta |
| 证据 | ~~E2~~ → **E3**(§7.0 已证伪,无竞品在用) | **E1**(`docs/14 §11`:两家都支持) + **E1**(真 ST 的结算器就用工具提交,§7.1) | **E1 ×2 互证**(`dsh-tavern` + 真 SillyTavern,§7.1) |
| 流式正文纯净 | ❌ 需要"吞噬模式"状态机,标记会跨 chunk 切分 | ⚠️ 较好(工具片在独立字段) | ✅ **完美**,正文零污染 |
| 模型兼容性 | ✅ 任何模型 | ❌ 需支持 tools(实测 394/465 = 85%,`docs/14 §11`) | ✅ 任何模型 |
| 成本 | 1 次请求 | 1 次请求 | **2 次请求**(但第二次可用便宜模型 + 短上下文) |
| 失败隔离 | ❌ JSON 坏了可能连正文一起崩 | ⚠️ 中 | ✅ **完全隔离**,结算失败不影响已显示的正文 |
| 结算可重试 | ❌ 要重跑整轮叙事(贵) | ❌ 同左 | ✅ **只重跑结算**(便宜) |
| `max_tokens` 可控 | ❌ 与正文共用预算(`docs/14 §4`) | ❌ 同左 | ✅ **结算输出结构化,可安全设 512** |
| 竞态 | 无 | 无 | ❌ **有**:状态栏可能短暂落后于正文 |

## 4. 🔴 决策:Mirage 的状态协议定稿

### 4.1 决策

> **主方案 = C(后台独立结算)。B(Tool Calling)作为 C 内部的实现细节可选。A 只做「解析兼容」,不做生成。**

写成一句话:**我们生成时永远走 C;解析时必须认得 A。**

### 4.2 理由与代价

| 理由 | 证据 |
|---|---|
| 一线厂商在自家模型上选了 C,并明文禁掉 A | **E1** §3.1 |
| C 让流式正文零污染 —— A 的"吞噬模式"是个必然出 bug 的状态机(标记跨 chunk、模型漏闭合标签) | E1 + `docs/05 §4.2` 原设计已预见要缓冲 12 字符 |
| C 把 `max_tokens` 的两难**解开了**:叙事调用不设上限(避免 `finish_reason=length` 截断),结算调用设 512 + 关思考(结构化输出,安全) | **E1** `docs/14 §4` + `AGENTS §5.1` |
| C 让结算可独立重试,而重试叙事要花 3~20 秒 + 全额 token | **E1** `docs/14 §12`(首 token 最长 12.57s) |
| C 对 85% 以下的小众/旧模型也成立(不要求 tools) | **E1** `docs/14 §11`(15% 模型不支持 tools) |

**必须接受的三个代价(写进设计,不许假装没有):**

1. 🔴 **每轮 2 次 API 调用。** 缓解:结算调用用**便宜模型 + 短上下文**(只需"上一轮状态 + 本轮正文 + 规则",不需要全部历史)。用户可在设置里为"结算"单独指定一个廉价模型 —— 这正好是 BYOK 的优势,竞品做不到(ChatterUI 单模型,DZMM 不给选)。
2. 🔴 **状态栏存在竞态。** 必须抄 `F10`:结算三态 `pending / running / done`,UI 上状态栏显示"结算中…"而**不是**显示旧值假装是新值。这与 `docs/02 §5.1.1b S6` 的进度三态是同一类设计。
3. 🔴 **结算调用也会被"中断不省钱"命中**(`docs/14 §13`):用户退出页面不代表结算不计费。→ 结算调用**必须**设 `max_tokens`(512),这是全项目唯一可以安全设上限的调用。

### 4.3 结算调用的设计(我们自己设计,不抄)

```
结算请求(第二次调用)
├─ system: 【结算规则】+【变量目录(路径+类型+约束)】   ← 稳定前缀,可缓存
├─ user:   【当前权威状态】(全量,来自客户端状态机,不是模型自述)
├─ user:   【本轮玩家输入】
├─ user:   【本轮正文】(刚刚生成的)
└─ user:   【输出要求】只输出一个 JSON:{"delta":{…}, "posture":"…", "reason":"…"}
参数: max_tokens=512 · 关思考 · temperature 低(0.2) · 可指定廉价模型
```

输出落到 `docs/05 §4.3` 已有的校验规则上(clamp / UNKNOWN_FLAG / DELTA_TOO_LARGE 等)—— **那张表不用改,它正好是 C 的消费端。**

### 4.4 A 的兼容范围(只读不写)

解析器必须能从正文里**识别并剥离**以下三种,用于导入酒馆生态角色卡与历史存档:

| 标签 | 来源 | 处理 |
|---|---|---|
| `<initvar>{…}</initvar>` | **E1** `messages[4]` | 解析为初始状态,`$meta.strictSet` 映射为"禁止新建未声明路径" |
| `<UpdateVariable>{…}</UpdateVariable>` | ~~E2~~ → **E3**(§7.0 已证伪) | 仍保留解析(成本极低,或有旧版 MVU 存档),但**不得作为「兼容 SillyTavern」的对外口径** |
| ```` ```state {…} ``` ```` | 我们自己 `docs/05 §4.2` 的原设计 | 保留解析,不再作为生成格式 |

**一律只解析、只剥离,不作为我们的生成协议。**

### 4.5 变量路径与命名

实测 `dsh-tavern` 用**中文 JSON Pointer**:`/地牢/难度`、`/冒险者/生命上限`,回灌时写成 `路径 = JSON字面量`:

```text
【上一轮变量变化】上一轮结算后发生变化的变量及最新值(路径相对于 stat_data),其余变量未变。写本轮正文时以此为准。
/地牢/难度 = "简单"
/地牢/总轮数 = 8
/地牢/当前轮 = 1
/地牢/本轮房间 = "小怪群"
/敌人/名称 = "湿皮盲兽 ×3"
/敌人/生命 = 30
```

✅ **抄:用 JSON Pointer 作为变量寻址**,允许中文键(对中文模型更友好,且用户写卡时不用翻译)。
✅ **抄:回灌用 `path = value` 行格式**,比嵌套 JSON 省 token 且更难让模型读错层级。
⚠️ 注意 `stat_data` 是它的根命名空间,我们需要自己定一个(建议沿用 `stat_data` 以便将来互通)。

## 7.2 结算规则的写法(值得整段抄的模板)

逐字段写,每条都绑定"什么事件触发 + 取值范围 + 计算式":

```text
- 地牢.当前轮：每完成一个房间 +1；开局为 0，选定难度进入第一轮改为 1。
- 地牢.是否最终轮：当前轮 = 总轮数 时为 true。
- 冒险者.生命：受击、中毒、流血、喝水、泉水、升级时增减，范围 0 到 生命上限；归 0 即死亡，本局结束。
- 冒险者.生命上限：升级 +8，属性提升房 +10。
- 水壶.当前/上限/每口恢复：喝水 −1，泉水补满；升级后重算 每口恢复 = floor(生命上限 × 0.2)。
- 资源.金币：掉落、强化扣费、材料抵价时增减，不得为负。
```

⭐ **注意最后两条**:数组元素用 `"铁片 ×3"` 这种**字符串内嵌数量**,并要求模型"合并同项"。
这其实是个**坏设计**(把结构化数据塞进字符串,解析和校验都难)。
→ **我们不抄这条**:物品栏用 `[{"name":"铁片","count":3}]`,合并由**客户端**做,不交给模型(铁律 2)。

## 7.3 ⭐⭐⭐ 状态面板的真实机制:一对"镜像正则"

这是本批材料**最有价值、也最出乎意料**的发现。

卡里有 2 条正则脚本,**`findRegex` 几乎相同,但开关完全相反**:

| 脚本 | `findRegex` | `markdownOnly` | `promptOnly` | `placement` | 替换为 |
|---|---|---|---|---|---|
| `dsh-mvu-status-view`<br>「MVU 状态视图 · 剧场报幕单」 | `/<mvu-status\s*\/>/g` | **`true`** | `false` | `[2]`(AI 输出) | **7225 字节的完整 HTML 文档** |
| `dsh-mvu-hide-marker`<br>「隐藏模型历史中的状态入口」 | `/\n*<mvu-status\s*\/>/g` | `false` | **`true`** | `[2]` | **空字符串** |

**机制解读:**

```
模型/开场白输出的正文里只有一个 7 字节占位符：  <mvu-status/>
                    │
    ┌───────────────┴───────────────┐
    │                               │
 markdownOnly=true              promptOnly=true
 (只在 UI 渲染管线生效)          (只在送进 Prompt 时生效)
    │                               │
    ▼                               ▼
 膨胀成 7KB 的 HTML 状态面板      替换为空 ——
 (含 CSS + <script> 实时渲染)     模型永远看不到这个标记
```

**这个设计解决了三个问题,一个都不多余:**

1. **正文零污染** —— 存进历史的只有 7 个字节。
2. **上下文零开销** —— `promptOnly` 那条把它抹掉,不占 token,也不会让模型误以为"我上轮输出过一个 HTML"而去模仿。
3. **UI 任意富** —— 面板可以做到血条/经验条/敌人条/水壶圆点/物品标签,还带一句随机台词。

→ ✅ **这是我们必须抄的核心机制**:**正文里只留语义占位符,渲染与回灌走两条独立管线。**
→ 对应到我们的架构:存储层存占位符;**渲染管线**把它换成状态卡片 Composable;**上下文装配管线**把它直接删掉。

## 7.6 🔴 由此产生的**重大架构抉择**:状态面板怎么渲染

这是本批材料逼出来的一个**必须拍板的决策**,之前没有意识到。

**事实:SillyTavern 的状态面板是角色卡自带的一段 HTML + JavaScript。**
也就是说:**面板 UI 属于内容,不属于 App。** 导入一张卡,就导入了一个前端程序。

| 选项 | 做法 | 优 | 劣 |
|---|---|---|---|
| **① 原生渲染** | 解析变量 → Compose 画状态卡片 | 性能好、移动端手感、可做悬浮/吸顶(DZMM 形态) | **无法运行卡自带的 HTML 面板**,导入卡的面板会丢失 |
| **② WebView** | 每条带 `<mvu-status/>` 的消息塞一个 WebView | 100% 兼容生态 | 🔴 每条消息一个 WebView = 移动端性能灾难;🔴 **角色卡里的 JS = 任意代码执行**(撞铁律 4);与 LazyColumn 滚动冲突 |
| **③ 混合** | 自有卡走①;导入卡检测到 HTML 面板时,提供**可选**的受限 WebView(默认关闭、沙箱、禁网) | 两头兼顾 | 工作量最大 |

### 🔴 我的建议(PM 视角):**v1 走 ①,为 ③ 留接口,明确不做 ②**

**理由:**

1. **安全是硬红线。** 角色卡是从互联网下载的 **不可信内容**,里面的 `<script>` 能发网络请求。若用 WebView 执行,等于给陌生人的 JS 一个运行环境 —— 而我们 App 里存着**用户的 API Key**(铁律 4)。这个风险不能换兼容性。
2. **移动端性能。** 一条消息一个 WebView,滚动 50 条就是 50 个 WebView 实例,与 LazyColumn 的回收机制直接冲突。
   > 🔴 **本条原文的后半句已被证伪,我自己写错了,记在这里不删。**
   > 原文曾写:"ChatterUI 之所以在移动端『状态管理弱』,很可能正是因为它也绕不过这一点。"
   > 2026-10-18 用户实测(`V-24`,见 §7.8)的真实答案是:**ChatterUI 根本没做世界书,也根本没做状态/MVU** ——
   > 这是**功能缺失**,不是**性能权衡**。我把"别人没做"错误地解读成了"别人做了但做不好",
   > 这是典型的 E3 臆断(教训与 §7.0 同类)。
   > 本条只保留前半句(WebView 与 LazyColumn 的冲突),它独立成立,与 ChatterUI 无关。
3. **我们的差异化恰好在这里。** 我们已定位"补足 ChatterUI 在状态/数值管理上的缺陷"。原生渲染让我们能做到**卡片自带 HTML 做不到的事**:悬浮吸顶、数值变化动画(+12/−8 飘字)、横滑切换多角色状态、与系统主题联动、点击数值看历史曲线。
   > **HTML 面板是 PC 时代的产物;移动端的正确答案是原生。** 这是我们对 SillyTavern 的一次真实超越,不是妥协。
4. **数据是标准的,UI 不必标准。** 我们和 SillyTavern 共享的是 **`stat_data` + JSON Pointer**(三份材料互证),不是 HTML。只要变量读得对,画成什么样是我们的自由 —— **兼容性在数据层,不在表现层。**

**代价(要诚实告诉用户):** 导入他人角色卡时,卡自带的精美面板**不会被渲染**,我们用自己的通用面板替代。
**缓解:** 检测到 `<mvu-status/>` 或 HTML 块时,在卡的导入页明确提示:"该卡自带状态面板,将以 Mirage 原生样式呈现",并允许用户**从 `stat_data` 字段映射到我们的面板模板**(选字段 + 选控件:进度条/数字/标签/圆点)。

→ 新增 **`ADR-011`**(`docs/02`)、**`A-19`**(面板模板编辑器,P1)。`V-24` 已于 2026-10-18 关闭,见 §7.8。

### 7.10.5 ⭐⭐⭐ 本轮真正的技术结论:`ADR-012` —— **约束必须下沉到代码层**

把三条互相独立的证据摆在一起,它们指向同一个结论:

| # | 证据 | 来源 | 性质 |
|---|---|---|---|
| 1 | 竞品失败原因是 **`未观察到对应变量变化`** —— 即**模型层的判断失败**,不是网络/解析失败。它的约束**全部写在 Prompt 与工具描述里**,靠模型自觉 | `变量更新失败.png` | **E1** |
| 2 | 我们自己的 **D5 对照:删掉「正文优先」「不得凭空编造」两条严约束后,断言通过率从 85% 反而升到 97%** | `out4/REPORT4.md §4.2` | **实测** |
| 3 | 我们自己的 **第 4 轮负向测试:玩家什么都没做,仍凭空产出 `/地牢/当前轮: 2→3`** —— 严规则**并没有拦住**它 | `out4/REPORT4.md §3` | **实测** |
| 4 | DZMM「只增不减」「更新不贴合上下文」 | `docs/11 §8.2` | E1 |

> 🔴 **三方(竞品 agent 宿主 / DZMM / 我们自己)都在同一个地方翻车,而三方都在用同一种手段:
> 用 Prompt 约束模型改数值。**
>
> **→ 结论:Prompt 约束不是可靠手段。它能提高合规倾向,但给不了任何保证,
> 而且(D5 实测)加码严约束甚至会压抑模型的合理推断、反而掉点。**

#### `ADR-012`(提案 · 待拍板)

> **LLM 只负责「提议」,代码负责「裁决」。**
> 任何一条 delta 在落盘前必须通过**代码层守卫**,Prompt 里不再承担硬约束职责。

守卫规则表(v1,全部可纯函数实现、可单测):

| 守卫 | 规则 | 拦截的真实缺陷 | 失败码 |
|---|---|---|---|
| **G1 路径白名单** | 路径必须存在于当前 schema | 凭空造字段 | `UNKNOWN_PATH` |
| **G2 类型** | 新值类型必须与 schema 一致 | 数值位置塞字符串 | `TYPE_MISMATCH` |
| **G3 值域夹取** | `min/max` 夹取,如 `生命 ∈ [0, 上限]` | DZMM「只增不减」溢出 | `CLAMPED`(警告,不拒绝) |
| **G4 枚举** | 枚举字段只能取声明内的值 | **D5 实测的 2 次 `ILLEGAL_ENUM`**(写了"战斗"/"石阶") | `ILLEGAL_ENUM` |
| **G5 单步幅度** | 单轮变化量 ≤ 阈值(可按字段配) | 一轮掉 90% 血 | `DELTA_TOO_LARGE` |
| **G6 🔴 只读/系统字段** | 标记为 `system` 的字段(如 `当前轮`、`总轮数`)**只能由引擎自增,模型无权写** | 🔴 **REPORT4 第 4 轮的 `当前轮 2→3` 凭空 +1** | `READONLY_PATH` |
| **G7 单调方向** | 可声明 `monotonic: increasing`(如 `经验`、`已用轮次`) | 经验倒扣 | `DIRECTION_VIOLATION` |

> ⭐ **G6 单独说一句**:REPORT4 第 4 轮那条「凭空 +1」里,**我自己的断言设计也有责任** ——
> 正文确实写了「门后是第三轮」,模型推进轮次**并非完全无依据**,
> 是我一边让正文推进场景、一边又断言 `当前轮` 不许变。
> 但**正确的修法不是改断言,也不是改 Prompt,而是 G6**:
> `当前轮` 这类**引擎时序字段压根不该让模型写**。改断言是掩盖,改 Prompt 不可靠,
> **把写权限收回代码**才是根治。
>
> 这条同时解释了为什么 D5(松规则)反而更好:
> **约束放在 Prompt 里,是在用「让模型少想」换「让模型听话」,代价是叙事推理能力下降;
> 约束放在代码里,模型可以放开想,想错了由代码兜住。** 两者不是同一个权衡。

## 7.11 ⭐⭐⭐ 第九轮:真实 ST 卡里发现 `$meta` —— `ADR-012` 的生态依据(E1)

> **材料**:真实 ST 卡 `DiLaoJSON.json`(`spec: chara_card_v2`)的
> `character_book.entries[11]`(变量初始化块)。**这是对 `ADR-012` 最有力的一条支撑。**

初始化块的第一行:

```json
{ "$meta": {"strictSet": true}, "地牢": {...}, "冒险者": {...}, ... }
```

| 发现 | 意义 |
|---|---|
| **`$meta` 字段存在** | 🔴 **MVU 生态已经接受「在初始化块里放约束元数据」** → 我们扩展 `$meta.mirage` **不是发明新格式,是用生态既有钩子** → **「ST 卡互通」与 `ADR-012` 不冲突**(完整论证见 `docs/06 §9`) |
| **`strictSet: true` 的语义 ≈ 我们的 `G1` 路径白名单** | ⭐⭐ **这张卡的作者自己就想要 G1** —— 他只是只能靠 Prompt 求模型遵守。**我们把它变成代码级保证,是在实现卡作者的原意,不是违背它。** 这是 `ADR-012` 从「我的设计偏好」升级为「生态既有诉求」的关键证据 |
| initvar **显式枚举 28 个路径 + 全部类型** | **G1/G2 零成本可得**,导入即生效,不需要用户做任何事 |
| 枚举值写在**世界书散文**里,不在 initvar | `地牢.难度` 初始 `"待选"`,真实取值 `简单/中等/困难` 在 `entries[2]` **正文**;`本轮房间` 取值在 `entries[4]` 正文 → **G4 机械推不出来**,必须靠 `B-14`(AI 补 schema) |
| `敌人: {"生命":0, "生命上限":0}` 是**占位值** | 🔴 机械推断 `max=0` 会**把敌人血量夹成 0,游戏直接玩不了** → **这就是 Tier B 必须 opt-in 的实证理由**(`docs/06 §9.2`) |
| `物品栏.材料: []` 空数组 + `entries[8]` 散文说格式是 `"铁片 ×3"` | 与 `docs/05 §4.4.1`「我们不抄字符串内嵌数量」**直接冲突** → 处置:**以卡的格式为存储事实,我们只加解析视图**(`docs/06 §9.3` 冲突类 1) |
| `entries[10]`(`constant: true`, `order: 110`)= **结算器 Prompt** | 再次印证 `§7.1`/`§7.2`:结算器是独立角色,规则靠常驻世界书条目注入 |

> ⭐ **一句话总结本节对 `ADR-012` 的意义**:
> 我原本担心「把约束搬到代码层」会不会违背 ST 生态的做法。
> `$meta.strictSet` 证明**恰恰相反** —— 生态早就想要这种约束了,只是**在纯 Prompt 架构里实现不了**。
> 我们不是在偏离标准,是在**把标准里一直存在的意图真正实现出来**。
