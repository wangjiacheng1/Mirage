## 第一部分 · 竞品全景图

### 1.1 先分类,再比较

这个赛道看着产品很多,但**底层只有四种商业模式**,每种模式的能力边界是由模式本身决定的,不是由团队水平决定的。看懂这一层,比记住几十个产品名更有用。

| 类型 | 代表 | API 来源 | 结构性优势 | **结构性天花板(无法靠努力突破)** |
|---|---|---|---|---|
| **① 自部署前端** | SillyTavern、RisuAI、Agnai | BYOK | 功能无上限、完全可定制、数据自持 | **移动端体验极差**;安装门槛劝退 99% 的人 |
| **② 原生移动客户端** | **ChatterUI**、Layla、通用 BYOK 客户端 | BYOK / 本地模型 | 移动端手感好、开箱即用 | 开发资源有限 → **叙事引擎深度普遍不足** |
| **③ 一体化托管平台** | Character.AI、**DZMM**、Janitor AI、猫箱/星野 | 平台自带 | 零门槛、UI 精良、有内容生态与社交 | **必须审查**(法律与支付通道要求);数据在平台手里;引擎封闭不可定制 |
| **④ 本地推理桌面端** | Backyard AI、KoboldCpp | 本地 GGUF | 完全离线、零 API 成本、无审查 | 需要好显卡;手机端模型质量不足以支撑长篇叙事 |

**Mirage 的坐标:类型 ②,但要把类型 ① 的引擎深度搬进来。** 这句话是整份文档的结论,后面所有内容都在论证它。

## 第二部分 · 重点竞品深度拆解

只拆**直接影响我们决策**的 5 个。

### 2.1 SillyTavern —— 引擎的标杆,移动端的灾难 ⭐

**它强在哪(我们要学的):**

| 机制 | 说明 | 对我们的意义 |
|---|---|---|
| **角色卡格式** | V1 → V2 → V3(CCv3),PNG 的 tEXt 块里塞 JSON,一张图即一个角色 | **这是我们接入生态的唯一钥匙**,见 §4.3 |
| **世界书(World Info / Lorebook)** | 关键词触发 + 扫描深度 + 插入位置 + 优先级 + 递归触发 | 比简单的"关键词注入"复杂得多,`docs/01` D-5 目前的描述偏简化 |
| **预设(Preset)体系** | 采样参数 + Prompt 结构模板,可一键整套切换与分享 | 社区会互相分享预设,是重要的内容形态 |
| **Author's Note(作者注释)** | 按"深度"插入上下文的指令,如"距离末尾第 4 条消息处插入" | **深度注入**是对抗人设漂移的关键技巧,比周期性复述更精细 |
| **正则(Regex)后处理** | 对模型输出做正则替换/删除,清理格式垃圾、隐藏思维链 | 重度用户的刚需,`docs/01` 的 G 模块**缺这一项** |
| **群聊** | 多角色同场,轮流发言 | 中后期能力 |

**它弱在哪(我们的机会):**

1. **移动端体验是灾难性的。** 要么用 Termux 在手机上装 Node 环境(劝退),要么在电脑上起服务然后手机浏览器连(电脑必须开着)。UI 是桌面 Web 直接缩放,手势、键盘、通知、后台续写全不对。
2. **配置复杂度极高。** 几十个参数铺在界面上,新手无从下手。
3. **没有真正的游戏化状态机。** 社区靠正则 + 扩展 + Prompt 硬凑出 HP/好感度,**本质是让模型自己算数,会漂移**——这正是我们 `§1.5 铁律一` 要解决的问题。

> **结论:SillyTavern 不是我们要打败的对象,而是我们要"兼容并继承"的生态。**
> 我们的目标用户此刻正在手机上痛苦地用它。

### 2.2 ChatterUI —— ⚠️ 你没提到,但这是最像我们的竞品 ◐

这是本次调研**最重要的发现**。它和 Mirage 的重合度:

| 维度 | ChatterUI | Mirage 计划 | 重合? |
|---|---|---|---|
| 平台 | Android 原生 | Android 原生(KMP) | ✅ 完全重合 |
| API | BYOK | BYOK | ✅ 完全重合 |
| 本地模型 | 支持(llama.cpp) | **明确不做**(`§1.4` 非目标) | ❌ 它多一项 |
| 角色卡 | 支持 | 支持 | ✅ 重合 |
| 世界书 | 🔴 **不支持**(E1 实测:建卡界面无此字段) | 支持 | ❌ **我们多一项** |
| **游戏化数值状态机** | 🔴 **确认没有**(E1 实测,`V-24` 已关闭) | **差异化核心** | 🎯 **确认是缺口** |
| 角色卡编辑字段完整度 | 7 个字段,**无字段填写说明**(E1) | 全字段 + 每字段示例 + AI 代填 | 🎯 **缺口** |
| 国内服务商预置 | 🔴 **不能选**(E1 实测) | 预置 DeepSeek/智谱/月之暗面等 | 🎯 **缺口** |
| 聊天气泡左右区分 | 🔴 **AI 与用户头像不分左右**(E1 实测) | 必须分 | 🎯 **及格线都没到** |
| 开源 | 是 | 待定(`docs/09` Q4) | — |

**这意味着什么:**

1. `docs/01 §1.2` 第 4 条"现有 BYOK 类手机 App 普遍只做聊天"的判断**仍然成立**,但要收窄为:"**已有原生移动 BYOK 客户端,但无人做游戏化状态机**"。我们的差异化必须更锋利地压在状态机上,而不是泛泛的"手机上的酒馆"。
2. **"做一个能用的手机版酒馆"已经不足以构成产品。** ChatterUI 已经做到了。
3. 但这也是**好消息**:它验证了需求真实存在,且证明了技术路线可行。

> ✅ **`T2-1` 已关闭。** 用户已亲手体验,结论见 §8.1 与 `docs/15 §7.8`。
> **一句话总结:它的引擎深度只到「角色卡 + 聊天」,世界书与状态都没做。**
> 这把我们的差异化从「做得更好」降级成了「它根本没做」—— 对我们是更有利的局面,但也意味着
> **「手机上的酒馆」这个坑位其实还空着**,不是只剩状态机一条缝。

### 2.3 RisuAI —— 盯住它的格式演进 ◐

它推动的 **Character Card V3(CCv3)** 可能成为下一代标准,支持更丰富的资产嵌入与模块化。

> **对 `docs/01 B-3` 的修订建议:** 目前只写了"V2 导入"。应改为 **V1/V2 全量兼容 + CCv3 尽力兼容(至少不崩、能降级读取基础字段)**。格式兼容性是生态产品的生命线,少支持一版就少一批用户。

### 2.4 DZMM —— 三个优势,我们一弃、二学 ⭐(用户实证)

> 以下为**用户一手信息**,置信度高于本文其它 ◐/❓ 条目。

DZMM 是一个**角色扮演游戏 App**(自带 API,用户零配置)。相对 SillyTavern,它有三个优势:

| # | DZMM 的优势 | 我们的应对 | 对应需求 |
|---|---|---|---|
| 1 | **玩家贡献的丰富角色卡市场** | ❌ **明确不做**。无服务端做不了 UGC 市场。改为**寄生现有生态**:把导入做到行业最好 + 做一个"去哪找卡"说明页 | `B-3`(战略级 P0)、`B-10`、`B-11` |
| 2 | **优秀的界面 UI 与立绘** | ✅ **学,但不自产美术**。把角色卡自带的图用到极致(大图/氛围背景/CCv3 多图切换) | `I-1`(已升 P0)、`docs/03` |
| 3 | **🎯 聊天窗口内悬浮的角色状态面板,每轮对话自动更新(MVU 形态)** | ✅ **学,而且要做得比它对** | `E-5a`(已进 MVP)、`E-5`、`E-5b` |

#### 2.4.1 关于第 3 点(MVU):这是本次调研最有价值的产品输入

**它验证了什么:** "聊天页里有一个会自己变的状态面板"这个产品形态是**被市场验证有效**的,不是我们一厢情愿的想象。
这直接导致 `docs/01` 的 MVP 扩容:**最小只读 HUD(`E-5a`)从 M4 提前进 MVP**,因为它是唯一一眼可见的差异化。

**但我们必须做对它做错的地方 —— 这是我们真正的技术优势:**

| | MVU / 酒馆社区方案 / DZMM(推测) | **Mirage** |
|---|---|---|
| 谁做算术 | **LLM 自己算**(直接输出 `HP = 88`) | **客户端状态机算**,LLM 只给 delta 意图 |
| 校验 | 基本没有 | 越界/非法/规则冲突一律钳制(`E-3`) |
| 长会话表现 | **必然漂移**(模型会算错、会被话术说服) | 稳定 |
| 能否追溯 | ❌ 做不到 | ✅ **点字段看历史变更**(`E-5b`),事件溯源的免费副产品 |

> 这正是 `docs/01 §1.5 铁律一` 的用武之地。**"玩一百轮数值也不会乱"是能被用户直接感知的质量差异**,也是抄不快的工程硬功夫。

#### 2.4.2 类型 ③ 的结构性特征(对所有托管平台成立)

| 它们的优势 | 我们能跟吗 |
|---|---|
| 零配置、点开就玩 | ❌ **结构上不可能**。无服务端 = 不能自带 Key。这是 `ADR-001` 已确认的取舍 |
| 内容生态与社交(角色广场、热榜) | ❌ 无服务端做不了 UGC 市场。**但可以寄生 Chub 等现有生态** |
| 精良的 UI 与立绘 | ✅ **可以追平**,这是纯投入问题,见 `docs/03` |

**它们的代价,正是我们的卖点:**

- **审查**:支付通道(Apple/Google/信用卡)和法律环境强制要求内容过滤。用户想玩的剧情经常被打断。我们 BYOK → **尺度由用户的 Key 提供方决定,不由我们决定**。
- **数据**:聊天记录在平台服务器上,平台可以改模型、涨价、关服、泄露。我们 → **数据不出端**。
- **成本**:订阅制,玩得多也是固定月费(或限流)。我们 → **用户按实际 token 付费给模型商,我们抽成为零**。
- **不可定制**:Prompt 是黑盒。我们 → **Prompt 完全可编辑**(`G-2`)。

> **结论:竞品分析不动摇"无服务端 BYOK"的决策,反而强化它。**
> 我们不是"做不起服务端",而是**主动放弃规模,换取硬核用户唯一在乎的三件事:尺度、数据、可控**。

### 2.5 AI Dungeon —— 请研究它的失败 ⭐

它是"游戏代入"玩法的开创者,但 2021 年的两次事件让核心用户大规模出走:

1. **审查系统误伤**:为过滤违规内容引入的过滤器大量误判正常剧情,体验崩坏。
2. **隐私事故**:用户发现私人剧情内容可被平台员工查看,信任彻底破裂。

**对我们的直接启示(应写入 `docs/07`):**

- 这两个雷我们**结构上天然免疫**(无服务端、不审查),这是**必须对外明确传达的卖点**,不是默默做到就行。
- 但要警惕:如果将来为了上架而加内容过滤(`docs/09` Q3),就是在重蹈覆辙。**真要加,必须是用户可关闭的本地开关,且默认关闭。**

## 第四部分 · 结论

### 4.1 三个核心结论

**结论一:市场空白是真实存在的,但比原先判断的要窄。**

```
                引擎深度(世界书/状态机/可定制)
                         ↑
      SillyTavern ●      │      ● RisuAI
                         │
                         │           ◆ Mirage 目标位置
                         │        (引擎深度 × 移动原生)
        ─────────────────┼──────────────────→ 移动端体验
                         │      ● ChatterUI
                         │
             Backyard ●  │   ● Character.AI / DZMM / 猫箱
```

右上角确实没人占据。但 **ChatterUI 已经在往上爬**,我们的时间窗口不是无限的。

**结论二:"手机版酒馆"不再是有效的差异化,"算得准的游戏化状态机"才是。**

必须把 `docs/01 §1.2` 第 4 条的判断**收窄并锐化**。详见 §6 的修订建议。

**结论三:无服务端 BYOK 的决策被竞品分析完全验证,不需要动摇。**

类型 ③ 的所有优势我们都拿不到,但它们的三个结构性缺陷(审查、数据、不可控)恰好是硬核用户出走的全部原因。

### 4.2 我们真正的护城河 —— 和假的护城河

| | 是不是护城河 | 为什么 |
|---|---|---|
| 功能数量多 | ❌ **假的** | 酒馆功能比我们多十倍,这条赛道上"功能多"不稀缺 |
| 移动端原生 | ❌ **已被抹平** | ChatterUI 已经做到 |
| BYOK / 数据本地 | ❌ **只是入场券** | 类型 ①② 全都是 |
| **游戏化状态机的正确性** | ✅ **真护城河** | 需要事件溯源 + 状态机 + 协议设计 + 大量调校,**是工程硬功夫,抄不快** |
| **移动端的叙事交互手感** | ✅ **真护城河** | 流式渲染、长文阅读、分支切换、单手操作——需要大量打磨,是你的 Android 经验优势所在 |
| **对酒馆生态的兼容深度** | ✅ **真护城河** | 格式兼容是脏活累活,做到 95% 和做到 70% 是两个产品 |

> 这三条,全是**工程质量**而非**功能清单**。对你(有 Android 经验、AI 新手、单人开发)来说,这其实是最有利的竞争结构。

### 4.3 必须承认的三个劣势与对策

| # | 劣势 | 严重度 | 对策 |
|---|---|---|---|
| 1 | **内容冷启动**:Chub 有海量角色卡,c.ai 有海量用户创作,我们是零 | 🔴 高 | **不要自建市场**(无服务端也做不了)。战略是**寄生**:把"角色卡导入"做到行业最好,让用户 10 秒内把 Chub 的卡搬进来。`B-3` 应从"技术需求"升级为**战略级 P0** |
| 2 | **BYOK 转化漏斗**:配 Key 会劝退绝大多数人 | 🔴 高 | 承认并接受。**首发只服务已有 Key 的酒馆用户**(`§1.3` 画像 A 的判断是对的)。`A-10` 引导流程是生死线。不要为画像 B 妥协架构 |
| 3 | **ChatterUI 的先发优势** | 🟡 中 | 不要在它强的地方硬碰(轻量、本地模型)。**用状态机 + 兼容深度 + 交互手感做垂直超越**。它做"手机上的聊天",我们做"手机上的跑团" |

### 4.4 最终定位决策(v1.1,用户拍板)

> **初期不追求原创形态:对齐行业标杆 + 补足其短板。差异化与产品特性后续再开拓。**
> 理由:单人开发、人力与精力有限。原创形态的试错成本远高于"把已验证的事做对"。

```
   Mirage v1 = SillyTavern 的引擎深度
             + ChatterUI 的移动端实现
             + DZMM 的状态面板形态(但数值由代码算)
             − 角色卡市场(明确不做)
             − 自产立绘(明确不做)
             − 本地模型(明确不做)
```

这意味着 **v1 阶段的需求评审只有一个标准**:

> "酒馆/ChatterUI/DZMM 里有没有这个?有 → 我们做得对不对、顺不顺手?没有 → **先放进 backlog,不进 v1**。"

唯一的例外是 `§1.5 铁律一/二`(状态正确性与消息树)—— 那是**补短板**,不是开新特性,必须在 v1 做对。

### 待查（优先级提到 P1，因为它直接决定支柱 ① 怎么写）

见 §10.2 的 8 个问题。**最关键的 3 个**：
1. 导入一张带 `<initvar>` 的 MVU 卡，**状态面板会不会出来、数值会不会每轮更新**？
2. 有没有**世界书**编辑与召回？条目多了会不会全量注入？
3. 结算失败/无变化有没有**区分提示**？能不能重算？

> 如果 1 和 2 的答案是「没有」，那么 Foreverse 的定位更接近「UI 更好的 ChatterUI + 卡片库」，
> 我们的支柱 ① 依然成立，只需换成上面的新措辞。
> 如果答案是「有」，那它是我们**最直接的对手**，需要重新做一次定位。

### DSH Tavern 评分上调的理由（读源码后）

| 维度 | 原评分 | 新评分 | 理由 |
|---|---|---|---|
| 引擎完整度 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 内嵌完整 MVU 上游源码、ST 预设导入、兼容模式、分卷压缩、场景配图。3300 项测试。**它是目前功能最全的移动可用方案** |
| 数值可信度 | 🟡 | ⭐⭐⭐⭐ | revision 绑定 + stale 丢弃 + 原子提交 + 结算前快照。架构是对的，用户遇到的失败是已修复的具体 bug，不是设计缺陷 |

> 🔴 **诚实评估**：DSH Tavern 在**引擎能力**上已经超过我们的 M1~M3 规划。
> 我们的机会**不在功能数量**，而在三处：
>
> | # | 我们的机会 | DSH 的短板（E1 证实） |
> |---|---|---|
> | 1 | **安装门槛** | 必须先装 DeepSeek 的 DSH 宿主 + Node + pnpm，再跑 install.sh。普通玩家装不了 |
> | 2 | **确定性守卫** | 它的约束靠 MVU 框架的 schema，**G3 值域 / G5 幅度 / G6 只读 / G7 单调这四条它没有** —— 用户实测的「数值漂移」就是这个缺口 |
> | 3 | **原生体验** | 它本质是 WebView 里的 Web 应用（React + jsdom + Vue 面板），我们是原生 Compose |
>
> 这三条正好对上我们的三支柱。**定位不需要改，但不能再低估对手。**
