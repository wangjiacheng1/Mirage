## 开篇 · 三个你作为开发者最容易踩的产品陷阱

在给具体建议之前,先说三个我判断你最可能掉进去的坑。它们和技术能力无关,恰恰是技术能力强的人更容易中招。

## 1 · 状态 HUD:建议提前进 MVP ✅ 已采纳

**建议**:把"最小只读状态面板"(`E-5a`)从 M4 提前到 MVP。

**理由(三条,按重要性排序)**:

1. **它是 MVP 里唯一"一眼可见"的差异化。** 其余 MVP 功能(流式、角色卡、Swipe、编辑)ChatterUI 全有。**没有 HUD,我们的 MVP 就是一个功能更少的 ChatterUI**,拿给任何人看都无法说明"这个为什么值得用"。
2. **DZMM 已经替我们验证了形态。** 不是我们的假设,是市场结论。
3. **边际成本低。** `§1.5 铁律二` 本来就要求 MVP 打通双通道协议 + 状态事件表。在此之上加一个只读面板,主要是 UI 工作。**真正贵的是不做它的机会成本。**

**范围严格限定(防止膨胀)**:

| 做 | 不做 |
|---|---|
| 角色卡声明 3~5 个字段 | 复杂嵌套结构 |
| 每轮解析 delta → 状态机校验 → 更新 | 掷骰、结局判定、时间推进 |
| 悬浮/可折叠面板,只读展示 | 用户手动改数值、变化动效 |

**代价**:MVP 周期 +1~1.5 周。我认为非常值。

## 2 · MVU 的纠偏:把"算得准"做成可感知的卖点 ✅ 已采纳

这是我对你第 3 条思考最想补充的一点。

**现状**:酒馆社区的 MVU 类方案和 DZMM(推测),本质都是**让 LLM 自己做算术**——模型直接输出 `HP = 88`。这必然漂移,因为:① 模型会算错;② 用户可以用话术说服它("我刚才捡了 3 把钥匙")。

**我们的做法**:LLM 只输出**变更意图**(`hp_delta: -12`),算术与校验由客户端状态机做。

**关键建议:不要让这个优势只停留在工程层面,要让用户看得见。**

| 做法 | 用户看到的 | 竞品能做到吗 |
|---|---|---|
| `E-5b` 点击字段 → 查看变更历史<br>("第 12 轮 −12,原因:触发陷阱") | "这个 App 的数字是有据可查的" | ❌ 做不到。它们没有事件流 |
| 长会话压力测试后数值仍准确 | "玩一百轮也不会乱" | ❌ 必然漂移 |

**这是我认为最值得写进应用商店描述/社区宣传第一句的卖点。** 它具体、可验证、且抄不快。

## 3 · 不做三个入口:用"模式标签"统一心智 ⏳ 待你确认

**背景**:三类玩法(角色扮演 / 情景模拟 / 游戏代入)共用一套引擎,这是架构洞察。但**用户心智**上它们确实不同。

**建议**:**不要做三个首页入口**。改为在角色卡上标一个 `mode` 字段,它只影响三件事:

| mode | 默认预设 | HUD | 开场引导 |
|---|---|---|---|
| `roleplay` | 对话向 | 默认隐藏 | "你想对 TA 说什么?" |
| `simulation` | 对话向 + 评价维度 | 显示进度/评分 | "场景已就绪,开始吧" |
| `adventure` | 叙事向 | **默认显示** | "你站在洞口……" |

**理由**:三个入口会让产品看起来像三个半成品,且首页复杂度 ×3。一个标签就能解决差异,且角色卡导入时可以从 tags 自动推断。

**代价**:几乎为零。只是一个枚举字段 + 三套默认配置。

**风险**:如果将来某个玩法长成主力,可能需要独立入口。但那是幸福的烦恼,到时再拆。

   - 从剪贴板自动识别
   - **从 SillyTavern 整体迁移**(`B-10`)
2. 配一个**"去哪找角色卡"说明页**(`B-11`):列出 Chub 等社区来源,**纯文字说明,不内嵌浏览器**。
   - 不内嵌浏览器是有意的:① 规避内容责任;② 省开发量;③ 用户本来就会用浏览器。

## 5 · 视觉:性价比最高的一个决策 ✅ 已采纳

**问题**:DZMM 的立绘很好看,但那是重资产,我们不可能做。

**建议**:**不自产任何美术资源,把角色卡自带的那张头像用到极致。**

| 手法 | 成本 | 效果 |
|---|---|---|
| 聊天页顶部头像可展开为**大图** | 极低 | 立刻有"立绘感" |
| 头像**模糊 + 暗化**作为聊天背景 | 极低 | **氛围感提升最明显的一招** |
| CCv3 的多图资产,按情绪/状态切换 | 中 | 接近真立绘体验 |
| 按角色卡主色调自动生成配色 | 低 | 每个角色有独立视觉身份 |

**理由**:角色卡**本来就自带图**(PNG 格式决定的),这是免费素材。用户导入的卡质量越高,我们的界面就越好看——**这是一个会自己变好的设计**。

## 6 · 反"设置集合":用档位代替参数 ✅ 已采纳(`G-7`)

**这是酒馆最大的病,也是我们最容易继承的病。**

**建议定一个硬性产品指标**:

> **已有 Key 的用户,从打开 App 到说出第一句话 < 60 秒。**

配套规则:

1. 采样参数**只暴露三档**:稳定 / 平衡 / 狂放。原始数值(temperature/top_p/penalty)全部折叠进"高级"。
2. 任何新功能的默认值必须"开箱可用",**不允许出现"需要先去设置里打开才能用"的功能**。
3. 设置页分两层:**常用**(5~8 项)+ **高级**(其余全部)。
4. **我们对酒馆的超越不是"功能更多",而是"同样的功能,不用配置就能用"。**

## 12 · 🆕 把"服务商抽签"变成功能:透明化面板(E1,2026-10-16 实测驱动)

> **这条建议不是产品直觉,是实测逼出来的。** 依据 `docs/14 §10.4`:
> 同一次 60 秒探针运行内、同一个 model id `z-ai/glm-5.1`,5 个请求命中 **4 个不同上游**
> (StreamLake / GMICloud / Venice / StreamLake / StreamLake)。

### 12.1 问题:用户会遇到"同一个模型,今天突然变傻/变慢/变贵"

这在聚合商(OpenRouter 类)上是**必然发生**而不是偶发。而用户的归因一定是错的:

| 用户的真实体验 | 用户会怪谁 | 真实原因 |
|---|---|---|
| "今天 AI 写得特别水" | **怪我们的 App** | 漂到了一个量化更狠的上游 |
| "怎么等了 20 秒才出字" | **怪我们的 App** | 漂到了排队中的上游(实测首 token 12.57s) |
| "我今天没多聊怎么花了 3 倍钱" | 怪 OpenRouter 或我们 | 漂到了贵的上游 / 没关思考(实测贵 7.6 倍) |
| "工具调用/状态面板突然不动了" | **怪我们的 App** | 漂到了不支持 `tools` 的上游 |

**→ 这是一类我们"明明没做错却必然背锅"的差评来源。**

### 12.2 建议:每条消息都记录并可展开查看"这条是谁生成的"

**成本极低**(字段本来就在响应里,存下来即可),**收益很具体**:

| 字段 | 来源 | 展示价值 |
|---|---|---|
| `provider` | OR 顶层 `provider`(DS 用 `system_fingerprint` 代替) | **核心**:让"变傻了"可自证 |
| `native_finish_reason` | OR `choices[].native_finish_reason` | 区分是我们截断还是上游截断 |
| 首 token 延迟 / 总耗时 | 客户端自测 | 让"今天好慢"有数 |
| `usage.cost` + `reasoning_tokens` | OR `usage` | **让"钱花哪了"可见**:实测 87% 的输出 token 花在用户看不见的思考上 |
| `prompt_cache_hit_tokens` | DS `usage`(非标) | 长会话省钱是否生效 |

**形态建议**:消息长按 → "生成详情"(默认折叠,不占主界面)。
再加一个**会话级汇总条**:本会话花了 $X / 其中思考占 Y%。

### 12.3 为什么这是真的差异化(而且是 E1 级的)

- **SillyTavern**:有 token 计数,但**不展示 provider,也不做成本归因**(它面向的是本地/直连用户,漂移不是它的问题)
- **ChatterUI**:移动端,**连 token 统计都很弱**
- **DZMM**:自带 API,**不存在 provider 概念**,也没有成本透明的动机(成本是它自己的)

→ **BYOK 产品的用户是"自己付钱的人",成本透明与可归因对他们是刚需,而三个标杆都没覆盖这个场景。**
这比 §2 的"状态可追溯"(E3,依赖未证实前提)扎实得多 —— **建议把它作为对外卖点的候补第一位。**

### 12.4 连带的一条 UI 纪律(来自 `R-T19`)

实测首 token 可达 **12 570ms**,且**前 11 091ms 零字节、连心跳都没有**。
→ **"正在输入"的转圈动画绝对不够**,必须三态:`连接中` → `服务商排队中` → `正在生成`。
否则用户在第 8 秒就会判定卡死并重试,而**重试是双倍计费**(他自己的钱)。

### 12.5 🆕 面板能展示什么,已经被实测定死了(2026-10-16 第三轮)

| 字段 | 从哪拿 | 延迟 | 能不能做 |
|---|---|---|---|
| `provider` | **流内每个 chunk 的顶层 `provider`** | 实时 | ✅ **改用流内取**,不要去查后台(第三轮我自己就踩了这个坑,见 `docs/14 §12.3`) |
| `native_finish_reason` | `choices[].native_finish_reason` | 实时 | ✅ |
| 首 token 延迟 / 总耗时 | 客户端自测 | 实时 | ✅ |
| `usage.cost` / `reasoning_tokens` | 流**最后一条** chunk | 实时 | ✅ **但中断时拿不到**(实测:读 5 行就断 → 流内无 `usage`) |
| `cancelled` / 后台口径 `latency` / `generation_time` | `GET /api/v1/generation?id=` | 🔴 **有落账延迟**,实测 20s 内查不到(404) | ⚠️ **必须按异步设计** |
| 剩余额度 | DS `/user/balance`(0.2s) / OR `/api/v1/credits` | 快 | ✅ → `A-17` |

**🔴 由此得到一条硬性 UI 纪律:成本数字不能做成「请求一结束就显示」。**

两种形态任选,不要混:

| 方案 | 做法 | 代价 |
|---|---|---|
| **A(推荐)** | **只用流内自带的 `usage.cost`**,不查后台。中断的消息显示「成本未知」并给一个手动「查询」入口 | 中断的那条拿不到数字 |
| B | 后台异步补齐:消息先显示「计费中…」,后台轮询回填 | 要写轮询+重试,且用户会看到数字跳变 |

> **我的建议是 A。** 理由:B 的复杂度全花在「中断的那条消息的精确成本」上,
> 而这恰恰是用户最不在意的一个数(他刚刚亲手把它停掉了)。
> 会话级汇总条用「已知成本之和 + N 条未知」表达即可。

### 12.6 🆕 产品解锁:状态面板可以做成**真流式**,不必等整轮结束

> **这条之前是我不敢确定的,第三轮实测确认了(`docs/14 §12.2` C17)。**

实测:**叙事正文的 delta 与工具调用的 delta 在同一个 SSE 流里共存**
(OpenRouter 74 片正文 + 12 片工具;DeepSeek 53 片正文 + 43 片工具)。

**→ 交互可以做成:**

```
用户发消息
  ↓
正文开始逐字打出 ──────────────────────────→ 用户已经在读了
  ↓(同一条流里,工具分片在后台静默累积)
收到 [DONE]
  ↓
HUD 的 HP/物品**一次性原子更新** + 轻微高亮动画
```

**三条对比竞品的含义:**

| 竞品 | 它的做法 | 我们可以更好的地方 |
|---|---|---|
| **DZMM**(E1,你的一手信息) | 悬浮状态面板,每轮自动更新 | 形态照学。但我们能做到「正文不等状态」 —— 不需要为了算状态而延迟放出叙事 |
| **SillyTavern**(E2) | 变量/状态靠正文里的约定格式(待 `V-1` 确认) | 若它是文本协议,**流式下就必须等正文写完才能解析** → 我们用 tools 通道可以不污染正文 |
| **ChatterUI**(E1) | 基本没有状态管理 | 这就是我们要补的短板 |

**🔴 但两条纪律必须同时写死:**

1. **HUD 绝不在流式中途做「中间态更新」。** 分片拼接到一半的 `arguments` 是非法 JSON
   (`docs/02 §5.1.1c` T4),任何乐观解析都会在换模型时崩。**只在 `[DONE]` 后原子更新一次。**
2. **数值仍然由客户端状态机算,不是直接采信模型给的最终值。** 模型给的是 `delta`
   (实测两家都正确理解了「记录增量而非最终值」),客户端做 `fold` —— 这是铁律 2,不可放宽。
