## 2 · T1 · 账号与 API Key 准备(0.5 天)

### 2.1 为什么必须准备 2 家以上

`docs/01` A 模块的核心需求是**多端点兼容**(用户会用各种服务商)。如果你只用一家测,会把这家的"方言"当成标准,到 M1 才发现兼容性问题。

**至少 2 家,最好 3 家,且要覆盖:**

| 要覆盖的类型 | 为什么 |
|---|---|
| 一家**便宜的**,用来跑大量评测 | 评测要跑几百次请求,用贵模型会心疼 |
| 一家**聚合型**(一个 Key 调多个厂商模型) | 低成本验证"换模型"场景,也最接近用户真实用法 |
| 一家**能力弱的小模型** | ⭐ **关键**:用来验证"崩人设"和"工具调用降级"。强模型看不出我们的 Prompt 有多脆弱 |

### 2.2 推荐组合

> ⚠️ 定价和模型名会变,以官网为准。以下是选型思路,不是报价单。

| # | 候选 | 选它的理由 | 建议充值 |
|---|---|---|---|
| 1 | **DeepSeek** | 便宜、中文叙事能力不错、OpenAI 格式兼容、国内直连 | ¥50 |
| 2 | **OpenRouter** | 一个 Key 调几十家模型(含 Claude/Gemini/Llama 系),**最适合测多端点与换模型** | $10 |
| 3 | 任意**小参数开源模型**(可从 OpenRouter 里选免费/极便宜的) | 压力测试用 | ¥0 |

**注意**:OpenRouter 等境外服务需要你自备网络条件。如果不方便,可用国内的 OpenAI 格式中转服务替代,但**要确认它是否完整支持 `stream` 与 `tools`**——很多中转站在这两项上有阉割,而这正是我们要验证的核心。

### 2.3 具体操作步骤

1. 注册账号 → 充值 → 创建 API Key
2. **在官网文档里找到并记下三样东西**(这三样就是我们 App 里要用户填的):
   - `base_url`(⚠️ **实测修正**:DeepSeek 官方示例是 `https://api.deepseek.com`,**不带 `/v1`**;OpenRouter 则是 `https://openrouter.ai/api/v1`,**必须带**。各家不统一,照抄官网)
   - `api_key`(形如 `sk-xxxx`)
   - `model` 的准确 ID(形如 `deepseek-chat`,**不是产品名**)
3. 在本机设成环境变量,**不要写进任何文件**:
   ```bash
   export MIRAGE_BASE_URL="https://api.deepseek.com/v1"
   export MIRAGE_API_KEY="sk-你的key"
   export MIRAGE_MODEL="deepseek-chat"
   ```

##### 📦 V-1 交付物规格(2026-10-16 补,用户问"给一个完整的 Response JSON 可以么")

**可以,而且很有用 —— 但单给它不够。** 原因:完整 response JSON 只告诉我**模型吐了什么**,
而 V-1 真正要定稿的是**协议**,协议 = 「我们怎么要求」+「模型怎么回」+「客户端怎么解析」。
只拿到中间一环,我仍然得靠猜去补另外两环,那就又回到 E3 了。

**按价值排序,能给几样给几样:**

| 优先级 | 交付物 | 为什么需要 | 从哪拿 |
|---|---|---|---|
| 🔴 **1** | **请求侧的那段指令原文** —— 即 Prompt 里要求模型"输出变量更新"的那一段模板 | **这才是协议本体。** 有了它我才能照着写我们的 `docs/05` 模板,而不是另创一套 | 酒馆里看「预设 / Author's Note / 世界书条目 / 扩展设置」里那段模板文本;或扩展的 README / 示例文件 |
| 🔴 **2** | **模型吐出来的原始 `content` 字符串**(✅ **完整 response JSON 正好含这个**) | 决定我们解析器的形态(JSON? 标记? 脚本命令?) | 你说的那份 response JSON 就够 |

### 4.9 M0 通过判定标准 ⭐

**必须全部满足才算通过,才可以开工写 Android:**

| # | 判定项 | 标准 |
