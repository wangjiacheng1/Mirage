## 4. M2 切片定义与排序依据

**用户提议**：先做流式对话 MVP，角色卡解析器往后放。
**决定：采纳。** 并把 M1 剩余项（卡解析、Room 存储）移入 M2，M2 改用**垂直切片**推进。

### 为什么采纳（理由比「先做个 MVP 爽一下」强）

| # | 理由 |
|---|---|
| ① | **风险前置** —— M0 只用 **Python** 验过 SSE，**Ktor 的流式解析在 Kotlin 侧一次都没跑过**，是剩余不确定性最高的一块 |
| ② | **守卫还没端到端验证** —— G1~G8 只在单测里绿过，它真实的输入是「模型提议的状态」，没有真实 LLM 输出就验不了 |
| ③ | **卡解析器的正确性依赖「有东西能跑」** —— 解析出字段但不能对话，无法验证字段是否真进了 prompt；反之先有对话链路，导卡后立刻能看出来 |
| ④ | 反方理由都能低成本绕过 —— 没卡用硬编码 system prompt 顶上；没存储先在内存里跑 |

### 🔴 但不做「纯聊天 MVP」，要做垂直切片 —— 这一条有 E1 源码支撑

M0 验证的是**方案 C 双通道**（正文流式 + 独立结算请求）。若 MVP 只做正文流式，
**结算通道在 Kotlin 侧仍然是零验证**，风险只是推迟、没有消除。

而「能不能安全地分两步做」不是我拍脑袋，是 **E1-源码**给的答案（`docs/16 §12.1`）：

> 竞品把结算挂在 `MESSAGE_RECEIVED` 事件上 —— **结算发生在正文完整收到之后**，不是边流边算。

→ **正文流式通道与结算通道天然解耦、天然串行**，所以 **S1 做完再做 S2 不会返工**。
这是本轮最有价值的一条结论：它把「先做哪个」从偏好问题变成了有证据的工程排期。

### 切片定义

| 切片 | 内容 | 产出验收 | 优先级 |
|---|---|---|---|
| **S1** | **正文流式通道**：接入点配置（含国内服务商模板）+ 凭据加密存放 + 流式解析 + 最小对话界面（气泡**区分左右**）+ 进度三态 + 停止按钮 | 手机上能和真实模型流式对话 | 🔴 P0 |
| **S2** | **结算通道**：独立 Provider 配置 + 非流式结算请求 + 围栏剥除兜底 + 接到 `StateGuards` + 结算回执 UI（7 态） | 真实模型产出的提议能被守卫裁决并显示回执 | 🔴 P0 |
| **S3** | **ST 角色卡解析**：PNG tEXt + JSON，`<initvar>` → schema 推导，含 `B-15` | 真卡导入后能对话、状态面板能出来 | P1 |

> 否则 S4 不是「加个数据库」而是重写。这是本次调整唯一的真实代价，必须认。

### 3.2 M0 硬约束（S1 已全部落实，勿重新发现）

| 约束 | 出处 |
|---|---|
| `[DONE]` 是唯一可靠收尾判据；OR 会发**两条** `finish_reason:"stop"`，`usage`/`cost` 只在第二条 → **不得在首个非空 `finish_reason` 时 break** | `docs/14`，铁律区 #4 |

### 第 11 轮：IDE Sync 的第二个坑 —— Invalid Gradle JDK configuration

命令行已全绿，但 Android Studio Sync 仍失败：`Invalid Gradle JDK configuration found`。
**纯 IDE 侧问题**（命令行用 PATH 里的 java，AS 用它自己记的那份配置）。

查到的环境事实：

| 事实 | 值 |
|---|---|
| Android Studio | 2025.1.1 Narwhal（`AI-251.25410.109`），只装了这一个 |
| `JAVA_HOME` | **空的**（命令行能跑是靠 PATH 里的 java 兜底） |
| 系统 JDK | 只有一个：`ms-17.0.15`（`~/Library/Java/JavaVirtualMachines/`） |
| AS 内置 JBR | 实测 **21.0.6** |
| `jdk.table.xml` 注册项 | `jbr-17` / `jbr-21` / `ms-17` |
| 🔴 异常 | **`jbr-17` 和 `jbr-21` 指向同一个路径**，而该路径下实际是 JDK 21 |

**推断（E3，未直接证实）**：`jbr-17` 是早年 AS 捆绑 JBR 17 时留下的陈旧条目，
路径不变但内容已换成 21 → 名实不符。项目 Gradle JDK 若指向它，AS 解析后
发现版本对不上注册信息，就报 `Invalid Gradle JDK configuration found`。
（`.idea/` 当时尚未生成，看不到项目级设置原值，故只能标 E3。）

修复（对所有可能原因都有效）：

| 改动 | 内容 |
|---|---|
| `app/.idea/gradle.xml` 🆕 | `gradleJvm = ms-17`（真实绝对路径，且**就是命令行用的那个 JDK**）+ `distributionType = DEFAULT_WRAPPED`（强制走 wrapper 的 8.9，禁止 IDE 另选） |
| `app/.idea/misc.xml` 🆕 | 工程 SDK = `ms-17`、languageLevel = JDK_17，避免「编译能过但编辑器满屏飘红」 |
| `app/shared/build.gradle.kts` | 🔴 新增 `jvmToolchain(17)` —— 见下 |

> `.idea/` 已被 `.gitignore` 排除，属本机配置，不入库。

**为什么选 `ms-17` 而不是 AS 内置的 `jbr-21`**：不只是「能用就行」。我们这两轮栽的
都是「命令行过、IDE 不过」，让两边用同一个 JDK 能直接消灭这一整类分歧，
顺带共用一个 Gradle daemon（省一份内存）。

**顺带补掉的真实缺陷：`jvm()` 目标没钉编译 JDK**

`:shared` 里 `androidTarget` 显式写了 `jvmTarget = 17`、`android{}` 也写了 17，
**唯独 `jvm()` 这个 target 没有任何约束** —— 它跟着「当前跑 Gradle 的那个 JDK」走：
命令行（PATH 里是 JDK 17）编译成字节码 17，而 Android Studio（Gradle JDK 若是
JBR 21）会编译成字节码 21。产物不一致会让构建缓存反复失效，更糟的是会制造
「命令行测试全绿、IDE 里却报错」这种最难查的问题。

`jvmToolchain(17)` 把「用哪个 JDK **编译**」和「用哪个 JDK **跑 Gradle**」彻底解耦。

> 📌 教训：**多 target 的 KMP 模块，每个 target 的 jvmTarget 都要显式钉死，
> 或者直接上 toolchain。漏一个就会产生跟随环境漂移的产物。**
