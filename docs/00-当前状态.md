**三条关键设计**：

| 决定 | 理由 |
|---|---|
| 🔴 **备份里绝不含访问密钥** | 备份会被发到电脑、传进网盘。密钥跟着走是直接的金钱损失；它留在系统密钥库里，换机重填一次即可。**有专门用例扫文本里不许出现 `apiKey`/`credential`/`secret` 等字样** |
| **导入是「加进来」不是「盖掉」** | 覆盖式看起来更干净，但点错一次文件，正在玩的进度就没了且不可撤销。多出几局重复的，用户自己删即可 —— 两种错误代价差太远 |
| **插入消息按「先父后子」拓扑排序** | 备份文件可以被手工改过，不能假设它一定有序。反复扫描只插「上一条已就位」的，一轮插不动就停，剩下的跳过并计数 |

**一处修正：汉字 token 系数 1.0 → 1.5**

对照 DSH Tavern 的估算实现（E1-源码 `features/request-context.js`：*a CJK character is about 1.5 tokens*）发现
**我们中文场景低估 24~31%**，而中文正是主场景。改后四个样本对照：

| 样本 | 我们（新） | DSH | 偏差 |
|---|---|---|---|
| 纯中文 | 27 | 26 | +4% |
| 中英混排 | 25 | 25 | 0% |
| 纯英文 | 15 | 13 | +15% |

内部用「半 token」整数运算（汉字 3 个半 token），避免浮点累加误差。

**🔴 关于上下文超长，我们和 DSH Tavern 的策略差异（E1-源码）**

| | 我们 | DSH Tavern |
|---|---|---|
| 超长怎么办 | **丢弃最旧的历史** | **压缩成摘要**（Tavern Compaction），保留最近 N 轮原文 |
| 触发 | 每次发送前算 | 手动 / 每 N 轮 / **达 X% 自动**（默认 80%，界面标注「估算」）|
| 保留原文 | — | 「压缩后保留最近几轮原文」默认 **10** |
| 代价 | 免费、即时、真的会忘事 | **额外一次模型调用**，但记得住大意 |

⚠️ **分层说明（铁律一要求）**：这个压缩是**宿主（agent 框架）层**的能力，Tavern 自己只负责
配置策略、定义摘要契约、决定在哪个安全边界触发。我们没有这样一个宿主，**不能直接照搬**。
它的护栏值得抄：**「压缩不改变 Story Timeline 的权威性」**——摘要是投影，原始事件永远留着。

→ **摘要压缩列入 M3 记忆系统**，不在 M2.5 范围。

**另一个查证结论：正文排版我们零约束（E1-代码 + E1-卡数据）**

提示词里**一个字都没要求排版**（唯一自写的指令是状态栏那句「不要在正文里写数值」）。
而两张真卡的 `system_prompt` / `mes_example` **星号数均为 0**，示例对话示范的是「引号台词 + 纯叙述」。
→ **用户测不到斜体是必然的**，不是 bug。粗体那条通（地牢卡开场白的 `**简单**` 等）。
结论：**排版风格属于卡作者，我们只负责正确渲染**。不加提示词约束（省 20~30 token/轮，且不与卡作者风格打架）。

**🔴 真机反馈的三个问题（2026-11-04，全部已修）**

| # | 现象 | 真因 | 修法 |
|---|---|---|---|
| 1 | 切回旧版本后，状态栏数值变回去了，但下面的结算回执还是新版本那次的 | **轮次编号撞车**。重新生成时先退回上一条，当前这条线上就没有回复了 → 编号归零 → 新回复又拿到 1 号。结算回执按编号挂，两个版本都是 1 号，后来的覆盖了先来的 | 编号改成从**整局全部消息**取最大值，保证树内唯一；`messageIdByTurn` 也改成收全局 |
| 2 | 重新生成后切走存档再切回来，最后一条回复**重复一遍** | 一次生成结束后，界面状态里仍留着那段完整回复（用量、停止原因要靠它显示）。切存档会调用「停止」→ 停止会定稿 → **把已经存过的文字又存了一遍** | 加 `pendingReply` 标记位，只有真的有未定稿内容才定稿；切存档时只在正在生成时才调停止 |
| 3 | 改了自己说的话，下面按旧内容生成的回复还留着 | 设计缺口，用户指出的 | 编辑自己的话时多给一个**「保存并重新生成」**：把「聊到哪一条」挪到被改那条，重新生成一次。**旧回复连同它后面聊过的内容原样留在树上**，用 ‹ › 能切回去 |

第 3 条没有选择「直接删掉后面的内容」：那些内容可能已经聊了好几轮，为改一个错字全删掉太狠。
用树的分支能力就不用做这个取舍 —— 这也是消息树结构第二次兑现价值。

⚠️ **一个尚未解决的缺口（本轮主动暴露，未擅自扩大范围）**：
**结算回执目前只存在内存里，重启 App 后全部消失**（状态栏数值不受影响，它是持久化的）。
同一次会话内切版本已经正确。要让回执也能跨重启，有三条路：
① 不做，接受重启后消失；② 从 `state_events` 重建「变化了哪几项」的简版视图（**拿不到拦截记录和本次开销**）；
③ 新建一张回执表（**要升数据库版本 + 写迁移**）。等用户拍板。

**✅ M2.5 第 3 项交付：重新生成 / 编辑 / 删除（2026-11-02）**

这一项第一次真正用上了消息树的分支能力 —— 铁律 3 当初要求「MVP 一次做对」的那个结构，到这里开始兑现。

| 操作 | 做法 | 关键点 |
|---|---|---|
| **重新生成** | 把「聊到哪一条」退回它的上一条，重新发一次请求 | **旧回复完全没动**，仍挂在树上。新回复挂到同一个上一条下面 → 这句话就有了两个并列版本。不删除、不覆盖，只是多挂一条 |
| **切换版本** | 在同一个上一条的几个孩子之间移动 | 切过去后要顺着那条分支**走到它自己的末尾**（`latestDescendantOf`）—— 那个版本后面可能已经接着聊了好几轮 |
| **编辑** | 原地改文字，不留旧版本 | 编辑的用意是「这句话本来就该这么说」，想保留两个说法那是重新生成的事 |
| **删除** | 删这条 + 挂在它下面的全部（`descendantsOf`），然后退回上一条 | 后面的内容是接着它写的，留着就成了没有上文的碎片。状态变化记录一并删 |

| 位置 | 内容 |
|---|---|
| `MessageTree.descendantsOf()` | 取某条连同它下面长出来的全部，含自己；走过的点记下来，数据成环也不会死循环 |
| `ChatStore` + Room | 新增 `updateMessageText()` / `deleteMessages()`。删除时**先删变化记录再删消息** —— 反过来万一中断，留下的是找不到主人的记录，更难排查 |
| `ChatViewModel.refreshFromHead()` | **所有会改动消息结构的操作最后都走这一个口子**。好处是界面、状态栏、轮次编号三者永远是同一时刻算出来的 |
| `androidApp/MessageActions.kt` | 气泡下的操作行 + 编辑弹窗 + 删除二次确认。生成过程中不显示入口（那时改结构要处理一堆边界，不如先不给） |

**版本号显示**：`TranscriptEntry` 增加 `versionIndex` / `versionCount`，由 `alternativesOf()` 现算。
只有一个版本时不显示左右箭头 —— 摆着「1/1」和两个灰按钮只会让人以为功能坏了。

已生成的内容是计过费的，不能因为切存档就丢掉。

**🔴 滚动跟随第二次修复（2026-11-01）—— 上一版的修法是错的**

| 项 | 内容 |
|---|---|
| 症状 | 发完消息后 AI 回复不自动出现，仍要手动往下滑（上一轮已「修过」一次，没修好） |
| 真因 | 上一版的判断条件是「插入新行的那一刻，第 0 项还在不在视口里」。但反向布局插入新行时，**原先那条的下标会从 0 变成 1**，而视口正锚在它上面 —— 判断结果**永远是「不在底部」**，跟随再也不会触发 |
| 修法 | 把「要不要跟随」改成**只由用户拖动改写**的状态（`snapshotFlow { isScrollInProgress to firstVisibleItemIndex }`）；插入新行碰不到它。另外给我们自己触发的滚动打标记排除，否则自动滚动途中读到的中间位置会被当成「用户翻页了」 |
| 教训 | **凡是「变化发生后再去读变化前的状态」的判断都是错的** —— 要么提前快照，要么改成只由真实用户操作驱动。已记入 `AGENTS.md §8` |

设计要点已写进 **`docs/06 §11`**，四条核心结论：

- 消息存成树 —— 列表存法在「同一句话多个版本」「改掉更早一句重新来」上做不到
- 状态值 = 开局值 + 这条线上的变化按顺序加一遍 —— 覆盖式存法在「切分支」「回更早一轮」上做不到
- 快照只为快，丢了能重建；变化记录才是权威数据
- **反向撤销是错的**（中间被代码修正过就减不回去），从开局值重新加一遍才永远准确

这几个文件与 Android、数据库、网络都无关，是纯算。Room 接进来只负责存取和 SQL，这层算法一个字不用改。

| ① | **风险前置** —— M0 只用 **Python** 验过 SSE，**Ktor 的流式解析在 Kotlin 侧一次都没跑过**，是剩余不确定性最高的一块 |
| ② | **守卫还没端到端验证** —— G1~G8 只在单测里绿过，它真实的输入是「模型提议的状态」，没有真实 LLM 输出就验不了 |
| ③ | **卡解析器的正确性依赖「有东西能跑」** —— 解析出字段但不能对话，无法验证字段是否真进了 prompt；反之先有对话链路，导卡后立刻能看出来 |
| ④ | 反方理由都能低成本绕过 —— 没卡用硬编码 system prompt 顶上；没存储先在内存里跑 |

### 🔴 但不做「纯聊天 MVP」，要做垂直切片 —— 这一条有 E1 源码支撑

M0 验证的是**方案 C 双通道**（正文流式 + 独立结算请求）。若 MVP 只做正文流式，
**结算通道在 Kotlin 侧仍然是零验证**，风险只是推迟、没有消除。

而「能不能安全地分两步做」不是我拍脑袋，是 **E1-源码**给的答案（`docs/16 §12.1`）：

> 竞品把结算挂在 `MESSAGE_RECEIVED` 事件上 —— **结算发生在正文完整收到之后**，不是边流边算。

→ **正文流式通道与结算通道天然解耦、天然串行**，所以 **S1 做完再做 S2 不会返工**。
这是本轮最有价值的一条结论：它把「先做哪个」从偏好问题变成了有证据的工程排期。

### 第 11 轮：IDE Sync 的第二个坑 —— Invalid Gradle JDK configuration

命令行已全绿，但 Android Studio Sync 仍失败：`Invalid Gradle JDK configuration found`。
**纯 IDE 侧问题**（命令行用 PATH 里的 java，AS 用它自己记的那份配置）。

查到的环境事实：

| 事实 | 值 |
|---|---|
| Android Studio | 2025.1.1 Narwhal（`AI-251.25410.109`），只装了这一个 |
| `JAVA_HOME` | **空的**（命令行能跑是靠 PATH 里的 java 兜底） |
| 系统 JDK | 只有一个：`ms-17.0.15`（`~/Library/Java/JavaVirtualMachines/`） |
| AS 内置 JBR | 实测 **21.0.6** |
| `jdk.table.xml` 注册项 | `jbr-17` / `jbr-21` / `ms-17` |
| 🔴 异常 | **`jbr-17` 和 `jbr-21` 指向同一个路径**，而该路径下实际是 JDK 21 |

**推断（E3，未直接证实）**：`jbr-17` 是早年 AS 捆绑 JBR 17 时留下的陈旧条目，
路径不变但内容已换成 21 → 名实不符。项目 Gradle JDK 若指向它，AS 解析后
发现版本对不上注册信息，就报 `Invalid Gradle JDK configuration found`。
（`.idea/` 当时尚未生成，看不到项目级设置原值，故只能标 E3。）

修复（对所有可能原因都有效）：

| 改动 | 内容 |
|---|---|
| `app/.idea/gradle.xml` 🆕 | `gradleJvm = ms-17`（真实绝对路径，且**就是命令行用的那个 JDK**）+ `distributionType = DEFAULT_WRAPPED`（强制走 wrapper 的 8.9，禁止 IDE 另选） |
| `app/.idea/misc.xml` 🆕 | 工程 SDK = `ms-17`、languageLevel = JDK_17，避免「编译能过但编辑器满屏飘红」 |
| `app/shared/build.gradle.kts` | 🔴 新增 `jvmToolchain(17)` —— 见下 |

> `.idea/` 已被 `.gitignore` 排除，属本机配置，不入库。

**为什么选 `ms-17` 而不是 AS 内置的 `jbr-21`**：不只是「能用就行」。我们这两轮栽的
都是「命令行过、IDE 不过」，让两边用同一个 JDK 能直接消灭这一整类分歧，
顺带共用一个 Gradle daemon（省一份内存）。

**顺带补掉的真实缺陷：`jvm()` 目标没钉编译 JDK**

`:shared` 里 `androidTarget` 显式写了 `jvmTarget = 17`、`android{}` 也写了 17，
**唯独 `jvm()` 这个 target 没有任何约束** —— 它跟着「当前跑 Gradle 的那个 JDK」走：
命令行（PATH 里是 JDK 17）编译成字节码 17，而 Android Studio（Gradle JDK 若是
JBR 21）会编译成字节码 21。产物不一致会让构建缓存反复失效，更糟的是会制造
「命令行测试全绿、IDE 里却报错」这种最难查的问题。

`jvmToolchain(17)` 把「用哪个 JDK **编译**」和「用哪个 JDK **跑 Gradle**」彻底解耦。

> 📌 教训：**多 target 的 KMP 模块，每个 target 的 jvmTarget 都要显式钉死，
> 或者直接上 toolchain。漏一个就会产生跟随环境漂移的产物。**
