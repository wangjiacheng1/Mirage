## 1. 上下文结构(最终发给模型的 messages)

> 🔴 **v1.1 已按 `V-1` 实测结论重写(E1,`docs/15 §1`)。**
> 旧版把所有 Block 都放在 `system` 位,**是错的** —— 实测的 `dsh-tavern` 只把"整局不变"的内容放 system,
> **把全部可变指令放在最后一条 `user` 消息**。下表为定稿版。

```
── 稳定前缀(整局一字不改,吃满 Prompt 前缀缓存)──────────────────
messages[0]   role=system     ← 【Block: 行文规范】+【Block: 角色设定】+【Block: 用户人格】
                                 +【Block: 变量目录】(只有路径+类型,没有值!见 §1.2)
messages[1]   role=user       ← 【约定轨迹 1/3】"我们正在共同创作一部持续发展的沉浸式虚构小说…"
messages[2]   role=assistant  ← 【约定轨迹 2/3】"明白。后续我会把人物卡…只输出小说正文。"
messages[3]   role=user       ← 【约定轨迹 3/3】"开始。请从角色卡给定的开场继续。"
messages[4]   role=assistant  ← 【开场白】角色卡 first_mes + <initvar>{…}</initvar>(仅首轮)
── 每轮循环一组(按真实发生顺序追加)───────────────────────────
messages[5]   role=user       ← 玩家原话
messages[6]   role=user       ← 【Block: 世界书】本轮命中条目(条件注入,可缺省)
messages[7]   role=user       ← 【Block: 上一轮变量变化】**只给 delta**,不给全量(见 §1.3)
messages[8]   role=assistant  ← 模型正文(零数值)
…
── 队尾指令帧(每轮重建,永远是最后一条)────────────────────────
messages[n]   role=user       ← 【前台指令帧 foreground-frame】= 4 段拼接:
                                 ① 行文规范(本轮生效的硬约束)
                                 ② 【现场 · 主要人物状态】自然语言姿态快照(§2.8)
                                 ③ 【附加要求】角色卡自带玩法要求 + 临时导演指令
                                 ④ 【状态协议禁令】"变量更新由后台结算,正文不要输出任何变量块"
```

### 1.1 为什么指令要放队尾而不是 system(E1)

| 原因 | 说明 |
|---|---|
| **近因效应** | 长会话里 system 位的约束会被后面几万 token 稀释;队尾紧贴生成位置,最难被忽略 |
| **前缀缓存** | system 位必须是"整局不变"的内容。把每轮都变的行文规范/姿态塞进 system 会让**整段缓存失效**(`docs/14 §2.2` 实测 DeepSeek 返回 `prompt_cache_hit_tokens`) |
| **实测佐证** | `dsh-tavern` 第 8 轮的 `messages[27]`(最后一条,`role=user`)才是真正的指令帧,`sectionKind` 分别为 `base`/`posture`/`card-instruction` + 一段 `stage:mvu-background-owner` 的禁令 |

### 1.2 变量目录 ≠ 变量值(E1,关键)

system 位只放**路径与类型索引**,并明确告诉模型"这不是当前值":

```json
[{"path":"/地牢/难度","type":"string"},{"path":"/冒险者/生命","type":"number"},
 {"path":"/物品栏/材料","type":"array"}]
```

> 原文提示语:"以下是初始化后的一次性变量路径与类型索引,**不代表当前值,也可能未列全**。
> 数组仅列容器。需要最新值或更多路径时,调用 `tavern_read_variables` 的 list/search/read。"

**好处:**状态表长到几百个字段也不会撑爆稳定前缀,也不会每轮把全量状态重发一遍。
**代价:**需要提供一个只读查询工具(我们的对应物见 `docs/02` 工具清单)。

### 1.3 状态回灌只给 delta(E1)

实测格式 —— `role=user`,JSON Pointer + `=` + JSON 字面量,一行一条:

```text
【上一轮变量变化】上一轮结算后发生变化的变量及最新值(路径相对于 stat_data),其余变量未变。写本轮正文时以此为准。
/地牢/难度 = "简单"
/地牢/总轮数 = 8
/地牢/当前轮 = 1
/敌人/名称 = "湿皮盲兽 ×3"
/敌人/生命 = 30
```

另一轮只变了一个字段时,就真的只发一行:`/冒险者/生命 = 58`。

✅ 我们照抄这个格式。比嵌套 JSON **省 token**,且模型更难读错层级。

**注意事项:**

- 多条 system 消息并非所有模型都支持 → 适配器可按 `ProviderCapabilities` 合并为一条。
- **示例对话必须明确标记为"示例"**,否则模型会把它当成真实发生过的事。推荐在前面加一条 `system: [以下是展示说话风格的示例,并非真实发生的对话]`,后面加 `system: [示例结束,以下是真实对话]`。
- ~~最后一条 system(人设复述)放在历史之后,利用"近因效应"对抗漂移。~~ → **已被 §1.1 取代**:不是"再加一条 system",而是**把全部可变指令合并成队尾的一条 user**。
- ⭐ **装配顺序要对前缀缓存友好(`docs/14 §2.2`,E1)。** DeepSeek 实测返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`,说明它做了 **Prompt 前缀缓存**:**只要请求的前缀逐字节不变,这部分就能命中缓存、大幅降价**。
  因此装配必须是 **[稳定前缀] + [易变尾部]**:
  - **稳定前缀**(整段会话内尽量一字不改):行文规范 → 角色设定 → 用户人格 → 示例对话
  - **易变尾部**:世界书(每轮命中项会变)→ 长期记忆 → 近期历史 → **权威状态** → 人设复述 → 本轮输入

  > 💡 **幸运的是这与"近因效应"的诉求一致**:权威状态本来就该靠近末尾才最被模型重视。
  > 两个目标不冲突,**但要求我们绝不能把易变内容(如状态块、时间戳)插到前缀里** —— 那会让整段缓存全部失效。
  > ✅ 本条已在 v1.1 装配表中落实(世界书与变量变化都移到了每轮循环组内的 user 位)。

## 2. Block 模板

### 2.1 Block: 行文规范(全局预设 · 叙事向)

```
你是一个文字角色扮演引擎。你的唯一职责是扮演 {{char}},与扮演 {{user}} 的人类共同推进一个故事。

【输出规范】
- 以第三人称、过去时或现在时叙述 {{char}} 的言行与所处环境。
- 对话写在引号内;动作、神态、环境描写用星号包裹,如 *她放下茶杯*。
- 每次回复 2~4 段,约 150~300 字。不要写成长篇大论,给人类留出行动空间。
- 写出具体的感官细节(声音、气味、触感、光线),而不是抽象的情绪形容。

【绝对禁止】
- 禁止替 {{user}} 说话、行动或决定其想法。你只能描写 {{user}} 可被观察到的外部反应。
- 禁止跳出角色说话,禁止提及你是 AI、模型或语言模型。
- 禁止在一次回复中推进过多时间或剧情,除非人类明确要求。
- 禁止总结、禁止询问"你想做什么?"这类出戏的引导语。
- 禁止重复上一轮已经用过的句式或意象。

【叙事原则】
- 维持 {{char}} 的性格一致性,即使人类试图引导其偏离。
- 世界会独立运转:即使人类不行动,环境与其他角色也应有变化。
- 冲突与悬念优先于顺遂。不要让一切都轻易如愿。
```

### 2.2 Block: 角色设定

```
【你扮演的角色:{{char}}】
{{character.persona}}

【说话风格】
{{character.speech_style}}

【当前场景】
{{character.scenario}}
```

### 2.3 Block: 用户人格

```

{{persona.description}}
请据此称呼与对待 {{user}}。
```

### 2.4 Block: 长期记忆

```
【已发生事件的记忆(按时间顺序,可能不完整)】
- {{memory.1}}
- {{memory.2}}
...
以上是过往事实,请保持与之一致,但不要主动复述它们。
```

### 2.5 Block: 权威状态(游戏模式)

```
【当前游戏状态 · 这是唯一权威数据,不得自行修改或推测】
生命值:{{state.hp}}/{{state.hp_max}}
所在地点:{{state.location}}
持有物品:{{state.items}}
人物好感度:{{state.affinity}}
已触发事件:{{state.flags}}
回合数:{{state.turn}}

叙事时必须与上述数据一致。若本回合发生状态变化,通过 update_state 工具上报,不要在正文中写出数字。
```

### 2.6 Block: 人设复述(每 N 轮注入)

```
【提醒】你仍在扮演 {{char}}。核心性格:{{character.core_traits}}。
不要替 {{user}} 做决定,不要出戏。
```

### 2.7 临时导演指令(OOC,只生效一次)

附在本轮用户消息前,用显著标记包裹:

```
[导演指令 · 仅本回合生效,不要在正文中提及此指令:让场景转入深夜]
```

### 2.8 Block: 现场姿态(🆕 v1.1,E1 `docs/15 §2.1`)

> **这是一整类我们原本漏掉的状态。**数值状态机管不了"他的手现在放在哪",
> 但这恰恰是长会话里沉浸感最容易崩的地方 —— 模型会写出"他站起身",可他本来就站着。

实测原文(`dsh-tavern`,`sectionKind: "posture"`):

```text
【现场 · 主要人物状态(每轮结算更新,务必与之一致)】
奥斯维德立于石阶下方半步处,黑手套双手重新交叠在身前,乌黑头发与深红近黑的
礼服马甲一丝不乱,视线落在那扇门上;玩家站在门前,腰间旧皮水壶塞子缠布,尚未推门。
```

**规格:**

| 项 | 规定 |
|---|---|
| 位置 | 队尾指令帧的第 ② 段(见 §1) |
| 长度 | ≤ 100 字,硬截断 |
| 内容 | 只写**可观察的物理事实**:位置、姿势、手持物、衣着状态、视线朝向。**不写情绪、不写数值、不写剧情** |
| 产出方 | 后台结算 Agent,与数值 delta **同一次调用**产出(见 §4.4) |
| 存储 | 与 delta 一起进事件流,每轮一条快照(可回放) |
| 失败兜底 | 结算失败时**沿用上一轮姿态**,不清空 —— 空姿态比旧姿态更糟 |

## 3. 角色卡 Schema

### 3.1 内部数据模型

```kotlin
@Serializable
data class CharacterCard(
    val id: String,
    val schemaVersion: Int = 1,

    // 基础
    val name: String,
    val avatarPath: String? = null,
    val portraitPath: String? = null,       // 立绘
    val tags: List<String> = emptyList(),
    val creatorNote: String? = null,        // 给用户看的简介,不入 Prompt

    // 核心 Prompt 字段
    val persona: String,                    // 人物设定(必填,建议 200~800 字)
    val speechStyle: String? = null,        // 说话风格
    val scenario: String? = null,           // 开场场景
    val greetings: List<String> = emptyList(),      // 开场白,可多条备选
    val exampleDialogues: List<DialogueExample> = emptyList(),  // 强烈建议 ≥3 组

    // 高级
    val systemPromptOverride: String? = null,   // 覆盖全局行文规范
    val postHistoryInstruction: String? = null, // 注入在历史之后的强约束
    val lorebookIds: List<String> = emptyList(),

    // 游戏规则(E 模块)
    val stateSchema: List<StateFieldDef> = emptyList(),
    val endingConditions: List<EndingCondition> = emptyList(),

    // 元信息
    val createdAt: Long,
    val updatedAt: Long,
    val source: CardSource,   // MANUAL / IMPORTED_ST_V2 / BUILTIN
)

@Serializable
data class DialogueExample(val userSays: String, val charSays: String)

@Serializable
data class StateFieldDef(
    val key: String,              // "hp"
    val label: String,            // "生命值"
    val type: FieldType,          // INT / FLOAT / BOOL / ENUM / STRING / LIST / MAP
    val initial: JsonElement,
    val min: Double? = null,
    val max: Double? = null,
    val enumValues: List<String>? = null,
    val whitelist: List<String>? = null,  // LIST 类型的合法元素,null = 允许自由值
    val showInHud: Boolean = true,
    val hudStyle: HudStyle = HudStyle.TEXT,  // BAR / TEXT / CHIP / COUNTER
)
```

| 检查 | 提示 |

## 4. 状态输出协议(游戏模式)

> 🔴 **v1.1 已按 `V-1` 实测定稿。本节结构变了,请整节重读。**
> 旧版叫"双通道协议",在"正文内标签(A)"与"Tool Calling(B)"之间摇摆。
> 实测证据(`docs/15 §3`)表明一线厂商选了**第三条路**,并明文禁掉了 A。

### 4.0 🔴 决策:生成走 C,解析认 A

**主方案 = C · 后台独立结算。** 一句话:**我们生成时永远走 C;解析时必须认得 A。**

| | A · 正文内标签 | B · 原生 Tool Calling | **C · 后台独立结算** |
|---|---|---|---|
| 形态 | `<UpdateVariable>{…}</UpdateVariable>` | 同一次请求,`tool_calls` 与正文同流 | 正文完成后**第二次请求**只产出 delta |
| 证据 | ~~E2~~ → **E3**(已证伪) | **E1**(`docs/14 §11`)+ **E1**(真 ST 结算器用工具提交) | **E1 ×2 互证**(`dsh-tavern` + 真 SillyTavern) |
| 流式正文纯净 | ❌ 要写"吞噬模式"状态机,标记会跨 chunk 切分 | ⚠️ 较好 | ✅ **完美,正文零污染** |
| 模型兼容 | ✅ 全部 | ❌ 需支持 tools(实测 394/465 = 85%) | ✅ **全部** |
| 请求数 | 1 | 1 | **2**(第二次可用廉价模型 + 短上下文) |
| 失败隔离 | ❌ JSON 坏了可能连正文一起崩 | ⚠️ 中 | ✅ **完全隔离** |
| 可重试 | ❌ 要重跑整轮叙事(3~20s + 全额 token) | ❌ 同左 | ✅ **只重跑结算** |
| `max_tokens` | ❌ 与正文共用预算(`docs/14 §4`) | ❌ 同左 | ✅ **结构化输出,可安全设 512** |
| 竞态 | 无 | 无 | ❌ **有**,需结算三态(见 §4.5) |

**采用 C 的决定性理由:它把 `max_tokens` 的两难解开了。**
`docs/14 §4` 实测 `max_tokens` 是"思考 + 正文"共用预算,设小了正文被截断(`finish_reason=length`),不设又没有成本上限。
走 C 之后:**叙事调用不设上限**(保证故事完整),**结算调用设 512 + 关思考**(输出是结构化 JSON,512 足够)。
这是全项目唯一可以安全设上限的调用。

**必须接受的三个代价(不许假装没有):**

1. 🔴 **每轮 2 次调用。** 缓解:结算用**廉价模型 + 短上下文**(只要"上一轮状态 + 本轮正文 + 规则",不要全部历史)。
   → 设置项:允许用户为"结算"单独指定模型。**这正好是 BYOK 的优势,ChatterUI 单模型、DZMM 不给选,都做不到。**
2. 🔴 **状态栏有竞态。** 结算未回时状态栏必须显示"结算中…",**不许显示旧值假装是新值**(见 §4.5)。
3. 🔴 **结算调用同样被"中断不省钱"命中**(`docs/14 §13`,E1):用户退出页面 ≠ 结算不计费。→ 结算**必须**设 `max_tokens`。

### 4.1 ⬇️ 路径 A · 正文内标签(降级为「只解析,不生成」)

**我们不再用 A 生成。**但解析器必须能从正文里识别并**剥离**以下三种,用于导入酒馆生态角色卡与存档:

| 标签 | 来源 | 处理 |
|---|---|---|
| `<initvar>{…}</initvar>` | **E1** `dsh-tavern` 开场白实测 | 解析为**初始状态**;`$meta.strictSet=true` 映射为"禁止新建未声明路径" |
| `<UpdateVariable>{…}</UpdateVariable>` | ~~E2~~ → **E3**(`docs/15 §7.0` 已证伪:真 ST 卡里 0 次) | 仍解析(或有旧版存档),但**不得作为「兼容 SillyTavern」的对外口径** |
| `mvu_submit_update` 工具 + `operations[]` | **E1**(`docs/15 §7.1` 真 ST 实证) | ⭐ **这才是 SillyTavern + MVU 的真实协议** → 我们的结算调用与之同构 |
| ```` ```state {…} ``` ```` | 我们自己的原设计 | 保留解析,不再生成 |

实测的 `<initvar>` 原文结构(注意 `$meta` 与中文键):

```json
{
  "$meta": {"strictSet": true},
  "地牢": {"难度": "待选", "总轮数": 0, "当前轮": 0, "本轮房间": "门厅", "是否最终轮": false},
  "冒险者": {"姓名": "无名氏", "等级": 1, "经验": 0, "生命": 60, "生命上限": 60, "攻击": 10},
  "水壶": {"当前": 5, "上限": 5, "每口恢复": 12},
  "物品栏": {"材料": [], "消耗品": []}
}
```

### 4.4 结算调用的设计(C 的具体实现,我们自己设计)

> `dsh-tavern` 的后台结算请求**不在**导出的 JSON 里(导出的是 `foreground:` 帧),
> 所以这一段**没有竞品证据,是我们自己的设计(E3)**,需要在 M0 Step 4 实测验证。

```
结算请求(第二次调用,与叙事调用完全独立)
├─ system: 【结算规则】+【变量目录:路径 + 类型 + 约束(min/max/枚举)】   ← 稳定前缀,可缓存
├─ user:   【当前权威状态】全量,来自客户端状态机(不是模型自述!)
├─ user:   【本轮玩家输入】
├─ user:   【本轮正文】刚刚生成的那一段
└─ user:   【输出要求】只输出一个 JSON,不要解释:
             {"delta": {"/冒险者/生命": 48, "/物品栏/材料": [{"name":"锈铁片","count":1}]},
              "posture": "≤100字的现场姿态",
              "reason":  "一句话说明依据,用于调试"}
             + 明确声明:delta 的值是该路径结算后的【新值(绝对值)】,不是增量。
               例「生命从 60 掉到 48,写 48,不要写 -12」。本轮未变的路径不要出现。

参数: max_tokens=512 · 关思考 · temperature=0.2 · 可指定廉价模型 · 不流式
```

**要点:**

| 项 | 规定 | 理由 |
|---|---|---|
| `delta` 用 JSON Pointer 键 | `"/冒险者/生命": 48` | 抄 `dsh-tavern` 寻址方式,允许中文键(对中文模型更友好) |
| 🔴 **`delta` 的值是「绝对新值」,不是增量** | 见 §4.4.2 | 幂等、不累积漂移、模型不用做算术、与真 ST 回灌格式一致 |
| 根命名空间 | 建议沿用 `stat_data` | 为将来与酒馆生态互通留口 |
| 权威状态由**客户端**提供 | 绝不让模型"回忆"当前值 | 铁律 2 |
| 不流式 | 结构化输出无需流式,且避免半个 JSON 进状态机 | |
| 失败 | 重试 1 次 → 仍失败则标记"结算失败",**保留正文**,姿态沿用上一轮,提供手动重结算按钮 | 代价 2 |

#### 4.4.2 🔴 `delta` 的语义:**绝对新值**,不是增量(本节修正了本文档自己的一处矛盾)

**先认错。** 本节上方的输出示例,在 v1.1 里曾经写成:

```json
{"delta": {"/冒险者/生命": -12, "/物品栏/材料": ["锈铁片"]}}
```

这里 `-12` 是**增量**,而 `["锈铁片"]` 是**新值** —— 同一个对象里混了两种语义,**是我写文档时的疏忽**。
如果照着实现,客户端根本无法判断某个键该加还是该覆盖。已在上方改正。

**定稿:一律用绝对新值。** 四条理由:

| # | 理由 | 说明 |
|---|---|---|
| 1 | **幂等** | 同一个 delta 重放两次结果一样。这对 §4.7 的「编辑楼层 → 截断重放」(`A-18`)是刚需 —— 增量语义下重放一次就多扣一次血 |
| 2 | **不累积漂移** | DZMM 实测的「**只增不减**」(`docs/11 §8.2`,E1)本质就是增量累加失配。绝对值从结构上消灭这类 bug |
| 3 | **模型不用做算术** | 结算器只需要「读正文 + 读快照 → 把新值抄出来」。让 LLM 做 `60 - 19 = 41` 是在给它送分题的同时送错题 |
| 4 | **与真 ST 的回灌格式一致** | `docs/15 §1.3` 实测的回灌格式就是 `/冒险者/生命 = 58`(绝对值)。两边同构,导入导出互通更省事 |

**代价:** 客户端自己算展示用的变化量(`58 → 41` 显示 `−17`)。这正好符合铁律 2「数值交给代码」。

**校验侧的额外收获:** 一旦声明了「必须写绝对新值」,就多出一个**廉价的语义错误探测器** ——
非负字段(生命/金币/经验/轮次…)出现**负数**,几乎必然是模型偷偷写成了增量。
已实现为 `m0_dualchannel.py` 的 `LOOKS_LIKE_INCREMENT` 违规码。

> ⏳ **待 M0 实测确认(D7)。** `tools/m0_dualchannel.py` 的 **D7** 用同一批正文、同一批输入快照,
> 只把输出要求从「绝对新值」换成「增量」,对比两者的可解析率 / 断言通过率 / 违规数。
> 若实测反过来(增量更准),以实测为准 —— 但上面 4 条理由里的第 1 条(幂等)仍然会逼我们在落库时转成绝对值。

#### 4.4.1 🔽 结算 Prompt 的四条约束(E1,`docs/15 §7.1` 真 SillyTavern 原文)

> 🔴🔴 **2026-10-19 第八轮降级:从「硬约束」改为「软引导」。标题里原来的「必须抄进」已撤销。**
>
> **实测打脸**(`out4/REPORT4.md §4.2`,D5 对照组):
> **把下面第 1 条和第 4 条删掉之后,断言通过率反而从 85% 升到 97%。**
> 同一份报告里,严规则组的第 4 轮**照样**凭空产出 `/地牢/当前轮: 2→3`(玩家什么都没做)。
>
> **这与我原先的预设相反,必须老实写下来。** 可能的解释:
> **严约束在压抑模型的合理推断** —— 它不敢写有依据的变化,于是漏报。
> 唯一反向证据:**松规则组出现了 2 次 `ILLEGAL_ENUM`**(写了枚举外的"战斗"/"石阶"),严规则组 0 次。
>
> → **处置**:四条**保留**(它们确实降低了枚举越界),但**不得作为正确性的依据**。
> 正确性由 `ADR-012` 的 **G1~G8 代码层守卫**负责(§4.6)。
> **样本量提示**:D5 只有 4 轮,这是**倾向不是定论**,M1 需用 `m0_eval.py` 扩样本复核。



| # | 原文 | 为什么重要 |
|---|---|---|
| 1 | **「最高优先级:正文优先。最新一版正文(包括用户编辑过的更早楼层)是唯一事实来源。若正文与变量快照冲突,以正文为准。」** | 解决"模型写了受伤但 delta 没扣血"的不一致。→ 同时逼出 `A-18` 截断重放(§4.7) |
| 2 | **「你是这场游戏的结算器。」** | 结算是**独立人格**,不是叙事角色的延续。不要让它沾染角色语气 |
| 3 | **「数值写成数字,不要写「+3」这类字符串。」** | 一看就是被模型坑过才加的。我们必须照抄 |
| 4 | **「不要提交正文没有依据的变化。每一项变化都要能对应到正文里的一个具体事件。」** | 对抗结算器**自己编数值**。配合 `reason` 字段可人工抽查 |

> ⚠️ **一条我们不抄的**:真 ST 的物品栏用 `"铁片 ×3"` 这种**字符串内嵌数量**,并要求模型"合并同项"。
> 这是坏设计(结构化数据塞进字符串,解析和校验都难)。
> → 我们用 `[{"name":"铁片","count":3}]`,**合并由客户端做,不交给模型**(铁律 2)。

### 4.7 🆕 编辑楼层后重新结算(截断重放,`A-18`)

> 🔴 **2026-10-19 硬性补充(E1,`docs/15 §7.9`)**:竞品 tavern 客户端把
> **`重新生成正文`** 与 **`重新结算变量`** 做成了**两个彼此独立的按钮**。
> → ① 这是**方案 C(双通道)在真实产品交互层的 E1 旁证**,`ADR-010` 据此加强;
> ② 我们**不许把它们合并成一个「重试」** —— 用户经常是「正文满意、只是数值算错了」,
> 合并会逼他把满意的正文一起重掷,等于惩罚用户(且 E1 硬约束 ⑩:重掷不省钱,是真金白银);
> ③ 因此**结算必须是可独立重放的纯函数**:
> `(权威状态快照, 本轮玩家输入, 本轮正文) -> delta`,正文不变时重算应得到同样结果。

真 SillyTavern 的结算规则把"用户编辑过更早楼层"列为**最高优先级**场景(`docs/15 §7.4`),
这要求一条我们原本没设计的链路:

```
用户编辑第 N 层正文
      ↓
作废事件流中 eventId > N 的全部 delta(不删除,标记 superseded —— 事件流只追加)
      ↓
从第 N 层开始重新结算(可批量,也可只重算 N 层然后让用户决定是否往下重放)
      ↓
重放期间状态栏进入 `replaying` 态(§4.5 第五态)
      ↓
重放完成 → 新 delta 追加 → 状态栏回到 done
```

✅ **我们选的「事件流 delta 累加」架构(铁律 3)天生支持这件事。**
❌ 若当初选了"直接存当前状态快照",这个功能做不了 → **铁律 3 的价值再次被证实。**

### 4.5 结算三态(UI 契约)

| 态 | 触发 | 状态栏表现 |
|---|---|---|
| `pending` | 正文已完成,结算请求未发出 | 数值灰显 + "待结算" |
| `running` | 结算请求在途 | 数值灰显 + 转圈 + "结算中…" |
| `done` | delta 已落库并通过校验 | 数值正常 + 变化量做 +N/−N 动画 |
| `failed` | 重试后仍失败 | 数值显示**上一轮**值 + 红点 + "结算失败,点击重试" |
| `replaying` 🆕 | 用户编辑了历史楼层,正在截断重放(§4.7) | 数值灰显 + 进度"重算第 N/M 轮" |

🔴 **硬性要求:`pending`/`running` 时绝不能把旧值当新值正常显示。**
实测 `dsh-tavern` 甚至把这件事告诉了模型 —— 它的只读工具描述里写着:
"`settlement` 表示当前结算状态,`pending`/`running`/`waiting-runtime` 时结果可能仍为上一轮已保存值。"
→ 我们的只读工具也要带这个字段(`docs/15 §2` F10)。

| 🆕 数值字段收到 `"+3"` 这类**字符串** | 尽力转换 + 记录 `STRING_NUMBER`。真 ST 明令禁止这件事(§4.4.1 第 3 条),说明它被坑过 |

|---|---|---|
| 替用户说话/行动 | 模型的"助手本能"要推进对话 | 行文规范中明确禁止 + 示例对话里演示"只描写对方外部反应" |
| 出戏说"作为 AI..." | 触发安全对齐 | 换模型或换服务商;降低描述的触发性;不要在 Prompt 里强调"不要说你是 AI"过多次(反而提示它) |
| 复读上一轮句式 | `presence_penalty`/`frequency_penalty` 不足;温度过低 | 提高 penalty 到 0.3~0.6;温度 0.85~1.0;行文规范中显式禁止重复意象 |
| 回复越来越长/越来越短 | 无长度锚点 | 规范中给明确字数;示例对话的长度就是最强锚点 |
| 忘记早期设定 | 上下文被挤出 | 记忆压缩(M3)+ 关键信息置顶 + 周期性复述 |
| 人设逐渐趋同为"温柔助手" | 长对话中 persona 权重被稀释 | 人设复述块放在历史之后 + 示例对话常驻不裁剪 |
| 过度顺从,毫无冲突 | 对齐训练导致 | 规范中强调"冲突与悬念优先于顺遂";persona 中写明角色的反对意见与底线 |
| 自己编造数值 | 未注入权威状态或注入位置太靠前 | 权威状态块紧贴历史之前 + 规范中禁止正文写数字 |
| 一回合推进几天剧情 | 无节奏约束 | 规范中限制时间推进;明确"除非人类要求" |
| 中英混杂 | 模型语言倾向 | 规范中指定语言;示例对话全用目标语言 |

## 6. 采样参数预设

| 预设 | temperature | top_p | presence_penalty | frequency_penalty | 适用 |
|---|---|---|---|---|---|
| **稳定** | 0.7 | 0.9 | 0.2 | 0.2 | 长对话、游戏模式(需要数值可靠) |
| **平衡**(默认) | 0.9 | 0.95 | 0.4 | 0.3 | 日常角色扮演 |
| **狂放** | 1.1 | 1.0 | 0.6 | 0.4 | 创意叙事、意外转折 |

### 6.1 🔴 `max_tokens`(本节已被实测推翻并重写,见 `docs/14 §4`)

> **原方案"默认 800,可调 300~2000"是错的,必须废弃。**
> `docs/14` 实测:`max_tokens: 1024` 下 **6 次请求 4 次 `finish_reason=length`**,
> 其中一次 reasoning 消耗 1447 token、`content` 直接为 `null`——用户一个字没看到,却全额计费。
> **`max_tokens` 是"模型思考 + 正文"共用的总预算,不是正文预算。**

| 规则 | 新方案 |
|---|---|
| 默认值 | **不下发 `max_tokens`**,使用平台默认上限 |
| 用户可调范围 | **下限 2048**(不再允许 300~800 这种会直接废掉回复的值) |
| UI 文案 | 必须写明"**此额度包含模型思考消耗,设低会导致 AI 不说话**" |
| 角色扮演默认 | **关闭思维链**(DeepSeek `thinking:{"type":"disabled"}` / OpenRouter `reasoning:{"enabled":false}`)。叙事不需要 CoT,它只会抢预算、加延迟、涨成本(实测占输出 token 的 68%~99%) |
| 截断处理 | `finish_reason == length` **必须显式提示**,并提供「继续生成」。详见 `docs/02 §5.1.2` |

> 注意:部分服务商不支持 `presence_penalty`/`frequency_penalty`,适配器需按 Capabilities 剔除,否则会 400。

#### 6.1.1 🔴 第二轮实测:`V-8` 关闭,"关思考"从建议升为**强制**(E1,`docs/14 §10.3`)

> 原先"关思考省钱"只是 **E2**(推断)。2026-10-16 第二轮探针实测后**升级为 E1**,
> 而且真实数字比预想严重得多 —— 关键不是"开 vs 关差 45%",而是:

| 对照 | `reasoning_tokens` | `cost` | 结论 |
|---|---|---|---|
| **不传思考参数(默认)** | **891**(占输出 **87%**) | **$0.003119** | 🔴 最贵 |
| 显式 `reasoning:{enabled:true}` | 24 | $0.000747 | —— |
| 显式 `reasoning:{enabled:false}` | **0** | **$0.000411** | ✅ 最省 |

**→ `reasoning:{enabled:false}` 是真关闭(不是"不返回但照样计费");"不传"是最贵的选项,贵 7.6 倍。**
(被测:OpenRouter `z-ai/glm-5.1`,同一 prompt「写约 150 字·雨中废弃车站」)

**三条连带修订:**

1. **参数名两家完全不同,不存在通用写法**;且 **DeepSeek 的思考不是布尔开关而是 `effort` 三档
   (`low`/`high`/`max`,`/models` 声明默认 **`high`**)** → 控成本在 DS 侧应考虑 `effort:"low"`。
   完整映射表见 `docs/14 §10.7`,实现约束见 `docs/02 §5.1.1`。
2. **开思考时平台会往 prompt 侧注入内容**:DS `prompt_tokens` 17 → **43**(+26),OR 17 → 24(+7)。
   → ① token 预算估算要留 buffer;② **同一会话内不要来回切思考开关**,否则前缀缓存永不命中
   (DS 的 `prompt_cache_hit_tokens` 可用来观测)。
3. **"我测了一个模型没事"不能推广到别的模型。** 同样 `max_tokens=256` + 开思考:
   `deepseek-flash` 思考 40 token → 正常出 189 字正文;`z-ai/glm-5.1` 思考 **255** token → **正文空、`finish_reason=length`、照样计费**。
   跨模型思考长度差两个数量级,而**我们管不了用户选什么模型** → `A-13` 不可省,`max_tokens` 默认不传的铁律不可放宽。

#### 6.1.1b 🔴 第三轮更正:**两家都默认开思考**,且 `effort` 三档无效(E1,`docs/14 §12.4`/`§12.5`)

> **上面 §6.1.1 第 1 条里「DS 侧应考虑 `effort:"low"` 控成本」这个建议,以及
> `docs/14 §10.7` 里「把思考档位做成三档 UI」的建议,本轮都被实测否决。原文保留以备溯源。**

**更正一:DeepSeek 不传思考参数时,也默认在思考。**

| 场景 | prompt | 有 `reasoning_content` | reasoning_tokens | completion |
|---|---|---|---|---|
| 「只回复两个字:收到」 | 35 | ✅ 有 | **30** | 32 |
| 短叙事 | 43 | ✅ 有 | 19 | 92 |
| 鸡兔同笼 | 59 | ✅ 有 | **72** | 81 |

上一轮据单次响应记录的「DS 默认不思考」**是错的**(`docs/14 §12.4` 有完整更正声明)。

**→ R6 升级(写进 `docs/02 §5.1.2`):「必须显式下发关思考参数」对*每一个* Provider 成立,
不是 OpenRouter 的特例。新接入一个 Provider 时,「默认是否思考 + 关闭参数写法」列入接入检查单。**

**对我们尤其致命的一点:短回合成本翻倍。**
「只回复两个字」花了 30 reasoning + 32 completion → **用户看不见的部分和看得见的部分一样多**。
角色扮演场景里「嗯」「好的」「继续」这类短回合占比很高,这不是边缘情况。

**更正二:`effort` 三档不是有效的成本旋钮 → 不做「思考深度」UI。**

| effort | reasoning_tokens | completion | 耗时 |
|---|---|---|---|
| `low` | **90** | 99 | 1.3s |
| `high` | **64** | 77 | 0.8s |
| `max` | **76** | 85 | 1.1s |

三档全部 HTTP 200(参数被接受),但 `reasoning_tokens` **无递增趋势,`low` 反而最高**。
→ **做成 UI 等于给用户一个假旋钮。只保留 on/off 二元开关,默认 off。**
⚠️ 保留意见:样本仅 1 次/档且用的是 flash 小模型,降级为 `V-22`(待大样本复测,低优先级),**不彻底否决**。

## 7. Prompt 版本管理与回归

1. 每个内置预设有 `promptVersion`(如 `narrative-p1.3`)。
2. 修改 Prompt → 版本 +1 → 必须在 `docs/08` 评测集上跑一遍回归 → 记录通过率变化。
3. 用户修改过的预设在升级时 **不覆盖**,而是提示"有新版本官方预设,是否查看差异"。
4. 预设以 JSON 文件形式放在 `:shared` 的资源目录(`presets/*.json`,保证跨平台可读),支持用户导入导出,官方可通过 GitHub Release 分发更新包(无服务端下的"热更新"替代方案)。
