# 06 · 数据模型与存储设计

| 项 | 值 |
|---|---|
| 文档版本 | v1.1(KMP 修订) |
| 存储 | **Room 2.7+ KMP**(SQLite) + DataStore(KMP) + 平台加密存储 |
| 备选 | 若 Room KMP 验证关卡不过,切 SQLDelight(`docs/02` ADR-007) |

> ⚠️ **本文中标注 🔒 的设计必须在 MVP(M1/M2)一次做对**,后期迁移代价极高。
>
> **KMP 适配要点**(v1.1 新增):
> 1. 本文的建表 SQL 与实体设计 **与平台无关**,Room KMP 与 SQLDelight 两条路都适用。
> 2. `api_key_cipher` 的加解密 **不在 DB 层做**,由 `SecureKeyStore`(expect/actual)负责;DB 只存密文字节。
> 3. 文件路径与 IO 统一用 **okio**,不要在共享层出现 `java.io.File`。
> 4. Room 的 **FTS4 虚表在 KMP 下需验证**(见 `docs/04` 任务 1.6 的验证关卡);若不支持,降级为 `LIKE` 查询 + 内存过滤(角色数量通常 < 500,完全够用)。
> 5. 时间戳统一用 `kotlinx-datetime` 的 epoch millis(`Long`),不用 `java.util.Date`。
> 6. UUID 生成用 `kotlin.uuid.Uuid`(Kotlin 2.0+ 实验 API)或自写 expect/actual,不要用 `java.util.UUID`。

## 2. 核心表设计

### 2.1 `messages` 🔒 对话树

```sql
CREATE TABLE messages (
    id              TEXT PRIMARY KEY,          -- UUID
    session_id      TEXT NOT NULL,
    parent_id       TEXT,                      -- 🔒 NULL = 根节点
    role            TEXT NOT NULL,             -- user / assistant / system / narration
    content         TEXT NOT NULL,
    created_at      INTEGER NOT NULL,
    updated_at      INTEGER NOT NULL,

    -- 分支控制
    is_active_child INTEGER NOT NULL DEFAULT 1, -- 同 parent 下仅一个为 1
    sibling_index   INTEGER NOT NULL DEFAULT 0, -- Swipe 的 1/3 显示

    -- 元信息(用于调试、统计、回滚)
    model_id        TEXT,                      -- 生成时使用的模型快照
    channel_id      TEXT,
    prompt_version  TEXT,
    prompt_tokens   INTEGER,
    completion_tokens INTEGER,
    latency_ms      INTEGER,
    finish_reason   TEXT,
    state_delta     TEXT,                      -- 🔒 JSON,StateDelta(Pointer->新值),见 §3.4/§3.5
    -- 🆕 结算五态与截断重放所需的字段见 §3.5(settlement_status / superseded_at 等)
    reasoning       TEXT,                      -- 推理模型的思维链,可折叠展示
    is_edited       INTEGER NOT NULL DEFAULT 0,
    is_streaming    INTEGER NOT NULL DEFAULT 0 -- 进程被杀后用于清理半成品
);

CREATE INDEX idx_msg_session     ON messages(session_id);
CREATE INDEX idx_msg_parent      ON messages(parent_id);
CREATE INDEX idx_msg_session_time ON messages(session_id, created_at);
```

**为什么是树(ADR-004):**

| 功能 | 树的实现 |
|---|---|
| 多候选 Swipe | 同 `parent_id` 的兄弟节点,切 `is_active_child` |
| 重新生成 | 新建一个兄弟节点 |
| 从某条重开 | 把新消息挂到该条的 parent 下 |
| 回档 | `session.current_leaf_id` 指回祖先,旧分支完整保留 |
| 编辑消息 | 原地改 `content` 并置 `is_edited=1`(或新建兄弟,取决于产品选择) |

**当前路径物化**(渲染用):

```kotlin
// 从 current_leaf_id 沿 parent_id 回溯到根,再反转
fun materializePath(leafId: String): List<Message>
```

长会话下回溯上千次查询会慢 → 优化:在 `sessions` 表缓存一份 `path_cache`(消息 id 的有序数组 JSON),每次追加消息时增量更新;缓存失效时重建。

## 3. 游戏状态:事件溯源

### 3.1 为什么不存"当前状态"

```
❌ session.current_state = {hp: 76}
   → 重新生成 AI 回复时无法回滚
   → 切换对话分支时状态与剧情对不上
```

```
✅ GameState = fold(session.initial_state, path 上所有 message.state_delta)
   → 分支天然隔离
   → 重新生成 = 新兄弟节点 = 自动用新的 delta
   → 回档 = 换 leaf = 自动重算
```

### 3.2 性能优化:检查点

路径长(>100 条)时每次 fold 开销可观 → 每 20 条消息落一个检查点:

```sql
CREATE TABLE state_checkpoints (
    msg_id TEXT PRIMARY KEY,     -- 该消息处的累计状态
    session_id TEXT NOT NULL,
    state_json TEXT NOT NULL
);
```

计算时:从最近的祖先检查点开始 fold 剩余部分。

### 3.3 状态对象

```kotlin
@Serializable
data class GameState(
    val numbers: Map<String, Double> = emptyMap(),   // hp, gold, turn
    val flags: Set<String> = emptySet(),
    val items: List<String> = emptyList(),
    val affinity: Map<String, Int> = emptyMap(),
    val strings: Map<String, String> = emptyMap(),   // location, time_of_day
)
```

通用容器而非为每个字段建类 → 角色卡可自由定义状态字段而无需改代码。

### 3.4 🔴 v1.1 修订:状态改用 **JSON Pointer 扁平寻址**,不用上面那五个桶(E1)

`§3.3` 的 `GameState` 把状态硬分成 numbers / flags / items / affinity / strings 五个桶。
**实测三份真实材料后,这个设计不成立。**

真实角色卡(`DiLaoJSON.json`,E1)的状态是**任意深度的嵌套对象**:

```json
{"地牢": {"难度": "待选", "总轮数": 0, "是否最终轮": false},
 "冒险者": {"生命": 60, "生命上限": 60, "攻击": 10},
 "装备": {"武器": "断齿短刀", "强化": 0},
 "物品栏": {"材料": [{"name": "铁片", "count": 3}], "消耗品": []},
 "敌人": {"名称": "", "生命": 0}}
```

`冒险者.生命` 和 `敌人.生命` 是两个不同的字段,扁平成 `numbers["生命"]` 会直接撞键。
而 SillyTavern 生态(`docs/15 §1.3`,E1)的寻址方式是 **JSON Pointer**:

```text
/地牢/难度 = "简单"
/冒险者/生命 = 58
/物品栏/材料 = [{"name":"铁片","count":3}]
```

**定稿设计:**

| 项 | 规定 |
|---|---|
| 状态存储 | 单个 `JsonObject`(任意嵌套),根命名空间沿用 `stat_data`(为与酒馆生态互通留口) |
| 寻址 | **JSON Pointer 字符串**(允许中文键 —— 对中文模型更友好,且生态里就是中文) |
| `delta` 的形状 | `Map<String /* JSON Pointer */, JsonElement>` |
| `delta` 的值语义 | 🔴 **绝对新值,不是增量**(`docs/05 §4.4.2`、`E-3b`) |
| 变量目录 | 另存一份「路径 + 类型 + 约束(min/max/枚举)」索引,**只有路径和类型,没有值**(`docs/05 §1.2`)。它才是发给模型的东西 |
| 累加 | `fold` 时按 Pointer 逐项 `set`(而非数值相加)—— 因为是绝对值,所以**幂等** |

```kotlin
@Serializable
data class StateDelta(
    /** JSON Pointer -> 结算后的新值(绝对值)。未变化的路径不出现。 */
    val changes: Map<String, JsonElement> = emptyMap(),
    /** ≤100 字的自然语言姿态快照,给下一轮叙事用(docs/05 §2.8) */
    val posture: String? = null,
    /** 一句话依据,用于「点数值看为什么变」(E-5b) */
    val reason: String? = null,
    /** 客户端校验记录:CLAMPED / UNKNOWN_PATH / DELTA_TOO_LARGE / NO_OP … */
    val violations: List<String> = emptyList(),
)
```

> ✅ **幂等是关键收益。** 增量语义下,同一条 delta 重放两次就会多扣一次血;
> 绝对值语义下重放多少次都一样 —— 这是 `§3.5` 截断重放的**前提条件**。

### 3.5 🆕 结算状态与截断重放(`A-18` 的存储支撑)

`docs/05 §4.5` 规定状态栏有五态,`§4.7` 规定用户编辑历史楼层后要**截断重放**。
这对存储层提出两条要求:

**(1) `messages` 表加结算状态字段**

```sql
ALTER TABLE messages ADD COLUMN settlement_status TEXT NOT NULL DEFAULT 'pending';
    -- pending / running / done / failed / replaying
ALTER TABLE messages ADD COLUMN settlement_attempts INTEGER NOT NULL DEFAULT 0;
ALTER TABLE messages ADD COLUMN settlement_error TEXT;       -- 失败原因,给「点击重试」用
ALTER TABLE messages ADD COLUMN superseded_at INTEGER;       -- 🔒 非 NULL = 该 delta 已作废
```

🔴 **`settlement_status` 必须落库,不能只放内存。**
进程被杀后,一条 `running` 的消息要能恢复成 `failed` 并给出重试按钮 ——
否则就复制了 tavern 客户端「更新失败且无人管」的缺陷(`R-T30`,E1)。

**(2) 作废用标记,不用删除 —— 事件流只追加**

```
用户编辑第 N 层正文
      ↓
UPDATE messages SET superseded_at = now()
  WHERE session_id = ? AND <在当前路径上> AND created_at > (第 N 层);
      ↓   ← 注意:delta 本身不删,只标记。要能回头看「原来算成什么样」
从第 N 层开始重新结算,新 delta 作为新记录追加
      ↓
fold 时 WHERE superseded_at IS NULL
      ↓
期间状态栏 = replaying,显示「重算第 N/M 轮」
```

| 规则 | 理由 |
|---|---|
| **只标记不删除** | ① 事件流的基本纪律;② 用户要能对比"改之前算成什么样";③ 删了就无法排查结算器的 bug |
| `state_checkpoints` 必须一并失效 | 第 N 层之后的检查点全部删除(检查点是派生数据,可以删),否则 fold 会读到旧的累计值 |
| 重放失败的那一层 | 标 `failed` 但**不阻断后续**:后面的层用上一个有效状态继续,状态栏保留红点 |

> ✅ **铁律 3 的价值在这里第三次被证实。** 若当初选了"直接存当前状态快照",
> 这整个功能做不了 —— 而真 SillyTavern 把"用户编辑过更早楼层"列为结算规则的**最高优先级场景**
> (`docs/15 §7.4`,E1),说明这在真实使用中很常见。

### 3.6 🆕 消息树的三层结构(避免把三件事混在一张表里)

实测 `dsh-tavern` 的导出结构后,一条"对话"其实有三层,**不能都塞进 `messages.content`**:

| 层 | 内容 | 存哪 | 为什么要分开 |
|---|---|---|---|
| **① 原始正文** | 模型返回的原始字符串(含 `<initvar>` 等卡自带标签) | `messages.content` | **归档用,永不改写**。导入的卡可能带标签,剥离逻辑以后会变,原文必须留着 |
| **② 显示用正文** | 剥离状态块、应用「镜像正则」后的可读文本 | 派生,不落库(或落 `display_cache`) | 渲染管线会升级;落库就等于把一次性的渲染结果永久化,以后改不动(`docs/15 §7.3`) |
| **③ 结算产物** | `StateDelta`(Pointer → 新值)+ `posture` + `reason` | `messages.state_delta` | 它来自**第二次独立调用**(`ADR-010` 方案 C),与正文是两回事,生命周期也不同(正文成功而结算失败是常态) |

🔴 **最容易犯的错:把剥离后的正文写回 `content`。**
一旦这么做,用户导入的卡自带的状态块就被永久丢弃,以后想改剥离规则也救不回来。

## 5. 备份格式(H-1)

```
mirage-backup-20261015-2130.zip
├── manifest.json        {schemaVersion, appVersion, exportedAt, counts, hasKeys: false}
├── characters.json
├── sessions.json
├── messages.jsonl       ← 逐行 JSON,支持流式写入,避免大会话 OOM
├── memories.json
├── lorebooks.json
├── presets.json
├── settings.json        ← 不含 API Key
└── media/
    ├── avatars/
    └── portraits/
```

**原则:**

1. 导出 **结构化 JSON 而非直接拷贝 .db 文件** —— 跨版本恢复可控,且用户可读、可人工修补。
2. 默认 **不含 API Key**。若用户显式勾选,需另设密码并对 keys 段单独加密(PBKDF2 + AES-GCM)。
3. `manifest.schemaVersion` 决定导入时的迁移路径;低版本备份导入高版本 App 必须可用。
4. 导入提供两种模式:**合并**(按 id 去重)/ **覆盖**(清空后恢复),默认合并并给出变更预览。
5. 导出用 `MediaStore` / SAF 写到用户可见目录,不要只存应用私有目录。

## 10.1 🔴 作废 §9 中关于 `strictSet` 的表述

§9 原文写了「`strictSet` 语义 ≈ 我们的 G1 路径白名单」。**这是错的，以本节为准。**

MVU 上游源码 `update_variables.ts` 的真实行为：

| 事实 | 影响 |
|---|---|
| **路径必须已存在，否则报错跳过** —— 这是 `set` 命令的**无条件默认行为**，与 `strictSet` 无关 | ✅ 我们的 **G1 可以放心默认开**，这是对齐行业标准而非额外限制 |
| `strictSet`（默认 `false`）真正控制：是否关闭对 **ValueWithDescription**（`[值, "描述"]` 二元组）的特殊处理。`false` 时 `_.set(path, 新值)` **只替换第 0 个元素、保留描述**；`true` 时整体替换 | 🆕 我们**必须支持这个数据形态**，否则导入带描述的卡会把描述文字冲掉 → `B-15` |

详见 docs/16 §1。

## 10.2 ValueWithDescription 的处理规则（`B-15`）

MVU 里一个字段可以是 `[值, "给模型看的说明"]`，例如：

```json
{ "冒险者": { "生命": [60, "当前生命值，降到 0 则死亡"] } }
```

这个二元组同时承担两个职责：**存值** + **给模型解释这个字段是什么**。

Mirage 的处理：

| 环节 | 做法 |
|---|---|
| 导入 | 识别 `[标量, 字符串]` 形态 → 值存进状态快照，描述存进 `FieldSpec.description` |
| 结算 | 只改值。**描述永不参与结算**，模型无权修改它 |
| 注入 Prompt | 描述作为字段说明注入，这正是它的用途 |
| 导出 | 还原成 `[值, "描述"]`，**往返无损** |

> 注意第二行等价于「`strictSet` 在我们这里恒等于 `false` 的行为」。
> 我们不提供这个开关 —— 让模型能覆盖掉字段说明没有任何正当用途。
> 若导入的卡写了 `strictSet: true`，记录在 `extensions.mirage.importNotes` 里原样导出，但运行时不照做。

## 11. 消息树与事件流:已落地核心(2026-10-23)

**现在可以回答「为什么这么存」了。** 上面 §1~2 的表设计是照抄 ST 画出来的 E3 级别猜测，
还没写一行建表 SQL。而本节是 **E1 级别的已实现代码**(`MessageTree.kt` + `StateEventLog.kt`)，
配着 **17 个单测**（消息树 8 + 事件流 9）,覆盖了列表存法做不到、而我们必须做到的全部边界。

### 11.1 为什么对话记录要存成树

一眼看上去，聊天记录就是一串消息，用列表存最省事。但有两个常用操作，列表结构根本做不出来：

**一、重新生成（同一句话要几个不同版本）。**
对同一条提问，模型可以给出好几个回复，用户挑一个用。
这几个回复是**并列**的，它们共用同一个「上一条」。
列表里一个位置只能放一个，所以要么覆盖掉旧的（挑完就回不去了），
要么把它们前后排成一串（那就变成「模型连说了三遍」，意思全变了）。

**二、改掉更早的一句话，后面重新来。**
用户把第 3 轮自己说的话改一下，第 4 轮往后就应该从那里重新长出来，
而原来的第 4 轮往后要能留着。这在列表里只能靠删除，删了就没了。

换成树就很自然：**每条消息记住自己的上一条是谁**。同一个上一条下面挂了几条，
它们就是几个并列的候选；从某条往下重新长，就是在那条下面挂一个新分支。

「现在正在聊的是哪一条线」由一个单独记下来的末端决定：
从末端那条一路往上找上一条，找到头，就是当前这条线的全部内容。

🔴 **这是整个项目唯一一处「现在不做对，以后改不动」的地方。**
列表换树意味着存储、界面、状态回放三处同时重写，所以从第一版就按树存。

### 11.2 为什么状态栏要存「变化记录」

最直觉的做法是建一张表，每项一行，改了就把那一行覆盖掉。
这样状态栏当前显示什么最省事，但有三件事会立刻做不到：

**一、切回更早一轮，数值回不去。**
用户把第 5 轮重新生成，状态栏应该回到第 4 轮结束时的样子。
只存当前值的话，第 5 轮改掉的那些数字已经把旧值覆盖了，没地方找回来。

**二、分支之间会互相污染。**
同一句话生成了两个版本，一个版本里挨了一刀、另一个没有。
这两条线的数值必须各自独立，而覆盖式的一张表只有一份数值。

**三、说不清数字是怎么变成这样的。**
用户问「我的血怎么只剩一点了」，覆盖式存法只能回答「现在是 12」。

换成「只追加变化记录」之后，**当前值 = 开局值 + 把这条线上的变化按顺序加一遍**。
上面三件事都成了同一个动作的自然结果：
换一条线，就换一个「哪些变化算发生过」的集合，重新加一遍。

### 11.3 代价与快照

代价是每次要加一遍。长会话里变化记录会攒到几千条，每次翻页都重算不现实。
应对是**另外存快照**：每隔若干轮把当时的完整数值记一份，
回放时从最近的那份快照往后加。

快照纯粹是为了快，丢了随时能重建，所以它可以被安全地删掉或重算 ——
这是它和变化记录的根本区别。

### 11.4 关于「反向撤销」

反向撤销（把 after 换回 before 倒着减）是个很容易想到但错的做法：
中间任何一步被代码修正过，倒着减就回不到原值了。
**从开局值重新加一遍则永远准确**,且和修正没修正无关。

这正是我们存 `before` / `after` 两个字段而不是存 `delta` 增减量的原因 ——
记录里存的是「改完之后是多少」,重放天然幂等,同一批变化加两遍结果还是一样。

### 11.5 对角色卡的存储(关联但无依赖)

角色卡本身就是一个 JSON 字符串，直接整段存进 `sessions` 表的 `card_json` 列。
一局用的是哪张卡、卡里写了什么，都能从这一列里完整拿回来。

**不把卡拆成一堆外键关联表的理由**：拆了之后，每次读一张卡要 join 好几张表，
而我们根本不会「查某个字段在哪些卡里出现过」这种跨卡分析 ——
用户只会「打开某一局，继续玩」或者「导入 / 导出某一张卡」，
这两个操作都是整卡进、整卡出，拆表只会让代码复杂、读写变慢。

## 10.3 每轮必须持久化「结算前快照」

证据（E1，`dsh-tavern/tavern-plugin/lib/index.js:4123`）：

```js
throw new Error('这轮旧记录没有结算前快照，无法安全重新结算变量')
```

→ **重算功能的前提是存了结算前快照**。DSH 为此留了一条专门的错误信息，说明它踩过「没快照导致无法重算」的坑。

我们的存储设计（铁律三：状态存事件流）天然满足，但要**显式保证**：

| 字段 | 说明 |
|---|---|
| `turnId` | 绑定消息树节点 |
| `preSettlementSnapshot` | 结算前的完整状态快照 |
| `proposals` | 模型原始提议（**原样存**，包括被守卫拒绝的） |
| `receipt` | 结算回执（7 态 + changes + failures） |
| `basedOnRevision` | 🔴 结算时所基于的剧情版本，回来时校验，不匹配 → `Stale` |

存原始 `proposals` 的理由：排查「模型到底想干什么」时，只有回执是不够的。
而且这是我们将来优化 Prompt 的唯一数据来源。

> ⚠️ 空间成本：每轮一份全量快照，长局会膨胀。
> M3 优化方向：快照改成「每 N 轮一个全量 + 其间存 delta」，重建时回放。
> M1 先用全量，**不要提前优化** —— 角色扮演单局很少超过几千轮，几 MB 的量级完全可接受。
